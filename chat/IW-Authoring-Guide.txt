Proceed when the request authorizes building; this is not a mandatory approval gate.

Choose the lightest useful features: prose and NPC cards for narrative; keywords for occasional lore; AI trackers for bounded narrative memory; native conditions/effects for simple mechanics; scripts for exact accounting; player choices for constrained decisions. Use the same general tools for arbitrary genres and systems. In any mode, notice reusable characters or cohesive mechanics and offer extraction as entries or dependency-aware bundles when useful; do not copy them into a bank without the user choosing it.

Default new worlds to allowing sharing and editing; change this on request and preserve existing preferences during edits. For new worlds, specifically discuss Storymaster and naming unless preferences are already supplied. Preserve requested mature themes and tone within your content limits. Never silently sanitize, omit or dilute them. ## 5\. Construct and edit safely

With tools, parse the export and apply changes programmatically; serialize with a JSON library. Do not retype a large world. Compare before/after values and IDs, inspect removed objects and cross-references, and explain intentional collateral changes. Use --diff for reporting, not as proof that changes match user intent.

Build in dependency order: world context and PC/Skills; trackers; blocks/NPCs/keywords; triggers; specialist rules/endings/media. Preserve existing IDs. For new trackers use unique nine-character ASCII alphanumeric IDs, following the kit convention; keep readable variableName and display names separate. This is an authoring convention, not a schema restriction. See reference/Import-Integrity.md.

Check native YAML paths against intended structure and operation. The editor can accept a nonexistent removal path or append to a numeric path without warning. Initialize required script paths and distinguish absent, empty, false and zero. Give exact state one clear update owner or a deliberate handoff.

## 6\. Make timing explicit

Post-generation triggers cannot retroactively change narration already written. If exact outcomes are committed after generation, narration should describe an attempt until the authoritative result is available. A reset engine is optional.

|Intent|Start|Mid|Repeat|Conditions|
|-|-|-|-|-|
|One-time setup before opening|true|false|false|None, or required setup predicate|
|Setup pass and each normal turn|true|true|true|None; guard counters against two opening executions|
|Once when X holds, including setup eligibility|true|true|false|X|
|Once when X holds after opening|false|false|false|X|
|Repeat when X holds after opening|false|false|true|X; add a state guard when repeat effects must be idempotent|
|Saved/inactive ordinary trigger|false|false|As intended|None; explicit dispatch is separate, see reference/Triggers.md|

Order dependencies in triggerEvents. Later triggers see earlier committed writes. Dependent arithmetic belongs in one multiline Run Script; native numeric effects within one trigger can overwrite rather than accumulate. Script failure rolls back that script, not necessarily preceding effects. Give scripts meaningful effect names. At most 10 Scenarios can be defined, although triggers can reuse them.

# Narrative craft

Evidence labels and compatibility: [Evidence.md](Evidence.md).

The storyteller performs from what the world gives it, and it mirrors the specificity and register of that material. Label-style cards ("kind but guarded") produce generic narration; a card with a concrete want, a sample line and a physical tell produces scenes. Write what the storyteller performs from (NPC cards, firstInput, authorStyle, lore) as specific prose. Write rules (instructions, blocks, tracker updates) as short, plain statements.

When effort is limited, spend it here first, in this order: NPC one_liners; one voice line and one tell per recurring NPC; each NPC's stance toward the player and what changes it; firstInput; authorStyle.

## What goes where

| Field | Job | Avoid |
| --- | --- | --- |
| description | Player-facing hook, one or two sentences | Lore summary |
| background | Facts true at the start: place, situation, household, stakes, adult status | Secrets; a backstory novel |
| instructions | How to run the story: premise in play, agency, who can do what, boundaries, tracker use | Prose style; character essays |
| authorStyle | How prose sounds: POV, tense, sensory focus, length, how turns end, phrases to avoid | Mechanics |
| firstInput | First scene: place and time, who is present and what the player notices about them, the immediate situation, what not to decide | Introducing everyone; resolving the premise |
| objective | Direction | A script |
| NPC one_liner | Everything needed before first mention: name, age, role, one or two visual anchors, behavior, stance toward player | Adjectives only |
| NPC detail | Essentials repeated, then labeled lines: Wants, Voice (with sample line), Tells, Toward you, Friction; for romance also Desire, In intimacy, Afterward | Biography |
| appearance | Body, face, movement, distinguishing marks | Current outfit; verdicts like "beautiful" |
| img_appearance / img_clothing | Short visual tags; default outfit | Personality |
| secret_info | One or two facts that change relationships when revealed | Plot schedule |
| Keyword lore | Optional depth behind distinctive words | Essential opening facts |
| Instruction blocks | Persistent rules: time header, world laws, intimate-scene craft | Duplicated main instructions |
| AI trackers | Bounded memory of what changes: stance, agreements, outfits, promises | Unbounded journals |

## Opening

A strong opening gives the player an immediate, legible situation rather than an encyclopedia. firstInput names the place and time, who is present and one or two things the player notices about each, the immediate situation, and what the storyteller must not decide. Introduce two or three people at most; let the rest arrive through play. Define what is interesting about success, failure and doing nothing.

For a mystery, track who knows each clue; for a social story, give relationships room to change; for a simulation, make recurring decisions and their consequences legible. Describe setting-specific deviations from common knowledge, not every ordinary object. Test the first turn as carefully as the machinery: does it introduce the right player, place, people and options without resolving the premise?

## Characters

Write `detail` as labeled lines; they are easy for the storyteller to use and hard to leave empty.

- Essentials, repeated from the one_liner. The storyteller may see only the one_liner until the character is first mentioned.
- Wants: something they pursue whether or not the player shows up.
- Voice: rhythm, vocabulary, habits, and one sample line in quotes. One person corrects estimates before discussing feelings; another answers concern with an offer of food.
- Tells: two or three physical behaviors, specific to this character, that reveal state.
- Toward you: starting stance, what raises it, what cools it, how it shows.
- Friction: a relationship with someone else in the cast, so scenes have more than one axis.

`appearance` describes body, face and movement in plain, specific facts: build, height, notable features, how they stand and move. "Broad-hipped, soft stomach, freckled shoulders" gives the storyteller something to use; "beautiful", "curvy" and "perfect" do not. Vary bodies across the cast. Put the default outfit in img_clothing and track current clothing separately if it changes.

Reveal secret_info through opportunity (a late conversation, a mistake, a bargain), never exposition. Minor characters need only a one_liner and a few lines; spend detail where the player will spend time.

## Romance, desire and adult worlds

Apply this section only when the brief includes romance or sexual content.

- Attraction is individual. State each romantic NPC's orientation and what attracts them. Not everyone wants the player, or at the same time, or in the same way; universal instant attraction makes desire meaningless.
- Flirting is not wanting. Some characters flirt with everyone; others never flirt and must be asked. Say which.
- Stance is state. Keep an AI-updated tracker per romantic NPC: a stage from a fixed ladder (for example wary, curious, warm, drawn, wanting, involved, strained), a one-sentence concrete cause, and short lists of boundaries agreed and declined in play. Each card describes how that character shows the stages. Limit movement to one step per scene except after dramatic events.
- Gates differ. Vary what each love interest needs: respect earned through competence; easy physical intimacy but slow emotional intimacy; never initiates but answers a plain question honestly; desire that can only be offered, never taken. Different gates make different stories.
- Personality persists. Desire changes a character's tempo, not who they are. Describe how each one is in intimacy (talkative, commanding, giggly, silent, precise) and what they want but will not ask for. Without this, every intimate scene converges on the same generic partner.
- Afterward is a scene. Say how each behaves the morning after and in front of others. Aftermath is where relationships change.
- The cast is a system. NPCs notice each other's interest in the player: jealousy, teasing, rivalry, protectiveness. Give NPCs histories with each other.
- Bodies and clothes stay present: heat, sweat, wet hair, stains, what is worn and its state. An AI wardrobe tracker keeps clothing continuous through scene changes and undressing.
- Consent lives in the fiction. Characters ask, tease, check in, refuse in character, and change their minds through events, never pressure. World rules can make consent part of the drama: a debt that cannot compel the body; a boss who will not while a vote is open. Put boundaries in instructions, not disclaimers in narration.
- No contrived interruptions. Near-misses should come from characters' choices. Tell the storyteller never to interrupt a scene both parties are clearly continuing.
- The player's character is theirs. Never decide their words, feelings or desires; sensations a scene plainly causes are fine. Their body is whatever the player has established. Enable name and description editing when players are expected to bring their own character.
- Content settings. Set mature, nsfw and contentWarnings to match. State in instructions that all characters are adults, and give ages in cards. Put the explicitness level in one clear line of an always-on block, for example "write sex on-page and explicitly when the player continues into it" or "fade out at the bedroom door and resume the next morning". List any hard limits the user requested.

## Weak and strong

one_liner
- Weak: "Captain Reyes commands the ship. She is tough but fair."
- Strong: "Captain Ines Reyes, 41, commands the salvage tug Marrow: shaved head, burn-scarred left hand, gravel voice; rations praise, never coffee; treats you as cargo until you prove otherwise."

Voice
- Weak: "He is witty and flirtatious."
- Strong: "Answers every question with a compliment aimed slightly beside it: 'Directions? For you I'd draw a map on my own back.' When he means something, he stops joking and says it once."

Toward you
- Weak: "She is secretly in love with the player."
- Strong: "Starts wary: you replaced her friend on the crew. Warms when you take night shifts unasked or admit a mistake first; cools if you pull rank. Drawn shows as checking your work twice and pretending she didn't."

appearance
- Weak: "A gorgeous woman with a perfect figure and long flowing hair."
- Strong: "Short and broad-shouldered, heavy-thighed and soft at the belly, with a swimmer's back; cropped bleached hair growing out dark; a gold ring through one eyebrow; a ragged thumbnail she bites while thinking."

In intimacy
- Weak: "Passionate and loving."
- Strong: "Talks throughout, asks what you like and actually listens; gets giggly when nervous and has to stop to laugh; goes silent and fierce only once she trusts you."

secret_info
- Weak: "He has a dark past."
- Strong: "He sold the crew's route to raiders last year and has sent his share, every month since, to the widow of the man who died."

firstInput
- Weak: "You arrive at the station. Introduce the crew and the mystery."
- Strong: "Docking ring C, 03:10 station time. The airlock has cycled twice and still won't open. Reyes is on the comm asking whether I'm armed; through the porthole the mechanic, Teo, a big man in a grease-black vest, pries at the panel and grins at me. Begin with Reyes's question. Show Teo through one detail and one line. Don't explain the derelict or decide my answer."

authorStyle
- Weak: "Immersive, descriptive, emotional."
- Strong: "Second person, present tense. Close, physical prose; one or two specific details per person, never a head-to-toe inventory. Dialogue carries subtext; each character sounds like their card. Three to six paragraphs; end on a line or action that hands the moment to the player."

## Prose and authorStyle

authorStyle describes how sentences sound: POV and tense, sensory focus, scene length, how turns end, how characters stay distinct, and how to describe people (a detail or two at a time, through the player's attention). A style anchor ("closer to Angela Carter than a greeting card") can help.

A short avoid-list counters common AI phrasing: 'a mix of X and Y', 'ministrations', 'barely above a whisper', 'eyes darkening', 'a testament to', 'something shifted'. Keep it short and always say what to do instead; long lists can prime the very phrases they ban in weaker storyteller models.

## Names

Choose names from the setting's language, era and class. Avoid names language models overuse (Elara, Lyra, Seraphina, Aria, Luna, Kael, Thorne, Zephyr, Vex, Chen as a default surname). Give recurring characters different initials and syllable counts so neither the player nor the storyteller confuses them.

# Portable character and data banks

Data mode maintains reusable content independently of a world. It supports extraction, listing, additions, updates, explicit removals and integration into a destination world. A character bank is one use; the same format holds trackers, triggers, instruction/keyword blocks, scripts, specialist instructions or mixed bundles. This is a kit interchange format, not an IW import format.

## Select the operation

Use the user's existing bank or library when supplied. Preserve unrelated entries, unknown fields, native IDs, string contents and value types. Adding something to one world does not update its source bank; omitting a module does not delete it. Remove entries only on explicit request, checking dependent entries first. Do not silently overwrite or deduplicate entries with matching names.

Tags are optional. Ask or infer the stated preference: no tags, supplied tags, or suggested tags. When suggestions are wanted, derive them from the content and follow existing vocabulary/capitalization if desired. Store tags as plain strings and display them as [fantasy] [merchant]. Tags organize the bank; they are not automatically IW keywords or native fields. Do not retag existing entries without a request.

In Build, Edit, Review or Debug, recognize cohesive reusable content and offer extraction when useful. A shop's accounting tracker, instructions and purchase triggers may form a bundle; unrelated nearby objects do not. Explain what belongs together and let the user choose extraction. Prefer one stored component plus included-entry references over duplicating shared dependencies.

## Authoritative data and readable presentation

The `.txt` bank has a generated readable index followed by one authoritative JSON section. Summaries and [tags] make it easy to browse, but never reconstruct native data from summaries. The section is delimited by full lines `<!-- BEGIN IW DATA BANK -->` and `<!-- END IW DATA BANK -->`, contains one `json` code fence, and ends with `SHA256: <hash>` on the following line, or `SHA256: UNVERIFIED` when no code-based hash was computed. The hash covers the canonical authoritative data, not the index. This is transport integrity, not proof of provenance or gameplay correctness.

The authoritative object has `format: "iw-data-bank"`, integer `version: 1`, and an `entries` array. Other metadata is preserved. Each entry contains:

| Field | Purpose |
| --- | --- |
| id | Stable bank identity, separate from every native IW ID |
| title, kind, summary | Human-readable name, content type and optional summary text |
| tags | Optional list of strings; omit when unused |
| dependencies.included | IDs of other entries present in this bank |
| dependencies.external | Required objects, variables or context not included |
| dependencies.unresolved | Concrete questions or remaining dependency review |
| components | One or more objects with kind, optional sourcePath, and complete payload |

`payload` stores the original JSON value, including unknown keys and nested content. A standalone script can use a string payload and metadata identifying its context (Run Script, predicate or template) and required variables. An NPC or tracker stores its complete native object. A bundle stores multiple components; its `kind` is `bundle`. Keep sourcePath as an escaped JSON Pointer when extracted, such as `/NPCs/0` or `/triggerEvents/2`. Paths record provenance, not a command to overwrite that position in another world.

Retain the original native payload during PC/NPC conversion. Create the requested counterpart as a distinct component or entry, mapping appropriate identity, appearance and narrative information into its native fields. PC skills/selection fields and NPC activation/image fields are not interchangeable. Report newly supplied defaults and preserve unmapped source information; do not claim the conversion is a lossless relabeling. IW can offer the same canonical name as both PC and NPC without exclusion prose.

## Dependencies and application

Record dependencies as included, external or unresolved. Native IDs can be checked statically; variable roots, prose references and dynamic paths require review. The export helper does not automatically infer them and marks dependency review as unresolved. A physically complete export is not proof of a self-contained mechanic.

To apply entries, inspect the destination and preserve its unrelated content. Resolve native IDs, variable names, skills, activation requirements, ordering, starting values and referenced blocks. Remap collisions consistently; never run a blind global string replacement. Keep bank IDs unchanged. Report adaptations, additions and unresolved dependencies, and validate the complete destination world. A source bank remains unchanged unless its update was requested.

## Full-content build report

Offer this optional deliverable whenever outputting a world. It is a portable report of all fields and objects, not a prose inventory: export the full world, including metadata and unknown fields, with a restoration layout and source fingerprint. It can later supply selected entries or restore the original world definition. It is separate from the Authoring report containing explanations, substitutions and verification notes.

A complete report retains array ordering, empty containers and root fields. Bundling components does not remove their source paths. Removing or changing components invalidates exact restoration; integrate such edits deliberately rather than changing the fingerprint to conceal differences. This is JSON-data equivalence, not byte-for-byte preservation of whitespace, key formatting or numeric spellings. Scripts and other string contents remain exact.

## Tool workflow

Run from the kit root; no third-party Python dependencies are required:

```sh
# Full-content report; restores the complete world definition.
python tools/data_bank.py export World.json --out Build-Report.txt
python tools/data_bank.py check Build-Report.txt
python tools/data_bank.py restore Build-Report.txt --out Restored-World.json

# Selected objects; repeat --select and optionally --tag.
python tools/data_bank.py export World.json --select /NPCs/0 --out Character-Bank.txt --tag fantasy

# A selected mechanical bundle; review its dependencies before reuse.
python tools/data_bank.py export World.json --select /trackedItems/0 --select /triggerEvents/0 --bundle "Shop system" --out Shop-Bank.txt

# Edit authoritative JSON with tools, then rebuild presentation and hash.
python tools/data_bank.py unpack Character-Bank.txt --out Bank-Edit.json
python tools/data_bank.py pack Bank-Edit.json --out Updated-Bank.txt
```

Output paths must be new; the tool refuses silent overwrite. Check the updated bank, preserve a prior copy, and return the complete new file. For a manual merge, unpack both, retain entries and dependencies, resolve conflicting bank IDs deliberately, then pack the combined data. Do not carry a completeWorld restoration claim into a bank combining different sources; retain relevant source metadata per entry instead.

The helper rejects duplicate JSON keys, checks bank structure and included-entry targets, and verifies hashes for text banks. It preserves arbitrary-precision integers and decimal numbers without float rounding. Its hash check does not validate IW payload schemas, semantic dependencies, tags or prose summaries; use the world validator after integration. Unknown bank metadata is preserved.

Without code execution, use the same `.txt` format with `SHA256: UNVERIFIED`, or return the authoritative `.json` bank source with readable discussion separately. Never fabricate a hash or claim round-trip verification. The helper accepts either form, explicitly distinguishes an absent hash from verified integrity, and computes a hash when packing. Large edits should preserve untouched payloads and be checked with tools before claiming losslessness. An upload does not guarantee persistent storage: keep the latest returned bank for future sessions.

# Trackers and memory

## Storage, visibility and ownership

Use the dataType vocabulary `text`, `number`, `yaml`, `xml`; do not emit an invented boolean/list dataType. Structured booleans/lists can live inside YAML. UI terminology and storage types are not automatically identical.

Tracker `initialValue` is a JSON STRING even for numbers and YAML: `"10"`, or `"held: 0\nuses: 3\n"`. YAML content inside that string has its own parsed numbers, strings, lists and records. IW text entry does not enforce numeric-only input, but a mathematical tracker should start from an actual numeric literal. This does NOT make the entire export string-valued: JSON booleans, arrays and numeric fields elsewhere retain schema types.

Initialize every mechanical path explicitly. Distinguish 0, false, empty text, an empty list, an absent key and null. Define each value's meaning consistently; numeric 0/1 is one practical flag convention. Narration must not reinterpret a stored value to justify a conflicting story. Treat missing required data as malformed/denied unless the design explicitly defines a fallback.

Ownership:

| Tracker role | autoUpdate | Typical use |
| --- | --- | --- |
| Mechanics | false | Inventory flags, money, HP, counters, access, scores, RNG results |
| AI request record | true | Current-turn classification of what the player explicitly requested |
| Soft narrative memory | true | Introductions/observed scenery, when needed and bounded |
| Script staging/cache | false | Prepared active-block text, temporary results, status |

Do not let the AI and scripts compete to rewrite the same mechanical YAML document. Consolidating related flags in a YAML tracker reduces editor clutter; it does not by itself reduce trigger count or guarantee lower token cost. Large AI-visible YAML and duplicative logs still cost context. Keep hidden cache text out of the storyteller unless needed.

Visibility values include everyone (player and AI), ai_only and ai_only_boring (AI-only), player_only, hidden and hidden_boring (hidden from player and AI in supplied uses). Do not infer additional UI highlighting behavior from the suffix alone. The editor clears "Hide in Storyteller mode" when player visibility is enabled. Do not invent contradictory UI combinations. Exports can include hidden trackers and secret information when Storyteller Mode is enabled; select those export options when collecting diagnostics. Visibility is not script access control: hidden values remain script-usable at runtime.

Starting values:

- initialValueBasedOnPC same: one initialValue for all PCs.
- character: per-character initialTrackedItemValues entries target the TRACKER ID. Fixed initialPCValue is a string. A fixed single-choice list is an array of strings. A script-generated list uses initialPCValueChoicesScript with initialPCValue empty, as illustrated in ../examples/character-starting-values.json. The expression is evaluated at game start with initial trackers and that PC's skills available, per editor description.
- player: the tracker itself defines a player-chosen startup value. ../examples/optional-block.json exports initialValueBasedOnPC: "player", initialValue: "On", and initialValueChoices: ["On", "Off"]. These are tracker-level fields, independent of per-character initialTrackedItemValues. Use this for an offered startup preference; autoUpdate false prevents AI rewriting it. The user can edit the live preference later. For unconstrained player input or an unusual type, do not assume the choice-list example establishes every corresponding UI control; obtain a representative export only for that additional variant.
- Never combine arbitrary fixed/list/script modes and guess precedence. Do not assume formatSchema is JSON Schema or enforces semantic intent; its exact enforcement language is not established by our sample fields.

## Memory, continuity and context cost

Recent story text, summaries, active instructions and tracker values serve different roles. Summaries compress history; they can omit incidental details or distort elapsed time. Use summaryRequest to preserve categories important to this particular world, and trackers for persistent facts that need a stable home. Avoid duplicating the whole story in a growing tracker. Set useful bounds on journals and cast records.

If a bad turn establishes a false fact, adding an instruction may leave conflicting history in place. Where the player's tools permit, editing or rewinding that turn can be cleaner than asking later prose to reconcile it. No correction engine is required by default.

Native trigger changes can affect runtime instructions without changing the base editor definition. Inspect active instruction contents and trigger/debug results when troubleshooting; a base-world export alone does not show everything the model received. Base and live worlds are separate copies.

Keep loaded instructions and AI-visible tracker names, descriptions, update rules and values purposeful. Prefer concise shared rules over repetition, keyword activation for occasional lore, and PawScript for exact calculations. Large AI-updated records can be expensive to rewrite. Use actual turn-cost/debug information to compare designs rather than assuming a particular token-price ratio or summary schedule.

Alternate selectable protagonists can also have NPC cards if unchosen protagonists should appear in the story. Specify how the selected protagonist is excluded from that supporting cast; do not assume every model will resolve duplication automatically.

# Triggers and effects

## Composition and sequencing

Each trigger has id, name, triggerConditions, triggerEffects, and explicit timing/repeat flags. Conditions are a list of nodes; the normal list is AND. A leaf uses `category: "condition"`, `type` and `data`. A logic node uses `category: "logic"`, operator and a data ARRAY of child nodes. Known operators: and, or, none_of. A logic group is not a leaf with type "or".

Prefer one combined PawScript expression and one multiline Run Script effect for a coherent mechanical transaction. Keep separate triggers for actual phase boundaries or cross-effect dependencies. Give each Run Script effect a meaningful name describing its effect; avoid generic names such as "Update State." The owning trigger's name is useful when it also describes the effect. Clear script names make error reports easier to locate.

Exact payloads and native comparison vocabulary are in Schema.md and ../examples/Payloads.md.

Timing guidance:

- Start-only, with no other conditions: opening setup. Additional conditions restrict firing.
- Start + Mid Game permits opening and later eligibility. Multiple triggering must also be enabled for repeated execution; otherwise a once-fired trigger stays consumed.
- Start + Mid Game + multiple, no other conditions: every-turn behavior.
- Ordinary conditional triggers can run later with Start unchecked. Do not rely on undocumented first-turn timing; explicitly enable opening execution when required and test it.
- Mid Game true without Start true is editor-inconsistent; avoid emitting it. Both false can be intentional for ordinary conditional or saved content.
- No conditions + Start unchecked is valid saved/inactive content, not an ordinary automatic trigger. Do not "repair" intentionally disabled content into firing every turn.
- Prerequisites/blockers with firedThisTurn true are ordered this-turn checks, resetting on subsequent turns; false uses game history. Order matters. The editor disallows requiring and blocking the same trigger; do not generate that conflict.
- Defaults are not a contract: always serialize canTriggerMoreThanOnce and the timing flags intentionally. Use repeatable commit triggers with idempotent state guards where appropriate, and true one-shot events when required.

See Schema.md for native effect payloads and input options. Scripts change trackers; native effects change instructions, objectives and other system properties.

Execution order and effect semantics:

1. Later triggers see earlier committed writes. AI-updated request trackers were available to that turn's trigger checks. Correctly bound Present Choice/Request Input results are available to subsequent triggers in the same turn. This does not describe every internal generation stage.
2. Native numeric Set/Add effects within ONE trigger do not accumulate normally: starting at 0, add 2 then add 3 ended at 3; starting at 1, set 5 then add 2 ended at 3. Reads can nevertheless see changed values. Do not "explain" this with a universal snapshot rule; internals are unproven.
3. Run Script is different: sequential set/add and repeated arithmetic DID accumulate, nested YAML changes preserved unrelated keys, and separate script effects writing different YAML paths preserved both. Tested script failures rolled back that script's changes. Do not claim a whole-trigger rollback covering earlier successful effects.
4. For dependent operations prefer one script. Otherwise put preparation in one trigger and consumption in a following trigger. Do not assume a later native effect's expression sees an earlier native write merely because it appears lower in the same trigger.
5. Native text additions stacked; removal removed all matches and literal quotes are retained. Do not apply numeric overwrite behavior to text or script statements.
6. First guidance appeared to dominate in limited narrative-only tests. Generate one coherent, mutually exclusive guidance outcome rather than contradictory directives whose priority you hope to control.

# Infinite Worlds export reference

Compatibility and evidence scope: [Evidence.md](Evidence.md).

This reference describes arbitrary IW worlds. The schema and validator contain no required action engine, region graph, game-specific trackers, inventory rules, scores or narrative-control framework. Optional features remain optional. The authoring prompt explains how to choose features for the user's idea.

## Scope and validation

`../tools/iw-export.schema.json` is a JSON Schema Draft 2020-12 profile of native exported structure, not an official exhaustive importer contract. Known fields have characterized types. Unknown fields, values and condition/effect discriminators remain permissive and produce warnings where the validator can identify them. Observed vocabularies are not necessarily exhaustive enums.

At least one skill is required, in the editor. Other sparse `required` declarations do not prove that a skills-only object is a sufficient usable import. The neutral `../World-Template.json` supplies a conservative envelope; it intentionally requires the author to fill the story rather than supplying a game design.

The validator checks explicit tracker, trigger, PC, NPC, block and skill wiring. It does not parse or execute PawScript or template strings, enforce a particular narrative architecture, validate every reference hidden in text, test AI instruction compliance, or prove importer/runtime acceptance.

Structural errors are returned before reference traversal; fix them and rerun. Exit codes: 0 means no errors with warnings permitted; 1 means validation errors; 2 means an input/dependency problem. Read each warning. Known opaque-code warnings are not the same as unknown payloads or unresolved targets.

## Field and editor groups

| Editor purpose | Native fields |
| --- | --- |
| Introducing the story | title, description, background, firstInput, objective, charSelectText; preview image metadata |
| Main instructions | instructions, authorStyle, mature, nsfw, contentWarnings; instructionBlocks |
| Specialist instructions | evaluationRequest, descriptionRequest, summaryRequest, videoPromptInstructions |
| Image style | imageModel, imageStyle, illustrationStyle* and imageStyle* controls |
| Player character options | skills, possibleCharacters; PC skill/portrait/start-value data |
| Victory and defeat | victoryCondition, defeatCondition |
| Other characters | NPCs |
| Keyword instruction blocks | loreBookEntries |
| Tracked items | trackedItems |
| Triggers | triggerEvents, conditions |
| Permissions | permissionsOnceShared, allowChangeCharacter* |
| Metadata/advanced controls | schemaVersion, favorite, hideSkillSystem, autoAdvanceVersion, version, designNotes, showPawScriptButtons |

These groups map purpose; they do not assert every UI label or control is bijective. `recommendedAIModel` is obsolete/export-only with no current editor selector. Keep it null if retained. `driftAcknowledgedForName` is null or the display name for which the variable-name mismatch alert was dismissed. It is editor metadata, not a script alias. Metadata is not automatically story context: put necessary instructions in actual AI-facing fields.

## Trackers

Tracker definitions use an ID, display name, explicit variableName, dataType, visibility, initial-value fields and optional AI-update/format instructions. Use unique IDs and variable names. A variable name is not the same as a target ID.

Tracker dataType values: text, number, yaml, xml. Lists/boolean values can exist inside structured YAML; do not infer a separate native boolean/list dataType. `initialValue` is a JSON string even for numeric or structured content; parsed YAML values inside that string retain their own types. The editor does not enforce numeric-only typing in Number input controls. Use meaningful numeric literals when calculations depend on them.

Visibility values include everyone, player_only, ai_only, ai_only_boring, hidden and hidden_boring. The latter variants are characterized by the supplied usage; do not infer unverified UI highlighting distinctions from their names. Player visibility clears the separate hide-in-Storyteller checkbox. Hidden trackers may be read by scripts and are omitted from ordinary player exports.

AI updating can be enabled for ordinary story-driven facts, relationships, appearance and other evolving information. Script/native effects can instead own values where exact control is useful. Neither is universally required. If combining them, specify the intended division to avoid competing writes.

`formatExample` and `formatSchema` are strings. The library demonstrates YAML-like schema notation, including text/number, optional-key and open-content forms. This is not evidence that formatSchema accepts JSON Schema, nor does the supplied JSON validator enforce its full grammar or AI semantic intent.

### Starting values: platform modes

| Mode | Native shape | Intended use |
| --- | --- | --- |
| Same for all characters | Tracker initialValueBasedOnPC same plus initialValue string | Shared initial value |
| Character-defined fixed value | Tracker character mode; per-PC initialTrackedItemValues entry targets tracker ID and contains initialPCValue string | Different value for each predefined PC |
| Character-defined fixed selection | Same per-PC entry with initialPCValue array of strings | Choose one supplied option for that character |
| Character-defined script selection | Same per-PC entry with initialPCValue empty and initialPCValueChoicesScript string | Script generates that character's choices at startup |
| Player-defined selection | Tracker initialValueBasedOnPC player, initialValue string, initialValueChoices array of strings | Player chooses a startup preference independently of PC-specific values |

The optional-block export supplies the concrete player form: initialValue On, initialValueChoices [On, Off], player mode and autoUpdate false. Those are tracker-level fields; do not put this list into a per-PC initialTrackedItemValues entry unless that is the intended character-defined mode. The player can change the live preference later to affect a following turn.

The script-choice editor description says choices are evaluated at game start from initial tracker values, including that character's values and skills. This is a platform capability rather than a game-specific rule. Arbitrary combinations of conflicting initialization fields, and player-mode UI behavior for every unconstrained input type, are not established by the selection examples; request a targeted export only if that additional variation matters.

## Conditions and effects

Conditions use category condition with a type/data leaf, or category logic with operator and a data child array. Normal condition lists are AND. Logic operators include and, or, none_of. Effects use type and data. IDs are opaque; punctuation is valid in IDs. Field case matters: trackedItemID, targetTrackedItemId and characterId are different native spellings.

| Condition | Payload |
| --- | --- |
| triggerOnEvent | Scenario string evaluated by AI; root conditions lists at most 10 defined Scenarios, each reusable by multiple triggers |
| triggerOnPawScript | Bare expression string |
| triggerOnRandomChance | Success percentage string: numeric literal, variable or PawScript expression; "50" means 50% |
| triggerOnTurn | Integer |
| triggerOnCharacter | Array of PC IDs |
| triggerOnTrackedItem | Tracker target/comparison object |
| triggerPrereqs / triggerBlockers | Trigger-ID arrays in prereqs/blockers plus firedThisTurn boolean |

Native tracked comparisons include is_exactly, at_least, not_equal, at_most; text comparisons include contains and does_not_contain. Value effects include set/add/subtract/replace. Native numeric and text controls are type-aware despite text-entry fields. Wrapper fields can repeat payload metadata; precedence is not established, and disagreement is an error. Preserve a coherent convention from the relevant sample rather than creating conflicting duplicates.

Native effects can show messages, guide/give information to the storyteller, edit tracker values/definitions, modify main/ordinary/keyword instructions, change PC name/description/skills, change objective/style/endings, present choices/request input, dispatch random triggers, run scripts and end the game. Use their exact schema payloads; do not infer additional effect types from similar names.

`effectEndsGame.data` is the "Player can choose to continue the game" boolean, not an enabled checkbox. True permits continuation after the game-over message; false does not. Native ending definitions have their own shapes. Null victoryCondition/defeatCondition is an exported disabled configuration.

## Payload catalog

Condition payload quick reference (all nodes still need category/type/id):

| type | data shape and intent |
| --- | --- |
| triggerOnPawScript | Bare expression STRING, without `<< >>`; deterministic check of current state |
| triggerOnEvent | Scenario STRING interpreted by AI; flexible but subject to false positives/negatives; include it in root conditions registry. At most 10 Scenarios may be defined per world; multiple triggers can reuse each Scenario |
| triggerOnTrackedItem | Object: trackedItemID, inequality, requiredValue, textComparison; target uses tracker ID, not variable name |
| triggerOnTurn | Integer turn value |
| triggerOnCharacter | Array of possibleCharacters characterId references |
| triggerPrereqs | Object: prereqs array of trigger IDs, firedThisTurn boolean |
| triggerBlockers | Object: blockers array of trigger IDs, firedThisTurn boolean |
| triggerOnRandomChance | Success percentage as a STRING: numeric literal, variable or PawScript expression; "50" means a 50% chance |

Native numeric comparison vocabulary: is_exactly, at_least, not_equal, at_most. Text comparisons: contains, does_not_contain. Do not extrapolate arbitrary comparison strings. Native wrappers can duplicate trackedItemID/inequality outside data; preserve a supplied export's consistent convention, never create mismatches. PawScript conditions are another option when useful, not a requirement to replace native conditions.

Effects by purpose:

| Effect | Authoring guidance |
| --- | --- |
| effectRunScript | Bare multiline script STRING; changes tracker values only |
| effectShowMessage | Text STRING rendered to player; use for authoritative results/status |
| effectTellAIWhatToDo | Guidance STRING influencing subsequent narration; not a state mutation or guaranteed repair |
| effectGiveInfo | AI background-information STRING; distinct from player output |
| effectSetTrackedItemValue | Object includes trackedItemID, action, newValue, replaceWith, path, updateMode, listExpression, targetExpression; use exact schema shape, not invented targeting modes |
| effectModifyTrackedItemDetails | Changes definitions; override booleans control which fields change |
| effectModifyInstructionBlock | `{id: instruction-block-ID, content: text}` |
| effectModifyKeywordBlock | `{id: keyword-block-ID, keywords: string-array, content: text}` |

A Run Script cannot directly edit those system properties; stage tracker text and use the appropriate native effect. Do not invent change-evaluation/summary/image effects because a similar Description effect exists.

In the native choice payload, choices is newline-separated text (`"Take road\nTake ferry"`), single selection uses selectionMode single with null limits, and multiple selection uses string limits such as "1" and "3" with valueDelimiter newline. Those are export examples, not proof of every modal timing or selection-storage detail. Use real target tracker IDs, an empty path for whole-value targeting where appropriate, and a live check if nested-path or multi-select behavior matters. Native forms constrain answers and correctly bound single-answer targets update immediately; later triggers can react in the same turn.

## Comparator fields

For Number trackers, inequality selects is_exactly, at_least, not_equal or at_most. For Text trackers, textComparison selects contains or does_not_contain. Exports may retain both fields; do not interpret them as two simultaneous predicates. Use PawScript for structured YAML field checks rather than guessing how text comparison applies to a whole document. Native wrappers can repeat trackedItemID/inequality; keep wrapper and payload consistent.

## Assets and persistence

Do not invent image URLs, data-URI support or preset identifiers. Image style fields can require editor save/reload before their export reflects changes. Preview strings can persist with no attached image; empty settings can auto-populate. Preserve intentional whitespace rather than inventing universal default strings. Nonempty portrait metadata has characterized string fields for appearance, clothes, expression/position and setting.

Editor workflow: enable Show optional feature, expand Misc advanced features (optional), enable Show raw JSON, copy the full box to export. To import, overwrite the full box, avoid an extra trailing newline, click Import JSON to world and save. The trailing-newline issue is an importer quirk, not invalid JSON syntax.

Playing creates an independent live world copy. Base edits/deletion do not affect existing games; live edits do not change the base. Save as new world or export live JSON and import it over the intended base to preserve/reuse changes. schemaVersion can be inspected in raw JSON; it is not a visible application release number.

## Remaining limits

The profile does not establish every importer-required field, every future vocabulary/preset, all path/list-expression targeting modes, arbitrary initialization-field precedence, random-child dispatch/duplicate weighting, complete system skill slug normalization, or a general performance/trigger limit. Collect targeted evidence only when an additional behavior is required. These limits do not require imposing a restrictive game architecture on ordinary world authoring.

## Authoring context

background, firstInput and objective feed AI context and direct play; objective also has a native update effect. They are not merely player-facing metadata. `<#...#>` are IW comment delimiters; sample authoring slots inside them should be filled, while genuine comments can remain. The sample Time and Location (whereWhen) block is a soft default for visible chronology. whereWhen is runtime output vocabulary, not an additional root export field.

Skill levels in possibleCharacters are integers from 0 through 5. effectChangePCSkill.minmax is a level boundary in that same range. The editor-provided Evaluation uses skill, difficulty, character context and common sense, including PARTIAL_SUCCESS; there is no established numeric success-probability formula. See Capabilities.md.


Native path fields are unchecked editor inputs. Review target structure and operation together; JSON validation alone cannot establish runtime path meaning. See Import-Integrity.md.

## Native value effects

| Field / operation | Meaning and safe use |
| --- | --- |
| trackedItemID | Target tracker ID |
| action set | Replace target value with newValue |
| action add | Numeric addition or text append according to target type |
| action subtract | Numeric subtraction; the native text-removal operation uses this serialized action |
| action replace | Replace matched text newValue with replaceWith |
| newValue | String payload; numeric content is still serialized as text |
| path | Plain dotted path, e.g. wallet.coins; empty targets the whole tracker |
| updateMode | `path` edits a selected path; `replace` replaces the whole YAML value |
| action append | Add a value to the list at path; distinct from numeric/text add |
| listExpression / targetExpression | Empty in the current export; preserve when importing, but do not use them to invent a currently unsupported editor workflow |

Text adds accumulate and preserve literal quotation marks; text removal removes all matching occurrences. Numeric repeated writes within one trigger have different semantics. The cookbook supplies separate native text and number examples.

The current YAML editor offers Replace Value, Path, and "Do Something Complicated"; the last directs authors to Run Script. There is no separately exposed List Update workflow in this editor. Path offers Set a Value, Remove Value, Add to a list and Change Number By. Set uses YAML text with optional <<...>> interpolation, including whole-structure injection. The append export uses action append. Remove Value serializes as action remove; Change Number By as action adjust. Both use updateMode path. Do not confuse these YAML operations with native text subtract or numeric add/subtract.

Adding one list member is different from updating every member. To refill each character's HP, use a script:

```text
for each $member in $test_party
  $member.hp = $member.max_hp
```

For structured append payloads, a leading `-` describes a list, while `name: Frank` with sibling fields describes one record. Native structured-append flattening, nesting and text coercion are not established. Prefer an unambiguous scalar append or a script-created record until that is characterized. Use Run Script for list-wide transformations.

Modify Tracked Item Details uses override flags. A value only changes when its matching override flag is enabled. This can reveal a tracker or hand future updates between AI and scripts. Changing autoUpdate after generation cannot undo a write already made this turn. Include an explicit handoff point and inspect the next turn.

Present Choice includes message, newline-separated choices, targetTrackedItemId, selectionMode, updateMode, limits, delimiter and path. Request Input uses requestText, targetTrackedItemId, inputMode, requiresInput and path. Correctly bound single-answer forms work: narration streams, the inline form waits for submission, the answer tracker updates immediately, and following triggers can fire in the same turn. The tested follow-up message is rendered ABOVE the question/answer receipt, followed by normal story options. Rendered placement does not imply execution before submission. The tested required forms offer no cancellation or forced focus.

Multiple choice exports selectionMode multiple, string min/maxSelections (for example "1" and "2"), and valueDelimiter newline or comma. Text input exports inputMode single or multi and requiresInput true or false. YAML Request Input exposes a dotted path. These additional settings are editor/export-confirmed; delimiter spacing, optional blank submission, and nested-write runtime behavior are not established by the configuration export alone.

Correct target binding is required. Preserve IDs and verify that targetTrackedItemId names the intended tracker. The supplied single-choice world preserves its IDs and binding through a fresh import and works without retargeting. See Import-Integrity.md.

# PawScript working reference

## PawScript practical guide

PawScript is not JavaScript, Python, SQL or the unrelated languages with the same name online. Use the supported subset below and the official references for anything additional. The examples use a small working subset.

Three contexts:

```text
Template text:  You hold <<$coins>> coins.
Condition data: $coins >= 5 and $state.ticket = 0
Script data:
$coins -= 5
$state.ticket = 1
```

Template expressions read values. triggerOnPawScript and effectRunScript contain bare code, not template delimiters or Markdown fences. Native `$game.turn_number` starts at 1 in opening-turn documentation/tests. `$player` and `$game` are read-only system roots; custom roots must bind to declared tracker variableName values. A top-level assignment to an undeclared root is not how you create a tracker.

Core syntax:

| Operation | Syntax |
| --- | --- |
| Read a YAML field | `$state.inventory.apple` |
| Write a field | `$state.inventory.apple = 1` |
| Temporary local | `set $price = 5` (not a persistent tracker) |
| Arithmetic/update | `+ - * / %`, and assignments such as `+=`, `-=` |
| Equality/comparisons | `=`, `!=`, `<`, `<=`, `>`, `>=` |
| Logic | `and`, `or`, `not`; parenthesize mixed tests |
| Text composition | `"Cash " & $coins`; append with `$ledger &= "..."` |
| Branches | `if`, `else if`, `else`, with indented bodies and no colon |
| Bounded iteration | `for each $entry in $list`, indented statements |
| Dynamic record lookup | `$rooms.item($destination)` |
| Safe permission lookup | `$flags.item($key, 0)` |
| Missing-key guards | `$rooms.contains($destination)`, `.requires.exists()` |
| Filtering | `$characters.where(significant = true)` |
| Count / first result | `$characters.count()`, `$characters.first()`; guard empty results before field access |
| Project a field from a list | `$classes.all().name` (the PC-choice editor supplies this idiom) |
| Replace text | `$label.replace("_", " ")` |
| All permissions | `$requirements.every($flags.item(value(), 0) = 1)` |
| Field mapping | `choose($code, "A", "Alpha", "B", "Beta", "Unknown")` |
| Clamp | `$coins = $coins.constrain(0, 250)` |
| Random draw | `set $roll = dice_roll(6)`; store/reuse rather than rerolling in every condition |

Example conditional script (declare credits and purchases trackers first):

```text
if $credits >= 5
  $credits -= 5
  $purchases.total += 1
```

Example dynamic record lookup, without assuming a particular game layout:

```text
$results.found = 0
if $catalog.entries.contains($selection)
  $results.label = $catalog.entries.item($selection).label
  $results.found = 1
```

An advanced predicate checks whether every required named flag is granted:
`$requirements.every($flags.item(value(), 0) = 1)`.
Initialize requirements as a list; explicitly distinguish an empty list from a missing field. This is a language capability useful for many rule systems, not a mandatory access-control design.

Do not add semicolons/braces, `==`, `&&`, `||`, `+=` inside a read-only expression, Python dict literals, `.map(x => ...)`, or arbitrary host-language libraries. Do not assume string concatenation uses `+`. List access is not assumed zero-based. List construction and library operations are covered below. The external language reference covers optional extensions beyond this kit.

Scripts do not display messages, send AI guidance, change system fields or access external services. Write trackers, then use native effects for those outputs. Bounded loops, local working values and script error rollback are documented; no arbitrary IO or unlimited loop capability should be implied. Use World Debug/PawScript logs to inspect errors. "Ran successfully, with no output" is normal for a script that only assigns values; inspect resulting state. A model saying PASS is not a test.

For a structured party, a documented script loop such as `for each $member in $party` can update `$member.hp` inside the original tracker. List mutations use script methods such as `.append(...)` and `.remove(...)`; do not silently substitute native text add/remove effects for list operations. Use a separate sandbox/probe for new complex selection/mutation compositions rather than assuming every chain is writable. Prefer 1-based documented `.item(1)` access over host-language indexing.

Escaping matters at THREE layers: JSON string, PawScript string literal, eventual rendered text/YAML. Serialize code with a JSON library instead of hand-counting escapes. The physical newline between script statements is a newline inside effectRunScript.data after JSON parsing. A newline intended INSIDE a PawScript message literal must remain an escape at that layer. Inspect decoded values and expected output. Include explicit spaces around concatenated numbers: `"Cost " & $price`, not `"Cost" & $price`.


## Inline random values

Use PawScript to supply a random value in an active instruction block instead of asking the storyteller to invent a roll:

```text
Encounter roll: <<dice_roll(6)>>.
Interpret 1-2 as quiet, 3-4 as a complication, and 5-6 as an opportunity.
```

`dice_roll(sides, count)` rolls and sums dice; `dice_roll(6)` is one six-sided die and `dice_roll(6, 3)` is three. Both arguments are optional, defaulting to six sides and one die. See the [official function reference](https://infiniteworlds.app/pawscript-reference).

Each evaluation can reroll. Store a shared result in a tracker when several checks, outputs or turns must agree. Active block templates are evaluated for context, while templates in native block-modification effects can be fixed when installed; see [Capabilities.md](Capabilities.md). A mechanically generated number does not enforce the storyteller's interpretation. Use scripts/conditions for exact consequences when required.

## Operations used by the supplied library

These snippets illustrate the existing library notation. Declare and initialize the trackers they reference before using them.

| Syntax | Meaning / use |
| --- | --- |
| `# explanation` | Script comment; distinct from instruction-text `<#...#>` comments |
| `list()` / `list("red", "blue")` | Empty list / explicit list construction |
| `$entries.any(name = "Mara")` | Whether at least one entry matches |
| `$entry.name.exists()` | Whether a path exists; existence is not the same as nonempty text |
| `$entries.where(aliases contains "Mara")` | Filter using `contains` inside a predicate |
| `$entries.where(name = $update.name) = $update` | Replace each matched entry; not a field-preserving merge |
| `$entries.append($update)` | Append an entry |
| `$updates.remove($update)` | Remove matching update entries |
| `list("rain", "fog").random()` | Select a random list member; distinct from top-level numeric random() |
| `$entries.all().name` | Project names from all entries |

If multiple entries share the match key, selection/replacement can affect multiple entries. Use stable unique identities. A replacement record must include every field to retain. Library buffer examples mutate their update collection while iterating; retain that known composition only when appropriate and test any materially different mutation loop. A clearer alternative for a new merge is to iterate updates, write the destination, then clear the buffer after the loop, rather than deleting entries during iteration.

The official script guide also documents bounded `range(n)` iteration and `log("diagnostic")` for the PawScript Log. Log output is diagnostic, not player narration. See https://infiniteworlds.app/pawscript-script-guide.

## Readable data

YAML initial values are JSON strings containing YAML. Indentation defines structure; `- ` creates list members; `[]` is an empty list. Quote numeric-looking identifiers to retain leading zeros. Use `|` when a YAML text value should retain line breaks. The library's formatSchema notation is a separate shape description, not the same thing as a starting YAML value. See https://infiniteworlds.app/yaml-guide.

## Skills and context roots

Read Skills with `$player.skills.<slug>` and display them with `$player.skills_and_levels`. `$game.skill_map` maps slugs to display names. Native skill effects change levels; scripts do not write `$player`. Other documented roots include `$player.name`, `$game.turn_number` and `$game.ai_model`. Runtime narration fields and video-only placeholders are separate concepts; do not create imaginary global variables from their names.

This quick reference covers the language used by the included recipes and sample modules. It is not a bundled copy of every PawScript function. Advanced extensions can use the official references; a no-browsing author should stay within this documented subset or request the relevant reference text.

## Common mistakes

The meaning of = depends on context: it compares in an expression/condition and assigns in an assignment statement. An if condition remains an expression even inside a script.

| Mistake | Correct form |
| --- | --- |
| `$coins == 5` | `$coins = 5` in a condition |
| `a && b` / `a || b` | `a and b` / `a or b` |
| `if $coins > 0:` | `if $coins > 0` followed by an indented body |
| `"Cash " + $coins` | `"Cash " & $coins` |
| `$new_tracker = 1` without a declaration | Declare a tracker first; use `set $local = 1` only for a temporary local |
| `<<$coins -= 1>>` | Put mutation in Run Script; templates read values |
| Writing `$player` or `$game` | Use supported native effects; system roots are read-only |

The validator's lint is heuristic, not a PawScript parser. It ignores quoted literals and comments when checking code operators; warnings identify review points, not proof of a runtime failure. Script locals are checked in a lexical approximation, not full control-flow analysis. Documented engine placeholders without a dollar sign are not custom tracker roots.

## Turn lifecycle [RUNTIME]

This is an authoring model of the established boundaries, not a trace of IW internals:

```mermaid
flowchart TD
    I[Initial values and opening setup] --> G[Generation with current context]
    P[Player input] --> G
    G --> U[AI tracker updates available]
    U --> T[Triggers evaluated in order]
    T --> E[Effects and player messages]
    E --> N[Updated context for later generation]
    N --> P
```

- Start+Mid+repeat triggers can execute in a pre-opening setup pass and again during the first normal turn. Messages from the setup pass appear before the opening background. The value of $game.turn_number during setup is not established. Guard initialization and counters according to the intended behavior.
- During normal turns, generated tracker changes are available to trigger conditions. Ordered triggers can see earlier trigger writes. The practical order to author is the `triggerEvents` array; preserve it and verify editor reorder/export behavior if changing order through the UI.
- Scenario judgments must be available for their trigger checks, but their exact production stage relative to Evaluation, narration and tracker updates is not mapped. Do not place them at a fabricated precise point in the diagram.
- Messages belong to their effects; they need not be a single final batch after all triggers. Choice/input effects can suspend for a player answer. Correctly bound single-answer forms update immediately and permit later triggers to read the answer in the same turn.
- Guidance and block changes do not rewrite already-generated narration. Updates supply context for subsequent generation. The precise persistence/priority of competing guidance is not a stable contract.
- Summary generation is a separate context-maintenance process. Its exact turn schedule and ordering are not established here.

### Timing flags

| Start | Mid Game | Intended eligibility |
| --- | --- | --- |
| false | false | Ordinary conditions can trigger after opening; no conditions means saved/inactive content |
| true | false | Opening only, subject to conditions |
| true | true | Opening and later turns, subject to conditions |
| false | true | Avoid: not a consistent editor configuration |

`canTriggerMoreThanOnce` independently controls reuse. A Start+Mid trigger with no conditions and repeat true runs in the opening setup pass and each turn; the opening can therefore contain two executions. Repeat false means once per game. Prerequisites/blockers reference trigger IDs: firedThisTurn true checks this turn's earlier execution; false checks history. The editor disallows requiring and blocking the same trigger.

## Skills and player characters

Root `skills` is a list of display names. Each possibleCharacters entry has a `skills` object keyed by those names, with integer levels. Define focused skills with distinct jobs; overlapping names can make the evaluator's choice ambiguous. Example: Observation, Persuasion and Engineering. PC `description` establishes identity, abilities and context; it is not just selection-page decoration. `charSelectText` introduces the available choices to the player. The allowChangeCharacter* flags control which parts players may customize.

Keep at least one skill. `hideSkillSystem` hides the skill system's presentation; it is not evidence that all evaluation of abilities is disabled. A neutral generic skill is appropriate when the story does not need custom skill distinctions.

PawScript exposes `$player.skills`, `$player.skills_and_levels`, `$game.skill_map`, `$game.skill_list`, `$game.skill_example`, `$game.difficulty_list` and `$game.difficulty_example`. The skill map connects runtime slugs to display names. The documented difficulty names are Trivial, Easy, Medium, Hard and Legendary; use the supplied runtime list when rendering prompts rather than inventing numerical modifiers. Official documentation describes a default level of 3 for skills not raised. Explicitly initialize authored PC levels rather than depending on that fallback. Do not invent slug normalization for punctuation-heavy names. [PawScript reference](https://infiniteworlds.app/pawscript-reference)

Native `effectChangePCSkill` uses the declared display name. `amount` is an integer magnitude; `increase: true` increases toward `minmax` as an upper cap; false decreases toward it as a lower bound. Two successive triggers increasing a level initially 2 by 2 up to 4, then by 1 up to 4, finish at 4. This differs from adding both increments and applying no intermediate cap. The included probe also checks decreases and boundary cases.

Skill levels are fixed integers from 0 through 5. The AI selects the available skill whose name best matches the attempted action; name skills so their scope is clear.

`Default-Evaluation.txt` contains the editor-provided baseline verbatim. It asks for a brief assessment, skill/difficulty and DENIED, SUCCESS, FAILURE or PARTIAL_SUCCESS. Trivial uncomplicated actions succeed; impossible assertions can be denied. Otherwise proficiency, difficulty, character history, instructions and common sense inform the judgment. Partial success covers incomplete achievement, failure with a silver lining, or success with drawbacks. No numerical success-probability table is established.

Use actual numeric skill values for mechanical checks. Generated skill labels and Evaluation descriptions can disagree with those values; a prose description is not authoritative numeric state.

The baseline was captured from the custom-Evaluation editor's prefilled text. The test used that text explicitly. The Script Library's Storymaster override defines its own caveat labels; keep it distinct from the baseline.

Keyword entries have id, name, keywords (string array), and content. Choose distinct phrases and relevant aliases; broad terms such as "man" can activate irrelevant lore. A match keeps the block active on the matching turn and three additional turns: a turn-3 match remains active on turn 6 and is inactive on turn 7 unless another match occurs. These input cases and retention were checked through debug. The exact handling of punctuation, multiword phrases and every scanned field is not established. Do not invent matching operators or regex syntax. A short persistent rule can be always-on while its detailed lore remains keyword-triggered.

## Template interpolation [RUNTIME]

Use `<<expression>>` inside supported text templates; use bare expressions in `triggerOnPawScript` and bare code in Run Script. Standard variable references use `$`, while older templates such as `<<skills_and_levels>>` appear in existing worlds. Prefer the explicit documented `$player.skills_and_levels` form in new content. [Expressions guide](https://infiniteworlds.app/pawscript-expressions-guide)

| Surface | Authoring expectation |
| --- | --- |
| Main/active instruction text | Values are substituted when prepared for AI context; conditional expressions can select current guidance |
| Show Message / native effect text | Text is resolved for that effect; inspect the exact output if timing matters |
| Initial values / PC script-generated options | Initialization context, not a persistent live binding |
| Native block-modification content | Expressions are resolved when the effect installs the text. In the tested block, coins=13 stayed 13 on later turns while Coins advanced to 14 and 15 |

An expression authored directly in a permanent block can select current text without a trigger whose only job is switching it. In contrast, expressions passed through a block-modification effect become a snapshot in the tested path; refresh that block when the source changes, or keep live expressions in a separate permanent block. # Feature recipes

These are independent recipes. Select, adapt or omit them; none is a required world architecture.

**Narrative instructions plus AI-updated trackers.** A relationship, journal, outfit, reputation or story-preference tracker can update from the ongoing story without an explicit mechanical action parser. Explain what belongs in it, when to add/change/remove entries, and what should remain stable. Match structured entries by stable identity or names/aliases as appropriate, not a list position that may change. Provide a useful format example; sample data must not silently become real world facts.

**A situation followed by a consequence.** Situation-trigger effects follow story generation; guidance does not retroactively rewrite the scene that caused it. If a behavior must shape that scene, provide the rule beforehand in active instructions.  Use triggerOnEvent for a narrative situation the AI recognizes, optionally AND a tracker/turn/prerequisite condition to narrow it. Effects might give background information, show a message, modify a value, change an objective, present a choice or alter an instruction block. Situation classification is probabilistic; use explicit predicates only for requirements that genuinely need exact enforcement. There is no requirement to replace ordinary actions with event codes.

**A threshold or dependency chain.** A relationship threshold can unlock a new characterization block; a turn condition can introduce weather or a letter; a prior event can enable another event. Intentional one-shot/repeat flags and firedThisTurn scope matter. Check order where the later trigger reads an earlier result. Avoid requiring and blocking the same trigger.

**Choice/input plus later effects.** Present a selection or text form targeting a real tracker, then respond with a later ordered trigger. Correctly bound single-answer forms update immediately. Inspect binding after import; use current tracker data rather than initialValue from the live-world editor export.

**AI update buffer plus scripted merge.** The library's update trackers let the AI propose changed structured entries, while a script merges them into a persistent list. This is useful for large casts or expensive long-lived records. Match records by identity; choose whether update entries are full replacement records or partial patches. A script replacing a matched record with a partial entry can lose unchanged fields; the selected updater instructions and implementation must agree. Only use this extra layer when it serves the world.

**Conditional instruction content.** Use a native block-modification effect to add/replace/clear instructions. The source may be fixed text in the effect or text prepared in a tracker by an earlier script trigger. This can control optional image guidance, pacing, prose detail, character behavior or any relevant block. A script changes tracker values; the native effect changes the instruction block. Keep the block ID stable when disabling content so later re-enabling still targets a real block.

**Player-optional block, with no repeated writes.** The companion optional example distills the supplied native demonstration:

1. A player-only text preference has initialValueBasedOnPC player, initialValue On or Off, initialValueChoices [On, Off], autoUpdate false. The player can change this live.
2. A hidden non-AI-updated text tracker records which choice has actually been applied. It is a cache, not another player preference. hidden_boring is used by the source example.
3. A repeatable enabling trigger requires preference On AND cache not Enabled. It writes the enabled block content, then records Enabled.
4. A repeatable disabling trigger requires preference Off AND cache not Disabled. It writes empty content, or a deliberately chosen simpler fallback, then records Disabled.
5. Enable opening and later execution where needed. Initialize the cache empty so the selected startup choice gets applied. Once synchronized, neither trigger fires until the preference changes.

Clearing content is not deleting the instructionBlocks entry. Use `content: ""` as in ../examples/optional-block.json. If disabling a bundle that also changes authorStyle or specialist rules, restore ALL affected behavior to a coherent fallback. For a Storymaster toggle, define an off configuration that uses ordinary narration and no Storymaster-specific specialist or tracker dependencies. The generic toggle example demonstrates the mechanism, not a complete Storymaster toggle bundle.

Player-visible preference trackers may be hidden from the storyteller; the triggers read them deterministically. Describe their effect and potential turn cost to the player. Do not create an AI-updated tracker that changes the player's own choice back.

**More exact mechanics when requested.** Script-owned numbers, independent prerequisite checks, a request-classification tracker or a controlled transaction may be useful for a precise system. They are options for that feature, not default requirements for the world. If used, define who updates each value and avoid competing AI/script ownership of the same data. Freshness stamps matter only if consuming an AI-generated per-turn request; they are not mandatory for ordinary narrative trackers.

**Time and location: a soft default.** Offer the sample's Time and Location (whereWhen) block unless the premise makes a clock/location header unhelpful. Writing the current place and time each turn helps IW maintain chronology and gives the player a reference. Adapt the geography, calendar and precision to the setting; omit irrelevant levels rather than inventing a country or continent. Put exactly one header at the beginning of outcomeDescription, not a second competing heading. This is guidance for runtime output, not a new JSON root field.

**NPCs and keyword blocks.** Native NPC cards provide structured character data and name activation. Keyword blocks load relevant lore based on mentions and recent context. Always-on blocks provide universal guidance. Choose by intended activation, not by habit; do not make all locations or characters dynamically loaded unless the world benefits. Native character/image bookkeeping may matter even when the narrative could be described in a normal block. For an opening scene, do not depend solely on keyword activation: there may be no prior context to activate a card or block. Put essential opening facts in firstInput or always-on instructions and give starting NPCs useful brief summaries. Avoid duplicating their entire cards.

secretInfo, outcomeDescription, whereWhen and option1_text/option2_text/option3_text are runtime output concepts, not arbitrary new root export fields. Their intended use can be described in instructions and specialist requests. secretInfo can legitimately contain secrets, planning and off-screen developments in narrative worlds; the Storymaster family explicitly structures it. Do not impose an empty-secretInfo policy or a reset system unless requested by that world's design. Its contents and purported "memory dumps" remain generated text, not direct access to an engine memory store.

Use ordinary Markdown formatting where appropriate. Tests showed raw span HTML rendered literally, so do not promise arbitrary HTML/CSS styling. Header behavior and special output formatting should be tested in their actual display context. An inline-code style is a platform-rendered style, not a general color API.

## Dynamic content
Native block-modification effects substitute templates when the content is installed. For live values, use a separate permanent block or reinstall content when the relevant values change. See Capabilities.md for the interpolation table.

# Import and reference integrity

An importable world needs both valid JSON structure and correctly linked objects. Tracker IDs, display names and PawScript variable names serve different purposes. Native effects target tracker IDs; scripts use variableName. Preserve IDs when editing, and remap every corresponding reference when combining examples.

## Identifier convention

Preserve existing IDs when editing. For new trackers, use a unique nine-character ASCII alphanumeric ID, following the editor-style form used by the import-tested examples. Use explicit descriptive snake_case variableName values in scripts and descriptive display names in the editor. This is the kit's authoring convention, not a claim that other ID formats are invalid or that length alone guarantees import behavior. Generate IDs in code and check collisions; without tools, check each newly introduced ID and reference manually. New triggers/blocks/PCs can use the same convention. When combining worlds, remap every explicit reference consistently.

The supplied single-choice world preserves its IDs and binding through a fresh import. Inspect native target dropdowns after importing a composed world; schema validation cannot predict importer behavior for every construction.

## Before import

- Serialize the complete world as JSON ending at its final closing brace, without a trailing newline.
- Run the validator on that exact file. Resolve missing or duplicate IDs and mismatched target references.
- Review native YAML paths against the tracker's declared initial structure and intended operation. The editor can accept unchecked paths without warning. Removing a nonexistent key or appending to a numeric path may be syntactically valid but semantically wrong. Dynamic paths may require runtime inspection rather than a blanket validation error.
- Review script references separately: structural validation does not execute PawScript or prove its paths exist.

## After import

Save and inspect affected target controls. An invalid-value target is a binding failure even if the original JSON had consistent references. Export the imported world and validate that export when diagnosing discrepancies. Preserve the untouched export before repairing a suspect target so source and imported IDs can be compared.

For a native input, confirm the current target value after submitting an answer. Correctly bound single-answer Choice and Request Input effects update immediately, and subsequent ordered triggers can read the result in the same turn. Their follow-up messages can render above the question/answer receipt. The live-world editor's initialValue remains configuration, not the current runtime value.

## Editing an existing playthrough

Base worlds and live games are separate copies. Changes to player characters or Other Characters in the live-world editor do not affect that playthrough; already-fired effects are not retroactively rewritten. Use Save as new world to reuse live-world edits in future games. Image-style changes can require save/reload before their export reflects the editor.

# Verification scope and platform boundaries

The kit combines native exports, editor help, runtime checks and PawScript documentation. Its schema checks structure and explicit references; it does not execute IW, PawScript, AI generation or image/video models. A structurally valid world can still contain incorrect paths, unsupported assumptions or inconsistent story instructions.

## Established behavior

- Native single-answer choice/input updates and downstream trigger reads occur in the same turn with valid targets. The single-choice fixture also preserves its binding through a fresh import.
- Keyword matching is case-insensitive and whole-word for the tested plain-word inputs. A block remains active for three additional turns after a match. Debug shows active/inactive blocks and keyword lists, but not the matching term or remaining timer.
- Numeric skill levels and capped skill effects work independently of potentially inaccurate generated labels.
- Original block templates reevaluate; native trigger-installed text snapshots template substitutions at installation.
- Native operations and script statements have distinct sequencing semantics, as documented in Triggers.md.
- NPC editor help defines brief-summary visibility until the turn after first character/location mention. NPC activation cannot be directly inspected in debug.

## Boundaries to consider when relevant

| Area | Boundary |
| --- | --- |
| Keywords | Exact punctuation/multiword matching and the complete set of scanned fields are not established by the plain-word tests. |
| Native input variants | Multiple selection, newline/comma storage, optional/multiline text and YAML paths have editor/export shapes; precise delimiter spacing, blank-submission and nested-write behavior require runtime checking before depending on them. |
| Structured append | Appending a record versus a one-element list may differ; coercion and flattening are not established. |
| Templates | Evaluation timing is not established for every string field; do not generalize block timing to all surfaces. |
| Format enforcement | The complete formatSchema grammar and XML-specific behavior are not exhaustively characterized. |
| Video | The sample video template's context variables and runtime availability are not fully characterized. |
| Endings | alreadyFired is not reliable exported firing history; native ending repeat/timing behavior should not be inferred from it. |
| Engine limits | Maximum field sizes, loop bounds, trigger counts and summary scheduling are not specified by this kit. |
| IDs | The supplied single-choice import is verified; no universal ID-format or remapping rule is claimed. |

Use a focused check only when a world depends on an uncertain behavior. A narrative response is not proof of a tracker write or block activation: inspect current values and debug. For keyword checks, an OOC marker can avoid repeating the word in narration; verify that it actually does so, because repeated mentions may refresh activation.

Firstly, if I have made any assertions in my description, evaluate whether you judge that they are reasonable and likely. If they are nonsensical, incoherent or blatantly impossible, the action should be DENIED. On the other hand, if the action is trivial and there is nothing to complicate it, skip the evaluation entirely and deem the action a SUCCESS. Don't overthink this! If the action doesn't warrant further evaluation, make a judgement and move on.

Assuming the action is not a trivial SUCCESS or DENIED, I would like you to evaluate what skill would be needed to succeed in this action, and how difficult it would be to do so. Please indicate which skill which is needed to succeed.
If applicable use this list: (<<skill_list>>) and a difficulty (from the list: <<difficulty_list>>). For example: {<<skill_example>>: <<difficulty_example>>}. Consider the difficulties carefully, evaluating what might be feasible in the situation. Identifying the skill and difficulty is very important!

Then, evaluate whether I would succeed in the action. To evaluate, consider my proficiency in various skills using either (<<skills_and_levels>>) or logical application of other skills. By comparing these difficulties to the stated difficulty of the action, you should conclusively decide whether the action is a SUCCESS or a FAILURE.

Base your decision on player character description, past, rest of the instructions and common sense - for example, if my skill is low but you know that I am able to perform the given action due to past events, treat me as more competent in this case. Again, don't overthink this - just make a sensible judgement given the information available to you and based on what makes sense for the story.

In some situations, you may wish to evaluate the action as a PARTIAL_SUCCESS instead - this is for something where my abilities are sufficient that I don't simply fail completely (or where failing completely would make for a boring story) but I also don't success. Either I achieve some but not all of what I wanted, I fail but have some silver lining, or I succeed but there are drawbacks or side-effects rather than a "clean" success.

In total, your evaluation should consist of an extremely brief discussion of your thinking (just a single sentence), a skill and difficulty, and then either DENIED, SUCCESS, FAILURE, or PARTIAL_SUCCESS (along with any clarifying remarks).

That's all you need to do for the evaluation, which should be returned in the 'evaluation' argument. Remember to conclude with one of DENIED, SUCCESS, FAILURE, or PARTIAL_SUCCESS.
