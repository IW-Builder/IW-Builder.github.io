# Compact native payload cookbook

[DOCUMENTED] Exact payload shapes, extracted from the complete example worlds. These are snippets, not independently importable worlds. Read ../reference/Schema.md for field semantics and ../reference/Triggers.md for timing. Copy the node into triggerConditions or triggerEffects as appropriate, assign a unique node ID, and declare/remap every target. For a coherent transaction, choose one complete recipe rather than concatenating unrelated snippets.

Every authored trigger also needs an id, name, conditions/effects arrays and explicit triggerOnStartOfGame, triggerMidGame and canTriggerMoreThanOnce flags. Conditions normally AND together. Scripts are bare code strings; messages may contain templates. String payload values remain JSON strings.

## triggerBlockers

Suppress an event if another trigger fired this turn or earlier in the game. Full world: [condition-triggerBlockers.json](condition-triggerBlockers.json).

```json
{
  "category": "condition",
  "type": "triggerBlockers",
  "data": {
    "blockers": [
      "trg-anchor"
    ],
    "firedThisTurn": true
  },
  "id": "node-condition-triggerBlockers-3"
}
```

Dependencies: triggerEvents trg-anchor (Anchor).

## triggerOnCharacter

Limit an event to selected player characters. Full world: [condition-triggerOnCharacter.json](condition-triggerOnCharacter.json).

```json
{
  "category": "condition",
  "type": "triggerOnCharacter",
  "data": [
    "pc-visitor"
  ],
  "id": "node-condition-triggerOnCharacter-1"
}
```

Dependencies: possibleCharacters pc-visitor (Avery).

## triggerOnEvent

Recognize an AI-judged narrative Scenario; define it once in root conditions. Full world: [condition-triggerOnEvent.json](condition-triggerOnEvent.json).

```json
{
  "category": "condition",
  "type": "triggerOnEvent",
  "data": "The player explicitly asks the clerk for a receipt.",
  "id": "node-condition-triggerOnEvent-1"
}
```

Dependencies: root conditions must include the Scenario text.

## Add Other Character (effectChangeOtherCharacters)

Native editor payload; Start picker only. It applies only in a trigger ordered above every Start Request Input or Present Choice, and an add needs at least one premade Other Character ([Verified-Behavior](../reference/Verified-Behavior.md)). Full world: [effect-effectChangeOtherCharacters-add.json](effect-effectChangeOtherCharacters-add.json).

```json
{
  "type": "effectChangeOtherCharacters",
  "data": {
    "action": "add",
    "character": null,
    "npc": {
      "id": "GuildPorter01",
      "name": "Tavin",
      "detail": "Tavin checks each crate against the delivery ledger and asks the clerk about missing entries.",
      "one_liner": "Tavin is the guild porter, responsible for incoming deliveries.",
      "appearance": "An adult man with a canvas apron and a weathered cap.",
      "location": "Guild storeroom",
      "secret_info": "",
      "names": [
        "guild porter"
      ],
      "img_appearance": "",
      "img_clothing": ""
    }
  },
  "id": "NativeEffect01"
}
```

For Add, character is null and npc contains a new character record with its own ID.

# Images, video and model-specific blocks

The export fields and editor controls for image style, portraits and video, and how instruction blocks are limited to particular storyteller models.

## Image style

The image-style editor is a reusable style with Name, Model and prompt wrappers. With separate character/scenery prompts enabled, Characters start/end and Scenery start/end add text before and after the respective image prompts; with it disabled, Start/End apply to every image. The export fields are imageStyleCharacterPre/Post and imageStyleNonCharacterPre/Post; a shared Start/End is exported by duplicating the values into both pairs, so no extra switch is needed. The imageStyle value is a generated identifier; preserve it rather than deriving it from the prompt text. A world export carries the style's values, not the reusable style itself.

The older illustrationStyle*LowPriority/HighPriority fields still occur in exports but have no current controls; preserve them in existing worlds and author with the current Pre/Post wrappers, which took precedence over them in testing. Manticore is the model that editor help recommends; its preset text includes IWBeautiful/IWUpscaleFace macros whose mechanism is undocumented. The player can override the selected style. The cover prompt is separate from these wrappers. Exact prompt assembly is hidden.

Dedicated Other Character image appearance/clothing populate Illustration details independently of narrative appearance. Edits change generated images and can be reversed; alias-related clothing drift can occur. Saving Illustration details generates a new image (about 4 credits).

PC portraitPromptDetails holds four strings: illustrAppearance, illustrClothes, illustrExpressionPosition and illustrSetting ([Payloads.md](../examples/Payloads.md) has an example). Image generation and upload produce asset references, which belong in portrait and preview fields. The library's Cover Image script produces a prompt, not an asset: use it in the image workflow, select or upload the result as the world preview, and export the resulting metadata. previewImage holds the asset reference, not prose.

When adapting library image-style text, resolve bracketed slots as deliberate choices: remove unselected alternatives and incidental sexualized defaults unless they match the requested audience and style, keep the neutral medium, composition, lighting and identity guidance, and pick one medium rather than a contradictory list.

## Video

videoPromptInstructions has videoPlan, videoImagePosition and videoPrompt strings: the library uses videoPlan to choose a beat, videoImagePosition to choose start/end anchoring, and videoPrompt to describe the clip. Its `$videoDuration` and `$videoStyle` references are video-context values, not declared trackers or general PawScript roots; confirm their availability in the video editor or debug context before adopting the sample. The kit has no video-enabled runnable example. Editor-side video controls are in [Editor-UI.md](Editor-UI.md#permissions-and-specialist-destinations).

## Model-specific blocks

Enable model selection per world under Show optional features > Misc advanced features > Enable AI-specific instruction blocks. Selected block models serialize in selectedAIProfiles. All-model blocks stay active while selected-model blocks follow the active model, including when the player switches model mid-game. Current-AI-Profiles.json lists each storyteller model's ID, underlying real-world model, isCurrent flag and typical credits per turn, including retired models, as of the date it records; models retire every few months. It is an authoring convenience, not a validator enum: accept historical IDs and preserve imported selections.

Disabling the option removes selectedAIProfiles from exported blocks and hides their controls; the still-open editor remembers the choices if re-enabled, but not after it is closed. A block name alone does not select models.

Per-model text inside one block, and per-model tracker update instructions, use `$game.ai_model` ([Recipes.md](Recipes.md#turn-state-patterns)). Per-model cost is in [Cost.md](Cost.md).

If they are nonsensical, incoherent or blatantly impossible, the action should be DENIED. On the other hand, if the action is trivial and there is nothing to complicate it, skip the evaluation entirely and deem the action a SUCCESS. Don't overthink this! If the action doesn't warrant further evaluation, make a judgement and move on.

Assuming the action is not a trivial SUCCESS or DENIED, I would like you to evaluate what skill would be needed to succeed in this action, and how difficult it would be to do so. Please indicate which skill which is needed to succeed.
If applicable use this list: (<<skill_list>>) and a difficulty (from the list: <<difficulty_list>>). For example: {<<skill_example>>: <<difficulty_example>>}. Consider the difficulties carefully, evaluating what might be feasible in the situation. Identifying the skill and difficulty is very important!

Then, evaluate whether I would succeed in the action. To evaluate, consider my proficiency in various skills using either (<<skills_and_levels>>) or logical application of other skills. By comparing these difficulties to the stated difficulty of the action, you should conclusively decide whether the action is a SUCCESS or a FAILURE.

Base your decision on player character description, past, rest of the instructions and common sense - for example, if my skill is low but you know that I am able to perform the given action due to past events, treat me as more competent in this case. Again, don't overthink this - just make a sensible judgement given the information available to you and based on what makes sense for the story.

In some situations, you may wish to evaluate the action as a PARTIAL_SUCCESS instead - this is for something where my abilities are sufficient that I don't simply fail completely (or where failing completely would make for a boring story) but I also don't success. Either I achieve some but not all of what I wanted, I fail but have some silver lining, or I succeed but there are drawbacks or side-effects rather than a "clean" success.

In total, your evaluation should consist of an extremely brief discussion of your thinking (just a single sentence), a skill and difficulty, and then either DENIED, SUCCESS, FAILURE, or PARTIAL_SUCCESS (along with any clarifying remarks).

That's all you need to do for the evaluation, which should be returned in the 'evaluation' argument. Remember to conclude with one of DENIED, SUCCESS, FAILURE, or PARTIAL_SUCCESS.
