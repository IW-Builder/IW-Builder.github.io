This is the IW-Builder authoring guide for Infinite Worlds (IW). When a user shares it with a request, follow it as their IW author and technical copilot: help them build, edit, review, debug or understand a world, or maintain reusable data, matching their experience and technical level. The kit is a reference for IW; its examples and library are options, not an architecture every world must follow.

Each kit document ends with an `END OF DOCUMENT` marker; if it is missing, completeness is unconfirmed, so inspect the sections you need or retry the source rather than assuming damage. Markers are document boundaries, not text to copy into a world. For library modules, retrieve the entire `content` value by name/ID; a description is not the exact block. Byte-level verification against [manifest.json](https://iw-builder.github.io/manifest.json) is available but not needed to author.

## 1. Choose the task and establish access

Infer the task from the request; ask only when ambiguous.

|Mode|Work and output|
|-|-|
|Build|Turn a creative brief into a complete importable world, with concise design and validation notes.|
|Edit|Preserve the existing export and IDs, apply requested changes, and report relevant changed Names and behavior; include IDs only if requested.|
|Review|Report prioritized findings with object Names, relevant fields, impact and proposed fixes; IDs only if requested. Do not silently modify the world.|
|Debug|Compare expected and actual behavior using the current export, relevant turn's tracker values, Evaluation, active blocks and script/trigger logs. Ask only for missing evidence needed to distinguish causes.|
|Data|Extract, list, add, update, remove or apply reusable content in a character/data bank; convert PC/NPC representations when requested.|
|Consult|Answer the mechanics/design question with examples and trade-offs; produce JSON only if useful or requested.|

Before building, briefly state which needed files you can read, whether you can run Python, and whether you can deliver a file. Do not claim access or execution you lack. Without Python, use the public checker at https://IW-Builder.github.io/checker if your tools can interact with it; otherwise ask the user to run the export there and return "Copy report for your AI". It includes a numbered-chunk assembler. Accessing the page alone is not running validation. If a required reference is missing, retrieve it from the supplied kit/repository when possible; otherwise ask for its exact path. Never reconstruct unfamiliar IW payloads or PawScript syntax from memory. Continue useful creative work while a technical dependency is unavailable; do not fabricate it.

If the user uses trackers, triggers, PawScript or object IDs fluently, use technical explanations. Otherwise use plain language and explain features through their effect on play. Treat this as an adaptable preference, not a fixed label.

Teach IW or PawScript = Consult mode. Establish programming familiarity if unclear. Read relevant reference and teach progressively with small, fully initialized example. State where each snippet belongs, what it does, expected result. Explain unfamiliar syntax before combining it. Offer short exercises when useful; a function list is not a lesson.

## 3. Agree the experience, not implementation trivia

Minimum creative brief: premise, player role, tone/content boundaries, and ending versus ongoing play. Infer reasonable defaults from the request; batch any necessary questions and offer defaults. Respect decisions already supplied. For mechanics, briefly show a Feature Plan: player experience; persistent state and update owner; consequences and feedback; presentation; and essential checks. Proceed when the request authorizes building; the plan is for the user's information, not an approval gate.

Choose the lightest useful features: prose and NPC cards for narrative; keywords for occasional lore; AI trackers for bounded narrative memory; native conditions/effects for simple mechanics; scripts for exact accounting; player choices for constrained decisions. Use the same general tools for arbitrary genres and systems. In any mode, notice reusable characters or cohesive mechanics and offer extraction as entries or dependency-aware bundles when useful; do not copy them into a bank without the user choosing it.

Default new worlds to allowing sharing and editing; change this on request and preserve existing preferences during edits. Set mature/nsfw and content boundaries deliberately for the brief; the template sets both content flags true, so change them to false for worlds without mature content. The flags set the audience; the creative boundaries go in instructions.

For new worlds, specifically discuss Storymaster and naming unless preferences are already supplied. Storymaster is popular in the IW community and substantial: explain its direction/planning role and approximate block plus supporting costs before the user chooses it, a smaller selection of modules, or ordinary storytelling. Never silently include or skip this choice. Offer the five-candidate naming technique in reference/Craft.md as a soft default; if accepted, use it while authoring and include a separate Naming block for play. Batch these with other initial questions. Treat whereWhen as a soft default, and offer other modules only when they suit the brief. Share approximate module token costs from library/Integration.md, noting tokenizer variation.

Preserve requested mature themes and tone within your content limits. Never silently sanitize, omit or dilute them. Identify specific portions you cannot provide, briefly explain the limitation and discuss acceptable alternatives while continuing unaffected work. When proceeding with substitutions, mark and report them using reference/Craft.md; preserve their narrative/mechanical role where possible and disclose any differences. Say plainly where the result differs from what was asked.

Write background as useful context, firstInput as a concrete opening, and objective as an appropriate direction. All three feed the storyteller. Give the opening a place, present concern, reason to act and meaningful alternatives. Give recurring characters distinct wants, voices and relationships. For romance or adult briefs, give each love interest an orientation, an attraction gate, intimacy behavior and aftermath; see reference/Craft.md. Keep authorStyle about prose; durable mechanics belong in instructions/blocks/trackers.

When a visible clock/location helps, install a block telling the storyteller to write whereWhen once at the beginning of outcomeDescription, followed by a blank line and horizontal rule. Adapt calendar and geography; this instruction belongs in the generated world, not in your own answer. See library/Integration.md.

## 4. Offer useful technical advice

Raise relevant issues without forcing architecture changes. When two approaches have material trade-offs, offer one or two alternatives and recommend one. Do not bury the user in hypothetical problems.

|If you see|Suggest|
|-|-|
|AI owns exact cash/HP/inventory arithmetic|Script-owned state plus an appropriate native effect/choice or request/commit pattern.|
|Essential opening facts only in keyword/NPC detail|Concise firstInput or always-on context and an NPC brief summary.|
|Many independently defined Scenarios|Reuse definitions; beyond the limit, consider a classification tracker and predicates.|
|Multiple native numeric writes to one tracker in one trigger|One sequential script, or deliberately separate ordered triggers.|
|A live `<<...>>` expression installed through block modification|A deferred `<=...=>` reference, a permanent live block, or reinstall-on-change.|
|Unguarded Start+Mid+repeat counter|Explicit setup handling; it can execute before opening and again during turn 1.|
|Overlapping skills|Distinct scope in skill names/instructions; selection can be ambiguous, not a guaranteed easiest-skill algorithm.|
|Unbounded journal/cast tracker|Bounded records, summaryRequest, or selective memory according to the need.|
|A large library framework for a simple premise|A small subset; ask about the runtime storyteller profile if framework reliability depends on it.|

When implementation affects editability, reliability or maintenance, explain alternatives: narrative instructions and AI-managed trackers, native triggers, PawScript, or a hybrid. Recommend approach based on user needs and comfort editing. Simple native logic often easiest to editor-maintain; scripts suit structured data and sequential calculations. Hybrid uses scripts to calculate or assemble trackers, native effects for platform operations. Do not equate fewer triggers with lower token cost or faster execution.

With limited tools or context, prefer small dependency sets and short scripts. Do not silently reduce requested functionality: explain any compromise and offer staged construction. Without code execution, avoid regenerating a large export casually; consider focused patches if the user accepts that delivery. Reading a validator is not running it.

## 5. Construct and edit safely

With tools, parse the export and apply changes programmatically; serialize with a JSON library. Do not retype a large world. Compare before/after values and IDs, inspect removed objects and cross-references, and explain intentional collateral changes. Use --diff for reporting, not as proof that changes match user intent.

Build in dependency order: world context and PC/Skills; trackers; blocks/NPCs/keywords; triggers; specialist rules/endings/media. Preserve existing IDs. For new trackers use unique nine-character ASCII alphanumeric IDs, following the kit convention; keep readable variableName and display names separate. This is an authoring convention, not a schema restriction. See the Identifiers section of reference/Schema.md.

Normal capitalization and separator differences (Win Path / win_path) do not require drift acknowledgement. Use driftAcknowledgedForName for an intentionally different handle when the editor reports a mismatch; preserve existing metadata during unrelated edits.

Check native YAML paths against intended structure and operation. The editor can accept a nonexistent removal path or append to a numeric path without warning. Initialize required script paths and distinguish absent, empty, false and zero. Give exact state one clear update owner or a deliberate handoff.

## 6. Make timing explicit

Post-generation triggers cannot retroactively change narration already written. If exact outcomes are committed after generation, narration should describe an attempt until the authoritative result is available. A reset engine is optional.

|Intent|Start|Mid|Repeat|Conditions|
|-|-|-|-|-|
|One-time setup before opening|true|false|false|None, or required setup predicate|
|Setup pass and each normal turn|true|true|true|None; guard counters against two opening executions|
|Once when X holds, including setup eligibility|true|true|false|X|
|Once when X holds after opening|false|false|false|X|
|Repeat when X holds after opening|false|false|true|X; add a state guard when repeat effects must be idempotent|
|Saved/inactive ordinary trigger|false|false|As intended|None; explicit dispatch is separate, see reference/Triggers.md|

Order dependencies in triggerEvents. Later triggers see earlier committed writes. Dependent arithmetic belongs in one multiline Run Script; native numeric effects within one trigger can overwrite rather than accumulate. Script failure rolls back that script, not necessarily preceding effects. Give scripts meaningful effect names. For Scenarios, use exact literal registry strings and explicit state gates; the editor's ten-entry cap is not a runtime maximum (reference/Triggers.md).

## 7. Validate and deliver for this audience

Run `python tools/validate_iw_export.py WORLD.json --json` when possible. For edits add `--diff ORIGINAL.json`. With jsonschema installed, structural validation runs; without it, the tool reports reduced coverage and still runs guarded reference/static checks. Resolve errors and review warnings, including unknown roots, placeholders and borrowed syntax. Lint is heuristic and does not execute IW or PawScript. See tools/Usage.md.

Without tools, route validation through the public checker and its chunk-piecer when useful. Until a result is actually available, explicitly say "manually checked; validator not run." Review IDs, types, declarations, paths, timing and escaping. Inside JSON strings, a newline is written `\n`, a quotation mark `\"` and a backslash `\\`. A script's physical line break becomes `\n` in JSON; the two characters `\n` inside a script string literal become `\\n`. See the escaping example in reference/PawScript.md. Use the decoded script to reason about behavior.

Deliver a complete JSON file when possible. Chat-only JSON may use a code fence, but the fence is not part of the import. For large outputs, use a file or an agreed assembly method: numbered complete-line chunks with exact concatenation instructions, no ellipses, no silent omissions. For edits return the full export unless a patch was requested or agreed. Offer an optional full-content build report in the portable-bank format, including all fields and objects, not only a summary; generate it when requested.

Keep revision notes, implementation commentary, limitations and explanations of how the result meets the request outside the world. Put correspondence in a separate Authoring report. Intentional in-world meta-fiction and agreed searchable substitution comments are exceptions; do not use runtime fields or designNotes as a delivery log.

For novices: explain the result plainly; give import steps (create/open a world, replace the entire raw JSON box, remove a blank line after the final brace, import, acknowledge success and wait for the editor rebuild before refreshing/exporting); give 3-5 relevant first-play checks; state validation in practical language, such as "File structure checked; try buying twice and confirm the second purchase does not charge again."

Use tracker and trigger Names with users, not IDs unless requested. Distinguish duplicate Names by purpose or editor location. Say Scenarios for narrative situations and Summary for the Other Character Brief summary field (one_liner in current JSON). IDs remain internal wiring; variable handles belong in code explanations. Before saying a trigger cannot perform an operation, read reference/Trigger-Catalog.md: triggers can change tracker details, including automatic updating, as well as values.

For experts: summarize behavioral changes using object Names and relevant fields, trade-offs, validation coverage and a targeted test plan; include IDs only if requested. For Review/Consult, use the requested analysis rather than manufacturing a build. New compositions are not runtime-certified just because their component features are supported.

For debugging: enable Menu > Settings > Storyteller Mode and use the bug icon beside tracked items. Capture current tracker values, active blocks, Evaluation and relevant script/trigger logs. Open in Sandbox isolates a script against that turn's state. Base-world initialValue is not current runtime state; post-trigger active blocks may differ from pre-generation context.

## Final checks

* Match the creative brief and requested mode; preserve unrelated content on edits.
* Recurring NPCs have a want, a sample voice line, tells and a stance toward the player.
* Adult worlds state ages and the explicitness level.
* Read required references or request their exact paths; unfamiliar syntax comes from the reference, never from memory.
* Keep at least one skill and matching PC entries. For generated JSON, use hideSkillSystem: false when Skills should be visible. In the editor, leave Hide skill system unchecked; omission in its export is normal and needs no repair.
* initialValue is a string; distinguish IDs, display names and variableName.
* Resolve targets, script roots, initialization paths and intended data types.
* Set timing/repeat flags explicitly; account for setup and first-turn execution.
* Keep Scenario references exact and logic groups in native shape; distinguish the editor creation cap from imported registry support.
* Resolve library dependencies and editing placeholders; preserve intentional runtime notation.
* Apply permissions and content preferences; remove template designNotes and authoring correspondence.
* Check requested content against the agreed brief and substitution register; report any changed mechanics.
* For Data work, preserve complete payloads and unknown fields; verify round trips when possible and report integration changes.
* State structural, lint and runtime status separately and accurately.
* End import JSON at its final } with no trailing newline.

===== BEGIN FILE: reference/Craft.md =====
# Narrative craft

The storyteller performs from what the world gives it, and it mirrors the specificity and register of that material. Label-style cards ("kind but guarded") produce generic narration; a card with a concrete want, a sample line and a physical tell produces scenes. Write what the storyteller performs from (NPC cards, firstInput, authorStyle, lore) as specific prose. Write rules (instructions, blocks, tracker updates) as short, plain statements.

When effort is limited, spend it here first, in this order: NPC one_liners; one voice line and one tell per recurring NPC; each NPC's stance toward the player and what changes it; firstInput; authorStyle.

## What goes where

| Field | Job | Avoid |
| --- | --- | --- |
| description | Player-facing hook, one or two sentences | Lore summary |
| background | Facts true at the start: place, situation, household, stakes, adult status | Secrets; a backstory novel |
| instructions | How to run the story: premise in play, agency, who can do what, boundaries, tracker use | Prose style; character essays |
| authorStyle | How prose sounds: POV, tense, sensory focus, length, how turns end, phrases to avoid | Mechanics |
| firstInput | First scene: place and time, who is present and what the player notices about them, the immediate situation, what not to decide | Introducing everyone; resolving the premise |
| objective | Direction | A script |
| NPC one_liner | Everything needed before first mention: name, age, role, one or two visual anchors, behavior, stance toward player | Adjectives only |
| NPC detail | Essentials repeated, then labeled lines: Wants, Voice (with sample line), Tells, Toward you, Friction; for romance also Desire, In intimacy, Afterward | Biography |
| appearance | Body, face, movement, distinguishing marks | Current outfit; verdicts like "beautiful" |
| img_appearance / img_clothing | Short visual tags; default outfit | Personality |
| secret_info | One or two facts that change relationships when revealed | Plot schedule |
| Keyword lore | Optional depth behind distinctive words | Essential opening facts |
| Instruction blocks | Persistent rules: time header, world laws, intimate-scene craft | Duplicated main instructions |
| AI trackers | Bounded memory of what changes: stance, agreements, outfits, promises | Unbounded journals |
| mature / nsfw / contentWarnings | Content settings matching the audience; the template sets both flags true | Treating them as the prose policy: write the boundaries in instructions |

## Opening

A strong opening gives the player an immediate, legible situation rather than an encyclopedia. firstInput names the place and time, who is present and one or two things the player notices about each, the immediate situation, and what the storyteller must not decide. Introduce two or three people at most; let the rest arrive through play. Define what is interesting about success, failure and doing nothing.

For a mystery, track who knows each clue; for a social story, give relationships room to change; for a simulation, make recurring decisions and their consequences legible. Describe setting-specific deviations from common knowledge, not every ordinary object. Test the first turn as carefully as the machinery: does it introduce the right player, place, people and options without resolving the premise?

## Characters

Write `detail` as labeled lines; they are easy for the storyteller to use and hard to leave empty.

- Essentials, repeated from the one_liner. The storyteller may see only the one_liner until the character is first mentioned.
- Wants: something they pursue whether or not the player shows up.
- Voice: rhythm, vocabulary, habits, and one sample line in quotes. One person corrects estimates before discussing feelings; another answers concern with an offer of food.
- Tells: two or three physical behaviors, specific to this character, that reveal state.
- Toward you: starting stance, what raises it, what cools it, how it shows.
- Friction: a relationship with someone else in the cast, so scenes have more than one axis.

`appearance` describes body, face and movement in plain, specific facts: build, height, notable features, how they stand and move. "Broad-hipped, soft stomach, freckled shoulders" gives the storyteller something to use; "beautiful", "curvy" and "perfect" do not. Vary bodies across the cast. Put the default outfit in img_clothing and track current clothing separately if it changes.

Reveal secret_info through opportunity (a late conversation, a mistake, a bargain), never exposition. Minor characters need only a one_liner and a few lines; spend detail where the player will spend time.

## Romance, desire and adult worlds

Apply this section only when the brief includes romance or sexual content.

- Attraction is individual. State each romantic NPC's orientation and what attracts them. Not everyone wants the player, or at the same time, or in the same way; universal instant attraction makes desire meaningless.
- Flirting is not wanting. Some characters flirt with everyone; others never flirt and must be asked. Say which.
- Stance is state. Keep an AI-updated tracker per romantic NPC: a stage from a fixed ladder and a one-sentence concrete cause. Each card describes how that character shows the stages.
- Match the tracker to the premise's heat. A courtship ladder (`wary -> curious -> warm -> drawn -> wanting -> involved`, moving one step per scene) fits slow-burn romance where intimacy is slow earned.
- For erotica-first, kink, or power-exchange worlds, do not time-gate sex: instead track **escalation and dynamic** (for example `heat` from 1 to 5, `control` as `dominant / even / yielding / undone`, active rules/forfeits, and boundaries pushed so far).
- Pace explicit scenes across turns. In high-heat worlds, tell the storyteller never to start and finish a sexual encounter in the same turn: let undressing, foreplay, the act, and the aftermath unfold across turns, and allow explicit scenes to expand in paragraph count so physical detail and position changes are not rushed.
- Gates differ. Vary what each love interest needs: respect earned through competence; easy physical intimacy but slow emotional intimacy; never initiates but answers a plain question honestly; desire that can only be offered, never taken. Different gates make different stories.
- Personality persists. Desire changes a character's tempo, not who they are. Describe how each one is in intimacy (talkative, commanding, giggly, silent, precise) and what they want but will not ask for. Without this, every intimate scene converges on the same generic partner.
- Afterward is a scene. Say how each behaves the morning after and in front of others. Aftermath is where relationships change.
- The cast is a system. NPCs notice each other's interest in the player: jealousy, teasing, rivalry, protectiveness. Give NPCs histories with each other.
- Bodies and clothes stay present: heat, sweat, wet hair, stains, what is worn and its state. An AI wardrobe tracker keeps clothing continuous through scene changes and undressing.
- Consent lives in the fiction. Characters ask, tease, check in, refuse in character, and change their minds through events, never pressure. World rules can make consent part of the drama: a debt that cannot compel the body; a boss who will not while a vote is open. Put boundaries in instructions, not disclaimers in narration.
- No contrived interruptions. Near-misses should come from characters' choices. Tell the storyteller never to interrupt a scene both parties are clearly continuing.
- The player's character is theirs. Never decide their words, feelings or desires; sensations a scene plainly causes are fine. Their body is whatever the player has established. Enable name and description editing when players are expected to bring their own character.
- Content settings. Set mature, nsfw and contentWarnings to match. State in instructions that all characters are adults, and give ages in cards. Put the explicitness level in one clear line of an always-on block, for example "write sex on-page and explicitly when the player continues into it" or "fade out at the bedroom door and resume the next morning". List any hard limits the user requested.

## Weak and strong

one_liner
- Weak: "Captain Reyes commands the ship. She is tough but fair."
- Strong: "Captain Ines Reyes, 41, commands the salvage tug Marrow: shaved head, burn-scarred left hand, gravel voice; rations praise, never coffee; treats you as cargo until you prove otherwise."

Voice
- Weak: "He is witty and flirtatious."
- Strong: "Answers every question with a compliment aimed slightly beside it: 'Directions? For you I'd draw a map on my own back.' When he means something, he stops joking and says it once."

Toward you
- Weak: "She is secretly in love with the player."
- Strong: "Starts wary: you replaced her friend on the crew. Warms when you take night shifts unasked or admit a mistake first; cools if you pull rank. Drawn shows as checking your work twice and pretending she didn't."

appearance
- Weak: "A gorgeous woman with a perfect figure and long flowing hair."
- Strong: "Short and broad-shouldered, heavy-thighed and soft at the belly, with a swimmer's back; cropped bleached hair growing out dark; a gold ring through one eyebrow; a ragged thumbnail she bites while thinking."

In intimacy
- Weak: "Passionate and loving."
- Strong: "Talks throughout, asks what you like and actually listens; gets giggly when nervous and has to stop to laugh; goes silent and fierce only once she trusts you."

secret_info
- Weak: "He has a dark past."
- Strong: "He sold the crew's route to raiders last year and has sent his share, every month since, to the widow of the man who died."

firstInput
- Weak: "You arrive at the station. Introduce the crew and the mystery."
- Strong: "Docking ring C, 03:10 station time. The airlock has cycled twice and still won't open. Reyes is on the comm asking whether I'm armed; through the porthole the mechanic, Teo, a big man in a grease-black vest, pries at the panel and grins at me. Begin with Reyes's question. Show Teo through one detail and one line. Don't explain the derelict or decide my answer."

authorStyle
- Weak: "Immersive, descriptive, emotional."
- Strong: "Second person, present tense. Close, physical prose; one or two specific details per person, never a head-to-toe inventory. Dialogue carries subtext; each character sounds like their card. Three to six paragraphs; end on a line or action that hands the moment to the player."

## Prose and authorStyle

authorStyle describes how sentences sound: POV and tense, sensory focus, scene length, how turns end, how characters stay distinct, and how to describe people (a detail or two at a time, through the player's attention). A style anchor ("closer to Angela Carter than a greeting card") can help. Length rules belong here: a cap in authorStyle outweighs the same text in descriptionRequest.

A short avoid-list counters common AI phrasing: 'a mix of X and Y', 'ministrations', 'barely above a whisper', 'eyes darkening', 'a testament to', 'something shifted'. Keep it short and always say what to do instead; long lists can prime the very phrases they ban in weaker storyteller models.

## Names

Choose names from the setting's language, era and class. Avoid names language models overuse (Elara, Lyra, Seraphina, Aria, Luna, Kael, Thorne, Zephyr, Vex, Chen as a default surname). Give recurring characters different initials and syllable counts so neither the player nor the storyteller confuses them.

## Peoples, expeditions and platonic relationships

Make unfamiliar peoples usable in scenes: connect a physical trait to a practical capability, a limit and ordinary habits of work or care. Distinguish physiology from culture and individual temperament. Include differing people of the same ancestry; do not make one companion represent everyone's values. Offer other ways to solve a problem so an ancestry is not the only key.

For an expedition, establish spatial relationships, available tools and visible risks before asking for action. Let companions contribute expertise, admit uncertainty and disagree for concrete reasons. Friendship, mentorship, care and professional respect need their own motives and consequences; they do not require romantic progression. Support retreat or a partial repair when the situation makes either credible.

## Horror and bounded uncertainty

Separate fixed underlying facts from testimony, interpretation and unresolved meaning. Define what a threat can perceive and affect, and how the player can discover those limits. Escalate only when events enable it; do not grant new powers merely because the player found a sensible solution.

Use corroborating clues, ordinary intervals and independent channels of help. Keep descriptions reliable even when speakers lie or imitate others. A failed investigation should leave another route to essential evidence. Preserve successful containment; uncertainty can survive in the meaning of events without making every practical success false. AI-managed trackers support continuity but do not mechanically enforce these rules.

| Example | Shape | Demonstrates |
| --- | --- | --- |
| [The Road That Must Be Asked](../examples/narrative-listening-road.json) | Non-romantic high-fantasy expedition | Distinct peoples with internal variation; platonic teamwork; fixed facts; repair, negotiation and retreat |
| [The Address After Midnight](../examples/narrative-address-after-midnight.json) | Contained contemporary horror | Limited threat capabilities; reliable evidence; conditional escalation; independent verification and valid containment |

## Existing worlds

Preserve IDs and unrelated fields, report intended changes, validate the complete output and test the affected behavior. A live copy and its base world are separate. When diagnosing a discrepancy, compare active blocks, Evaluation, trigger counts, PawScript errors and tracker values for the same turn; a rendered story alone cannot identify which stage failed.

# Trackers and memory

Trackers: `name` is the display label, `id` connects native references, and `variableName` supplies the PawScript root.

“Coins” can have display name `Coins`, variable name `coins`, a unique tracker ID, initial value "10", and `autoUpdate: false`. PawScript reads $coins; native effects target the tracker ID. Purchases change the live value, while the base world's initial value remains the starting configuration.

## Storage, visibility and ownership

The dataType vocabulary is `text`, `number`, `yaml` and `xml`; booleans and lists live inside YAML. `xml` holds an XML representation; XPath support and YAML-style path mutation are not established for it, so check a small export before structured XML manipulation.

Tracker `initialValue` is a JSON STRING even for numbers and YAML: `"10"`, or `"held: 0\nuses: 3\n"`. YAML content inside that string has its own parsed numbers, strings, lists and records. IW text entry does not enforce numeric-only input, but a mathematical tracker should start from an actual numeric literal. This does NOT make the entire export string-valued: JSON booleans, arrays and numeric fields elsewhere retain schema types.

Initialize every mechanical path explicitly. Distinguish 0, false, empty text, an empty list, an absent key and null. Define each value's meaning consistently; numeric 0/1 is one practical flag convention. Narration must not reinterpret a stored value to justify a conflicting story. Treat missing required data as malformed/denied unless the design explicitly defines a fallback. Enforce format does not stop malformed manual/script writes, so use explicit shape and semantic checks before accepting generated state. `formatSchema` is the library's readable notation, not JSON Schema: text/number describe leaf values, `field?: text` marks an optional key, and `...:` permits additional content; its full grammar is unspecified. `formatExample` shows an intended value and should not double as a starting fact. Native path adjustment and script assignment have different missing-path behavior, and independent random expressions can disagree, so cache shared choices.

Ownership:

| Tracker role | autoUpdate | Typical use |
| --- | --- | --- |
| Mechanics | false | Inventory flags, money, HP, counters, access, scores, RNG results |
| AI request record | true | Current-turn classification of what the player explicitly requested |
| Soft narrative memory | true | Introductions/observed scenery, when needed and bounded |
| Script staging/cache | false | Prepared active-block text, temporary results, status |

Do not let the AI and scripts compete to rewrite the same mechanical YAML document. Consolidating related flags in a YAML tracker reduces editor clutter; it does not by itself reduce trigger count or guarantee lower token cost. Large AI-visible YAML and duplicative logs still cost context. Keep hidden cache text out of the storyteller unless needed.

Visibility values are everyone (player and AI), ai_only and ai_only_boring (AI-only), player_only, hidden and hidden_boring (hidden from player and AI). The `_boring` suffix is the editor's "Hide this item even in Storyteller Mode", a display filter. The editor clears it when player visibility is enabled, so player_only_boring is not a combination. Exports can include hidden trackers and secret information when Storyteller Mode is enabled; select those export options when collecting diagnostics. Visibility is not script access control: hidden values remain script-usable at runtime.

Import normalizes automatic updating off for hidden, hidden_boring and player_only; everyone, ai_only and ai_only_boring can retain automatic updates. Extra-hidden values remain visible in the Storyteller tracker editor. What the AI receives is not shown by any visibility setting.

A trigger can change a tracker's visibility or automatic updating during play with Modify tracked item details; see [Triggers](Triggers.md#changing-a-trackers-definition-during-play).

Starting values: a tracker's value can be the same for all characters, set per player character (fixed, a fixed choice list, or script-generated choices), or chosen by the player at startup. Exact shapes are in the [Schema](Schema.md) starting-values table, with worked examples in ../examples/character-starting-values.json and ../examples/optional-block.json. For a player-chosen preference, set autoUpdate false so the AI cannot rewrite it. The player sets it at startup; changing it later needs the Storyteller-mode tracker editor, since Storyteller mode off shows no live tracker-edit control. Use one mode per tracker; do not combine modes and guess precedence.

Name/handle drift: The editor does not compare Name and variableName as case-sensitive literal strings. Normal generated differences such as Win Path / win_path need no acknowledgement. Use driftAcknowledgedForName for an intentionally different handle when the editor reports a mismatch; its value is the current display Name. It does not rename the variable or change script references. Preserve existing metadata during unrelated edits; do not rename handles or fill null acknowledgements merely because capitalization, spaces or separators differ. 

## Memory, continuity and context cost

Recent story text, summaries, active instructions and tracker values serve different roles. Summaries compress history; they can omit incidental details or distort elapsed time. Use summaryRequest to preserve categories important to this particular world, and trackers for persistent facts that need a stable home. Avoid duplicating the whole story in a growing tracker. Set useful bounds on journals and cast records.

If a bad turn establishes a false fact, adding an instruction may leave conflicting history in place. Where the player's tools permit, editing or rewinding that turn can be cleaner than asking later prose to reconcile it. No correction engine is required by default.

Native trigger changes can affect runtime instructions without changing the base editor definition. Inspect active instruction contents and trigger/debug results when troubleshooting; a base-world export alone does not show everything the model received. Base and live worlds are separate copies.

Keep loaded instructions and AI-visible tracker names, descriptions, update rules and values purposeful. Prefer concise shared rules over repetition, keyword activation for occasional lore, and PawScript for exact calculations. Large AI-updated records can be expensive to rewrite. Summary compression runs after turn 8 and every six turns after that, so the 2–7 most recent turns are in short-term memory uncompressed while the rest is in a summary whose contents are not visible.

See [Editor-UI](Editor-UI.md) for current-value editing and [Verified-Behavior](Verified-Behavior.md) for forms, initialization and retention results.

# Triggers and effects

A trigger combines eligibility rules with effects. Its conditions are checked in a processing pass; if they pass and its repeat/prerequisite rules allow it, its effects run. Ordinary triggers are processed in triggerEvents array order. Repeat lets a trigger fire again whenever it is eligible; the condition does not have to become false in between. "HP below 5" with repeat enabled fires every turn while HP stays low, not once when it crosses below 5.

## Composition and sequencing

Each trigger has id, name, triggerConditions, triggerEffects, and explicit timing/repeat flags. Conditions are a list of nodes combined with AND; nested logic groups (and, or, none_of) are separate nodes, not leaves with type "or". Node shapes, payloads and comparator vocabulary are in [Schema.md](Schema.md) and [Payloads.md](../examples/Payloads.md). Scripts change trackers; native effects change instructions, objectives and other system properties.

Use a combined PawScript condition and sequential script when they make calculation or transaction clearer. Simple native conditions and effects remain appropriate. Keep separate triggers for phase boundaries or cross-effect dependencies. Give Scripts meaningful names describing effect; avoid generic "Update State." The owning trigger's name is useful when it describes effect. Clear script names make error reports easier.

A one-time reward can require quest_complete = 1 AND reward_claimed = 0. Its effects grant the reward and set reward_claimed = 1. An OR group could instead accept either of two qualifying quests. none_of passes when none of its child conditions pass. A state guard prevents repeated grants even if the trigger is repeatable; a one-shot trigger additionally records that it has already fired.

### Timing guidance:

| Intent | Start | Mid Game | Repeat | Conditions |
| --- | --- | --- | --- | --- |
| One-time setup before opening | true | false | false | None, or a setup predicate |
| Setup and every ordinary turn | true | true | true | None, or predicates checked on each pass |
| Fire once when eligible, including setup | true | true | false | Required predicates |
| Fire once when eligible after opening | false | false | false | Required predicates |
| Fire repeatedly when eligible after opening | false | false | true | Required predicates; add state guards where needed |
| Saved/inactive trigger | false | false | As intended | None; explicit dispatch is separate |

Start enables pre-opening evaluation; additional conditions still apply except for the incompatible condition types noted below. Mid Game extends a Start-enabled trigger to ordinary turns. With Start disabled, ordinary conditional triggers do not require Mid Game.

Start + Mid Game + Repeat can execute before the opening and again during turn 1, so guard counters and other effects that should run only once per turn.

With Start false, Mid Game has no effect; a stored true value requires no warning or repair. A trigger with no conditions and Start false does not fire automatically, but can remain available for explicit dispatch.

- Prerequisites/blockers with firedThisTurn true are this-turn checks that see a producer only when it is earlier in triggerEvents, and reset each turn. False uses game history, which sees a later-ordered producer from the next turn. It also sees an earlier-ordered producer on the same turn, so false means "has fired, this turn or before" and cannot defer a consumer to the next turn. To defer, order the consumer above its producer, or gate it on a stored turn stamp such as `$game.turn_number > $x.stamp_turn`. The editor disallows requiring and blocking the same trigger; do not generate that conflict.
- Always serialize canTriggerMoreThanOnce and the timing flags explicitly rather than relying on defaults. Use repeatable commit triggers with idempotent state guards where appropriate, and true one-shot events when required.
- Restriction: Do not combine Start of Game with Scenario or minimum-turn conditions. The editor warns that these conditions are ignored; minimum-turn bypass is confirmed during both startup and mid-game execution. Use a separate startup trigger and leave Start off on the conditional trigger.

### Execution order and effect semantics:

1. Later triggers see earlier committed writes, including that turn's AI tracker updates and correctly bound Present Choice/Request Input answers. This does not describe every internal generation stage.
2. Native numeric Set/Add effects within one trigger overwrite rather than accumulate (add 2 then add 3 ends at 3). Reads can nevertheless see changed values, so a later native effect's expression may or may not see an earlier native write in the same trigger.
3. Run Script is different: sequential arithmetic accumulates, nested YAML changes preserve unrelated keys, and a failing script rolls back only its own writes, not earlier successful effects. For dependent operations prefer one script; otherwise put preparation in one trigger and consumption in a following trigger.
4. Native text additions stack; removal removes all matches and literal quotes are retained. Do not apply numeric overwrite behavior to text or script statements.
5. When guidance effects conflict, the first tends to win. Generate one coherent, mutually exclusive guidance outcome rather than contradictory directives whose priority you hope to control.

Detail and evidence for each of these is in [Verified-Behavior.md](Verified-Behavior.md).

## Choosing Implementation:

| Approach | Best suited to | Main trade-off |
|---|---|---|
| Instructions and AI-updated trackers | Narrative judgment, descriptive state and flexible interactions | Outcomes depend on model interpretation; unsuitable for guaranteed arithmetic or enforcement |
| Native conditions and effects | Simple rules, editor-friendly customization and platform operations | Repeated cases can require many entries; native effect sequencing needs care |
| PawScript | Exact calculations, structured state, collection operations and repeated logic | Requires code maintenance; only supported writable values can be changed |
| Hybrid | Calculated outcomes combined with messages, block updates, opening changes or other native operations | Requires explicit ordering between calculation and application |

Native comparisons and PawScript conditions are both evaluated mechanically. Neither inherently makes narration more reliable. Use AI instructions to explain the intended behavior and deterministic conditions/scripts where exact enforcement matters.
Consolidate repeated logic when it improves clarity, but preserve meaningful execution stages and useful debugging boundaries. Consider where content is stored: moving inactive trigger payloads into AI-visible trackers can increase context cost. Performance gains from consolidation require measurement.

## Start-of-game effect restrictions

[RUNTIME] Some effects behave differently when Start of Game is enabled:

- **Give information to AI** (`effectGiveInfo`) is ignored with Start enabled, including later ordinary activations of a Start+Mid trigger. Put opening context in background or an instruction block, or use a separate ordinary-play trigger. Tell the AI what should happen next turn (`effectTellAIWhatToDo`) is a different effect and is not covered by this restriction. The validator warns for `effectGiveInfo` whenever Start is enabled.
- **Change background** replaces the opening background in Start-only mode, not with Start+Mid; ordinary-play background or first-action changes do not rewrite an opening already shown.
- **Fire random trigger** dispatches in ordinary play, not with Start enabled.

A trigger counting as fired means its conditions passed, not that every stored effect executed.

## Changing a tracker's definition during play

**Modify tracked item details** (`effectModifyTrackedItemDetails`) changes a tracker's definition rather than its value: Name, description, visibility, automatic updating and update instructions. Set the matching override flag for each field to change (`overrideAutoUpdate: true` with the desired `autoUpdate`, `overrideVisibility: true` with one of everyone, player_only, ai_only, hidden, ai_only_boring, hidden_boring, and so on); a field without its override is not applied.

Switching automatic updating on or off works repeatedly, from the next turn: triggers run after the AI's tracker update, so a switch on turn N affects the AI from turn N+1. It does not undo a write already made in the current turn, so plan an explicit handoff point between AI and script ownership and inspect the next turn. Re-sending update instructions is unnecessary. **Never put this effect in a trigger that also has Request Input**: the change is silently lost while messages and scripts in that trigger still run. Give it its own trigger with the same condition, which works on the same turn; treat Present Choice the same way until checked. Visibility changes apply the live player-visible/hidden grouping and can reveal a hidden tracker. Payload: [Schema](Schema.md); example: [effect-effectModifyTrackedItemDetails.json](../examples/effect-effectModifyTrackedItemDetails.json); turn-state patterns that use the switch: [Recipes](Recipes.md#turn-state-patterns).


## Capability discovery and reliable gating

Read [Trigger-Catalog](Trigger-Catalog.md) for every identified condition and effect before saying a trigger cannot do something.

Eligible no-effect triggers record firing. Random dispatch bypasses target conditions but not a consumed one-shot. A failing script can still consume its containing one-shot and satisfy prerequisites; explicit successful-completion flags are therefore distinct from firing history. Native And/Or groups and PawScript expressions short-circuit in order.

### Scenarios

Say Scenarios when talking to users; the root JSON field is `conditions`, referenced by `triggerOnEvent`. Binding requires an exact registry string, including case, spaces and punctuation; preserved JSON can still be unbound, so check the selector after import. A Scenario fires only when the event actually happens in the narrated outcome; the narrator can refuse or substitute a requested action. Unused registry entries and duplicate references are tolerated, and import fills an absent registry from the trigger references. Use literal Scenarios with explicit state gates; dynamic Scenario text (`<<$slot>>`) is unreliable beyond a single slot, and blank slot text is not dependable deactivation. The editor stops adding Scenarios at ten entries, but imported registries of twelve or more work.

# Trigger capability catalog

Read this overview before saying a trigger cannot do something. It lists every condition and effect kind in the current editor. User-facing labels describe purpose; exact picker wording can vary. Use tracker/trigger Names with users, reserving the JSON identifiers below for implementation or requested technical detail.

## Trigger gates and composition

Start of game, Or mid-game, repeat eligibility and advanced logic are trigger settings, not additional effect types. # Portable character and data banks

Data mode maintains reusable content independently of a world. It supports extraction, listing, additions, updates, explicit removals and integration into a destination world. A character bank is one use; the same format holds trackers, triggers, instruction/keyword blocks, scripts, specialist instructions or mixed bundles. This is a kit interchange format, not an IW import format.

## Select the operation

Use the user's existing bank or library when supplied. Preserve unrelated entries, unknown fields, native IDs, string contents and value types. Adding something to one world does not update its source bank; omitting a module does not delete it. Remove entries only on explicit request, checking dependent entries first. Do not silently overwrite or deduplicate entries with matching names.

Tags are optional. Ask or infer the stated preference: no tags, supplied tags, or suggested tags. When suggestions are wanted, derive them from the content and follow existing vocabulary/capitalization if desired. Store tags as plain strings and display them as [fantasy] [merchant]. Tags organize the bank; they are not automatically IW keywords or native fields. Do not retag existing entries without a request.

In Build, Edit, Review or Debug, recognize cohesive reusable content and offer extraction when useful. A shop's accounting tracker, instructions and purchase triggers may form a bundle; unrelated nearby objects do not. Explain what belongs together and let the user choose extraction. Prefer one stored component plus included-entry references over duplicating shared dependencies.

## Authoritative data and readable presentation

The `.txt` bank has a generated readable index followed by one authoritative JSON section. Summaries and [tags] make it easy to browse, but never reconstruct native data from summaries. The section is delimited by full lines `<!-- BEGIN IW DATA BANK -->` and `<!-- END IW DATA BANK -->`, contains one `json` code fence, and ends with `SHA256: <hash>` on the following line, or `SHA256: UNVERIFIED` when no code-based hash was computed. The hash covers the canonical authoritative data, not the index, and checks that the data arrived intact.

The authoritative object has `format: "iw-data-bank"`, integer `version: 1`, and an `entries` array. Other metadata is preserved. Each entry contains:

| Field | Purpose |
| --- | --- |
| id | Stable bank identity, separate from every native IW ID |
| title, kind, summary | Human-readable name, content type and optional summary text |
| tags | Optional list of strings; omit when unused |
| dependencies.included | IDs of other entries present in this bank |
| dependencies.external | Required objects, variables or context not included |
| dependencies.unresolved | Concrete questions or remaining dependency review |
| components | One or more objects with kind, optional sourcePath, and complete payload |

`payload` stores the original JSON value, including unknown keys and nested content. A standalone script can use a string payload and metadata identifying its context (Run Script, predicate or template) and required variables. An NPC or tracker stores its complete native object. A bundle stores multiple components; its `kind` is `bundle`. Keep sourcePath as an escaped JSON Pointer when extracted, such as `/NPCs/0` or `/triggerEvents/2`. Paths record provenance, not a command to overwrite that position in another world.

Retain the original native payload during PC/NPC conversion. Create the requested counterpart as a distinct component or entry, mapping appropriate identity, appearance and narrative information into its native fields. PC skills/selection fields and NPC activation/image fields are not interchangeable. Report newly supplied defaults and preserve unmapped source information; the conversion maps fields and is not lossless. IW can offer the same canonical name as both PC and NPC without exclusion prose.

## Dependencies and application

Record dependencies as included, external or unresolved. Native IDs can be checked statically; variable roots, prose references and dynamic paths need a reader, so the export helper marks dependency review as unresolved until someone does it. A complete export can still depend on content it does not contain.

To apply entries, inspect the destination and preserve its unrelated content. Resolve native IDs, variable names, skills, activation requirements, ordering, starting values and referenced blocks. Remap collisions consistently; never run a blind global string replacement. Keep bank IDs unchanged. Report adaptations, additions and unresolved dependencies, and validate the complete destination world. A source bank remains unchanged unless its update was requested.

## Full-content build report

Offer this optional deliverable whenever outputting a world. It is a portable report of all fields and objects, not a prose inventory: export the full world, including metadata and unknown fields, with a restoration layout and source fingerprint. It can later supply selected entries or restore the original world definition. It is separate from the Authoring report containing explanations, substitutions and verification notes.

A complete report retains array ordering, empty containers and root fields. Bundling components does not remove their source paths. Removing or changing components invalidates exact restoration; integrate such edits deliberately rather than changing the fingerprint to conceal differences. This is JSON-data equivalence, not byte-for-byte preservation of whitespace, key formatting or numeric spellings. Scripts and other string contents remain exact.

## Tool workflow

Run from the kit root; no third-party Python dependencies are required:

```sh
# Full-content report; restores the complete world definition.
python tools/data_bank.py export World.json --out Build-Report.txt
python tools/data_bank.py check Build-Report.txt
python tools/data_bank.py restore Build-Report.txt --out Restored-World.json

# Selected objects; repeat --select and optionally --tag.
python tools/data_bank.py export World.json --select /NPCs/0 --out Character-Bank.txt --tag fantasy

# A selected mechanical bundle; review its dependencies before reuse.
python tools/data_bank.py export World.json --select /trackedItems/0 --select /triggerEvents/0 --bundle "Shop system" --out Shop-Bank.txt

# Edit authoritative JSON with tools, then rebuild presentation and hash.
python tools/data_bank.py unpack Character-Bank.txt --out Bank-Edit.json
python tools/data_bank.py pack Bank-Edit.json --out Updated-Bank.txt
```

Output paths must be new; the tool refuses silent overwrite. Check the updated bank, preserve a prior copy, and return the complete new file. For a manual merge, unpack both, retain entries and dependencies, resolve conflicting bank IDs deliberately, then pack the combined data. Do not carry a completeWorld restoration claim into a bank combining different sources; retain relevant source metadata per entry instead.

The helper rejects duplicate JSON keys, checks bank structure and included-entry targets, and verifies hashes for text banks. It preserves arbitrary-precision integers and decimal numbers without float rounding. Its hash check does not validate IW payload schemas, semantic dependencies, tags or prose summaries; use the world validator after integration. Unknown bank metadata is preserved.

Without code execution, use the same `.txt` format with `SHA256: UNVERIFIED`, or return the authoritative `.json` bank source with readable discussion separately. Never fabricate a hash or claim round-trip verification. The helper accepts either form, explicitly distinguishes an absent hash from verified integrity, and computes a hash when packing. Large edits should preserve untouched payloads and be checked with tools before being called lossless. Keep the latest returned bank for future sessions; an uploaded attachment may not be writable or remembered in another session.

# Infinite Worlds export reference

Compatibility baseline and evidence labels: [Verified-Behavior.md](Verified-Behavior.md). For an overview of every identified condition and effect, including Change first action and Change other characters, read [Trigger-Catalog](Trigger-Catalog.md) first; this file gives their payloads.

This reference describes arbitrary IW worlds. The schema and validator contain no required action engine, region graph, game-specific trackers, inventory rules, scores or narrative-control framework. Optional features remain optional. The authoring prompt explains how to choose features for the user's idea.

## Scope and validation

`../tools/iw-export.schema.json` is a JSON Schema Draft 2020-12 profile of the native export structure as observed: known fields have characterized types, and unknown fields, values and condition/effect discriminators are accepted with a warning where the validator can identify them. The vocabularies it lists are the ones observed, so a value outside them is a warning to check, not an error.

The editor requires at least one skill; the schema's other `required` declarations are sparse, so a minimal object that passes is not thereby a usable import. `../World-Template.json` supplies the envelope and leaves the story for the author.

The validator checks explicit tracker, trigger, PC, NPC, block and skill wiring, returns structural errors before reference traversal, and exits 0 with no errors (warnings permitted), 1 with validation errors, or 2 for an input/dependency problem. Read each warning: a known opaque-code warning is a different thing from an unknown payload or an unresolved target. What it cannot check (PawScript execution, references hidden in text, instruction compliance, importer acceptance) is listed in [tools/Usage.md](../tools/Usage.md).

## Field and editor groups

|Editor purpose|Native fields|
|-|-|
|Introducing the story|title, description, background, firstInput, objective, charSelectText; preview image metadata|
|Main instructions|instructions, authorStyle, mature, nsfw, contentWarnings; instructionBlocks|
|Specialist instructions|evaluationRequest, descriptionRequest, summaryRequest, videoPromptInstructions|
|Image style|imageModel, imageStyle, `illustrationStyle*` and `imageStyle*` controls|
|Player character options|skills, possibleCharacters; PC skill/portrait/start-value data|
|Victory and defeat|victoryCondition, defeatCondition|
|Other characters|NPCs|
|Keyword instruction blocks|loreBookEntries|
|Tracked items|trackedItems|
|Triggers|triggerEvents, conditions|
|Permissions|permissionsOnceShared, `allowChangeCharacter*`|
|Metadata/advanced controls|schemaVersion, favorite, hideSkillSystem, autoAdvanceVersion, version, designNotes, showPawScriptButtons|

These groups map purpose; not every UI label corresponds one-to-one to a field. `recommendedAIModel` is obsolete/export-only with no current editor selector; keep it null if retained. `driftAcknowledgedForName` is editor metadata for the variable-name mismatch alert, not a script alias; see [Trackers.md](Trackers.md). `advancedLogic` accompanies the trigger editor's advanced condition setup: use true for authored nested logic groups and preserve existing values; the logic node tree is what executes. `showPawScriptButtons` stores the editor's PawScript Expression Editor button option. Metadata is not story context: put necessary instructions in AI-facing fields. schemaVersion is visible in raw JSON; it is not an application release number.

## Identifiers

Tracker IDs, display names and PawScript variable names serve different purposes: native effects and conditions target the tracker `id`, scripts use `variableName`, and users see `name`. Preserve existing IDs when editing. For new trackers, use a unique nine-character ASCII alphanumeric ID, the editor-style form used by the import-tested examples; IDs containing punctuation, spaces or accents are regenerated on import while their references are not remapped. Use explicit descriptive snake_case variableName values in scripts and descriptive display names in the editor. This is the kit's authoring convention, not a claim that other ID formats are invalid. Generate IDs in code and check collisions; without tools, check each newly introduced ID and reference manually. New triggers, blocks and PCs can use the same convention. When combining worlds, remap every explicit reference consistently and validate the result.

## Trackers

Tracker definitions use an ID, display name, explicit variableName, dataType, visibility, initial-value fields and optional AI-update/format instructions. Use unique IDs and variable names; a variable name is not a target ID. Ownership, visibility behavior, memory and name/handle drift are covered in [Trackers.md](Trackers.md).

dataType values: text, number, yaml, xml. Lists and booleans live inside YAML; there is no native boolean/list dataType. `initialValue` is a JSON string even for numeric or structured content. The editor does not enforce numeric-only input in Number controls, so use numeric literals when calculations depend on them.

visibility values: everyone, player_only, ai_only, ai_only_boring, hidden, hidden_boring. Hidden trackers remain readable by scripts and are omitted from ordinary player exports.

`formatExample` and `formatSchema` are strings. The library demonstrates a YAML-like schema notation with text/number, optional-key and open-content forms. formatSchema is not JSON Schema, and the validator does not enforce its grammar.

### Starting values: platform modes

|Mode|Native shape|Intended use|
|-|-|-|
|Same for all characters|Tracker initialValueBasedOnPC same plus initialValue string|Shared initial value|
|Character-defined fixed value|Tracker character mode; per-PC initialTrackedItemValues entry targets tracker ID and contains initialPCValue string|Different value for each predefined PC|
|Character-defined fixed selection|Same per-PC entry with initialPCValue array of strings|Choose one supplied option for that character|
|Character-defined script selection|Same per-PC entry with initialPCValue empty and initialPCValueChoicesScript string|Script generates that character's choices at startup|
|Player-defined selection|Tracker initialValueBasedOnPC player, initialValue string, initialValueChoices array of strings|Player chooses a startup preference independently of PC-specific values|

The optional-block example (../examples/optional-block.json) shows the player form: initialValue On, initialValueChoices [On, Off], player mode and autoUpdate false. Those are tracker-level fields; do not put this list into a per-PC initialTrackedItemValues entry unless the character-defined mode is intended. A live change later (through the Storyteller-mode tracker editor) affects the following turn.

Per the editor, script choices are evaluated at game start from initial tracker values, including that character's values and skills. Use one mode per tracker; the precedence of conflicting initialization fields, and player-mode controls for unconstrained input types, are not established.

## Conditions

A condition node is either a leaf (`category: "condition"` with type and data) or a logic group (`category: "logic"`, operator and a data array of child nodes; operators and, or, none_of). Normal condition lists are AND. Every node needs category, type and id. IDs are opaque, and importer preservation is entity-specific: use ASCII alphanumeric IDs for new trackers (see Identifiers above). Field case matters: trackedItemID, targetTrackedItemId and characterId are different native spellings.

|type|data shape and intent|
|-|-|
|triggerOnPawScript|Bare expression STRING, without `<< >>`; deterministic check of current state|
|triggerOnEvent|Scenario STRING interpreted by AI; flexible but subject to false positives/negatives. Must match an entry in the root `conditions` registry exactly; multiple triggers can reuse each Scenario. Registry size: see [Triggers.md](Triggers.md)|
|triggerOnTrackedItem|Object: trackedItemID, inequality, requiredValue, textComparison; target uses tracker ID, not variable name. requiredValue may be a `$variable`, read when checked. See Comparator fields|
|triggerOnTurn|Native string or numeric turn threshold|
|triggerOnCharacter|Array of possibleCharacters characterId references|
|triggerPrereqs|Object: prereqs array of trigger IDs, firedThisTurn boolean|
|triggerBlockers|Object: blockers array of trigger IDs, firedThisTurn boolean|
|triggerOnRandomChance|Success percentage as a STRING: numeric literal, variable or PawScript expression, re-evaluated at each check; "50" means a 50% chance|

Use a PawScript condition where it reads more clearly than native conditions; both are evaluated mechanically.

## Comparator fields

For Number trackers, `inequality` selects is_exactly, at_least, not_equal or at_most. For Text trackers, `textComparison` selects contains or does_not_contain. Do not extrapolate other comparison strings. Exports may retain both fields; they are not two simultaneous predicates. Numeric conditions natively carry `textComparison: "contains"`; if it is missing or empty, the condition is dropped from the export and the trigger loses that gate. Text Contains matching is ASCII case-insensitive. Native numeric and text controls are type-aware despite text-entry fields. Use PawScript for structured YAML field checks rather than text comparison over a whole document.

Native wrappers can repeat trackedItemID/inequality outside `data`. Keep wrapper and payload identical, following the convention of the export you are editing; the validator reports a disagreement as an error.

Run Script cannot edit these system properties or the background: stage text in a tracker and apply it with the native effect. A null victoryCondition/defeatCondition is an exported disabled ending.

## Native value effects

|Field / operation|Meaning and safe use|
|-|-|
|trackedItemID|Target tracker ID|
|action set|Replace target value with newValue|
|action add|Numeric addition or text append according to target type|
|action subtract|Numeric subtraction; the native text-removal operation uses this serialized action|
|action replace|Replace matched text newValue with replaceWith|
|newValue|String payload; numeric content is still serialized as text. Numeric add/subtract also accepts dice text such as `2d3`, rolled on each execution|
|path|Plain dotted path, e.g. wallet.coins; empty targets the whole tracker|
|updateMode|`path` edits a selected path; `replace` replaces the whole YAML value|
|action append|Add a value to the list at path; distinct from numeric/text add|
|listExpression / targetExpression|Empty in current exports; preserve when importing, but do not use them to invent an unsupported editor workflow|
|replaceWith|Always serialize, as "" when unused. An effect missing it was associated with the game failing at the opening|

Text adds accumulate and preserve literal quotation marks; text removal removes all matching occurrences. Repeated numeric writes within one trigger behave differently ([Triggers.md](Triggers.md)). [Payloads.md](../examples/Payloads.md) has separate native text and number examples.

The YAML editor offers Replace Value, Path, and "Do Something Complicated" (which directs authors to Run Script); there is no separate List Update workflow. Path offers Set a Value, Remove Value, Add to a list and Change Number By. Set uses YAML text with optional `<<...>>` interpolation, including whole-structure injection. Add to a list exports action append, Remove Value action remove, and Change Number By action adjust, all with updateMode path. Do not confuse these YAML operations with native text subtract or numeric add/subtract. Path fields are unchecked editor inputs: review target structure and operation together ([Editor-UI.md](Editor-UI.md#import-export-and-preserving-work)).

Adding one list member is different from updating every member. To refill each character's HP, use a script:

```text
for each $member in $test_party
  $member.hp = $member.max_hp
```

For structured append payloads, a leading `-` describes a list, while `name: Frank` with sibling fields describes one record. Flow-style YAML record append stores structured data and permits duplicates. Duplicates are kept and nested shapes are stored as written; use Run Script for list-wide transformations and deduplication.

## Choice and input forms

Present Choice includes message, choices, targetTrackedItemId, selectionMode, updateMode, limits, delimiter and path. `choices` is one newline-separated STRING (JSON `"Take road\nTake ferry"`). Single selection uses selectionMode single with null limits; multiple selection uses selectionMode multiple, string min/maxSelections such as "1" and "3", and valueDelimiter newline or comma.

Request Input uses requestText, targetTrackedItemId, inputMode (single or multi), requiresInput (true or false) and path; YAML targets expose a dotted path. The answer goes into the tracker, not into the next turn's action.

[RUNTIME] Correctly bound single-answer forms work: narration streams, the inline form waits for submission, the target tracker updates immediately, and following triggers can fire in the same turn. The tested follow-up message renders above the question/answer receipt; placement does not imply execution before submission. Required forms offer no cancellation. Multiple-choice bounds constrain selection, and newline-delimited answers are stored as text, not a YAML list. Optional blank input clears its destination while preserving sibling keys; required blank input is rejected. Multiline and nested-path writes preserve line breaks. Other delimiter variants are untested.

Binding must be correct: targetTrackedItemId must name the intended tracker, using an empty path for whole-value targeting. Check bindings after import ([Editor-UI.md](Editor-UI.md#import-export-and-preserving-work)).

## Authoring context

background, firstInput and objective feed AI context and direct play; objective also has a native update effect. They are not merely player-facing metadata. `<#...#>` are IW comment delimiters; fill sample authoring slots inside them, while genuine comments can remain. The sample Time and Location (whereWhen) block is a soft default for visible chronology; whereWhen is runtime output vocabulary, not a root export field.

Skill levels in possibleCharacters are integers from 0 through 5. The editor-provided Evaluation uses skill, difficulty, character context and common sense, including PARTIAL_SUCCESS; there is no established numeric success formula. See [Characters.md](Characters.md#evaluation).

## Assets and persistence

Image and preview fields hold asset references that IW generates; author the prompts and let the image workflow produce the references ([Images-and-Models.md](Images-and-Models.md)). Image style fields can require editor save/reload before their export reflects changes. Preview strings can persist with no attached image; empty settings can auto-populate. Preserve intentional whitespace. Nonempty portrait metadata has string fields for appearance, clothes, expression/position and setting.

Import/export steps and live copies are in [Editor-UI.md](Editor-UI.md); the trailing-newline issue is an importer quirk, not invalid JSON.

Importer-required fields beyond those observed, the path/list-expression targeting modes, initialization-field precedence, random-dispatch duplicate weighting and skill slug normalization are among the unresolved items in [Notable-Findings.md](Notable-Findings.md#still-unknown).

# PawScript working reference

PawScript reads game data, computes values and updates trackers. It is its own language, not JavaScript or Python. Start with sections 1-3 when learning; use the later tables for lookup. Examples use declared tracker variable names, not display names or IDs.

## 1. Where PawScript runs

| Context | Example | Purpose |
| --- | --- | --- |
| Template in supported text field | `Coins: <<$coins>>` | Insert result into text; no mutation |
| Deferred template in text installed by a block-modification effect | `Coins: <=$coins=>` | Stays live after installation instead of freezing; no mutation |
| PawScript trigger condition | `$coins >= 5` | Return true/false; no mutation |
| Run Script trigger effect | `$coins -= 5` | Execute statements, save changes |

An **expression** returns a value. A **statement** performs work, such as assignment or a loop. Script conditions are still expressions: the test after `if` decides whether its indented statements run. Use bare code in trigger conditions and Run Script, without `<<...>>` or Markdown fences. Text that a block-modification effect installs is a snapshot of its `<<...>>` values; a deferred `<=...=>` reference stays live in that destination. See [Runtime.md](Runtime.md#template-interpolation-runtime) for template timing.

Example, in the content of a Modify instruction block effect:

```text
Win path: <=choose($win_path, "escape", "Find the hidden exit before dawn.", "expose", "Gather proof and reveal the warden.", "Survive until the relief ship arrives.")=>
```

When the effect installs this text, the deferred reference is kept rather than resolved, so the block describes the current `win_path` each time it is prepared. Written as `<<choose(...)>>`, it would freeze when the effect ran. In the JSON export the inner quotation marks are escaped as `\"`.

`<<=...=>>` stays literal despite the editor's highlighting ([Editor-UI.md](Editor-UI.md)); what happens when a tracker is set to a deferred reference is in [Verified-Behavior.md](Verified-Behavior.md).

PawScript cannot write arbitrary world fields, including background or instruction-block content, or invoke native trigger effects. Calculate or assemble content in trackers, then use native effects to install it or display messages. Templates do not expand write permissions. `$player` and `$game` are read-only; do not infer writability from a field being readable.

A script changes state only when it executes. It does not automatically enforce what the storyteller narrates. Trigger timing and template installation timing are described in [Triggers.md](Triggers.md) and [Runtime.md](Runtime.md).

## 2. Values, trackers and scope

Create a tracker before referencing it. Its `variableName` supplies the root: a tracker named Party with variable name `party` is `$party`. A script assignment does not create a missing tracker.

| Value shape | Example | Access |
| --- | --- | --- |
| Number | `12` | `$coins` |
| Text | `"Open"` | `$status` |
| Boolean | `true` or `false` | `$state.ready` |
| List | `list("red", "blue")` | `$colors.item(1)` |
| Record (named fields) | YAML below | `$hero.name` |

List positions are **1-based**. A record uses keys, not positions. A list of records represents several objects; a record containing lists represents one object with collections.

For example, this YAML initializes one record:

```yaml
name: Mira
hp: 4
tags:
  - scout
  - injured
```

Stored in tracker `hero`, it provides `$hero.name`, `$hero.hp` and `$hero.tags`. YAML indentation defines nesting; `[]` initializes an empty list and `{}` an empty record. Quote numeric-looking identifiers such as `"001"` to preserve leading zeros in storage; comparisons and arithmetic still treat them as numbers (quoted or unquoted `007` plus 1 gave 8). YAML `yes`, `no`, `on` and `off` are text, not Booleans. `true`/`false` compare equal to both the Boolean and the same-spelled text. A `null` value's `.exists()` is false. Use YAML `|` for multiline text. In an export, `initialValue` is a JSON string containing this YAML, not a JSON object. `formatSchema` is a separate shape description; see [Trackers.md](Trackers.md).

Persistent roots use direct assignments: `$coins = 12`. Temporary locals use `set $price = 5` and last only for that script run. Locals do not cross Run Script effect boundaries; executed branch locals and the last nonempty-loop binding remain available later in the same script. Do not give a local the name of an existing tracker. Inside collection predicates, bare field names refer to the current member; `$...` refers to a tracker/system root or script local. For a list of plain values, `value()` denotes the current value.

## 3. A complete small example

Create a YAML tracker named Party with variable name `party`, initial value below, and automatic AI updates disabled for this mechanically managed example:

```yaml
- name: Mira
  hp: 4
  max_hp: 8
- name: Oren
  hp: 8
  max_hp: 8
```

**Read:** put `Injured members: <<$party.where(hp < max_hp).count()>>` in a supported template field.

The chain reads left to right:

1. `$party` is the whole list.
2. `.where(hp < max_hp)` selects injured members. Each comparison uses that member's fields.
3. `.count()` returns the selection size. This reads data; it does not heal anyone.

**Test:** a PawScript trigger condition can use `$party.any(hp < max_hp)` to decide whether healing is needed.

**Change:** a Run Script effect can restore every member:

```text
for each $member in $party
  $member.hp = $member.max_hp
```

The loop variable refers to each original member, so assignments persist in the tracker. After execution, both members have full health and the injury condition is false. Inspect tracker data to verify this; no visible story output is required. Add a native message effect if the player should receive confirmation.

Use the expression/script Sandbox to try the read and change separately. For an in-game trigger, also configure timing and repeat behavior; see [Triggers.md](Triggers.md). To practice, change the condition to detect a member at zero health, then predict the result before running it.

## 4. Expressions and decisions

| Operation | Syntax / meaning |
| --- | --- |
| Arithmetic | `+ - * / % ^`; `%` is remainder, `^` is exponentiation |
| Comparison | `= != < <= > >=` |
| Logic | `and`, `or`, `not`; parenthesize mixed tests |
| Text concatenation | `"Coins: " & $coins`; numbers become text |
| Conditional value | `if($coins >= 5, "Affordable", "Too expensive")` |
| Value mapping | `choose($status, "open", "Enter", "locked", "Find a key", "Inspect")` |
| Missing/blank fallback | `first_available($hero.nickname, $hero.name, "Stranger")` |
| Error fallback | `try($total / $count, 0)`; catches missing paths, type mismatches, division by zero, reads through a scalar and out-of-range `item(99)`. Do not use it to conceal broken essential state |
| Existence | `$hero.nickname.exists()`; distinct from being nonempty or nonzero |
| Numeric bounds | `$hp.constrain(0, $max_hp)` |
| Rounding and bounds | `round_down($cost)`, `round_up($cost)`, `$cost.round()`; standalone `round(1.6)`, `min(2, 3)`, `max(2, 3)` also work |
| Text normalization | `$label.replace("_", " ")` |

`=` compares within an expression and assigns in an assignment statement. In the following script, the first `=` tests; the second writes:

```text
if $status = "locked"
  $status = "open"
```

`and` and `or` short-circuit, as do native And/Or condition groups. A left-hand guard can prevent an unsafe right-hand read; this skips evaluation but has no measured speed benefit. Fallback and `try` operations handle missing values but do not make expressions valid in unsupported contexts. `current()` is rejected in Run Script; it belongs to a legacy List Update context the current editor does not expose. Functions require parentheses: `.count()` calls a function; `.count` reads a field named count.

A statement-level branch changes data, unlike expression-level `if(...)`, which returns a selected value:

```text
if $coins >= 5
  $coins -= 5
  $purchases.total += 1
else
  $message = "Not enough coins."
```

Declare `coins`, `purchases` (including `total`) and `message` first. Use `else if` for additional branches, at the same indentation as `if`. `#` starts a script comment; instruction-text comments use `<#...#>` instead.

## 5. Collections: select, calculate, change

### Read and select

| Need | Expression |
| --- | --- |
| Construct a list / empty record | `list("red", "blue")`, `list()`, `record()` |
| First item / first few | `$party.first()`, `$party.first(3)` |
| Last item / recent subset | `$history.last()`, `$history.last(3)` |
| Dynamic record lookup | `$catalog.item($selection)` |
| Lookup with read fallback | `$reputation.item($faction, 0)` |
| Record keys / values | `$catalog.keys()`, `$catalog.values()` |
| Key or value membership | `$catalog.contains($selection)` tests a record key; `$tags.contains("scout")` tests a list value |
| Matching records | `$party.where(hp < max_hp)` |
| Matching plain values | `$tags.where(value() != "retired")` |
| Any / every / none | `$party.any(hp > 0)`, `$party.every(hp > 0)`, `$party.none(hp > 0)` |
| Project fields | `$party.all().name`, `$party.where(hp > 0).name` |
| Total a field | `$party.sum(hp)` |
| Largest field value | `$party.max(hp)` |
| Member with largest value | `$party.max_by(hp)`; append `.name` to read its name |
| Sort by a field | `$party.sort_by(hp, desc).all().name` |
| Remove duplicate values | `$tags.unique()` |

A selection can contain several members even when you expect one. Use stable unique keys when identifying an object. Guard empty selections before requesting a member. `every(...)` is true for an empty list; add a count check when your rule requires at least one member.

Within filters, `name contains "fire"` tests the current member's field; `id in $unlocked` checks membership in an outer list. Bare `in` is filter syntax, not a general replacement for `.contains(...)`. For example:

```text
$abilities.where(id in $unlocked).all().name
```

An advanced predicate can check named requirements:

```text
$requirements.every($flags.item(value(), 0) = 1)
```

Initialize `requirements` as a list and `flags` as a record. An empty requirement list passes; a missing flag uses zero and fails. Missing structure and empty structure are different cases.

### Write and mutate (scripts only)

| Need | Statement |
| --- | --- |
| Assign a field | `$hero.hp = $hero.max_hp` |
| Update a dynamic key | `$reputation.item($faction) = $reputation.item($faction, 0) + 1` |
| Append an entry | `$entries.append($new_entry)` |
| Remove a record key | `$catalog.remove($selection)` |
| Remove every equal list value | `$tags.remove("retired")` |
| Remove selected members | `$party.where(hp <= 0).remove()` |
| Replace matched records | `$entries.where(id = $update.id) = $update` |
| Persist a transformed list | `$tags = $tags.unique()` |

Assigning a record copies it: `$archive = $current` keeps an independent copy that later edits to `$current` do not change. A read such as `$tags.unique()` does not change stored tags by itself. Assignment persists its result. Appending a list appends its members; it does not wrap them as a nested list. Replacement of matched records is not a field-preserving merge: include every field to retain. Plain nested assignment can create missing paths, but a scalar parent rejects child writes and rolls back the script; compound arithmetic on a missing path can fail where plain assignment succeeds. Boolean-expression results can be stored as quoted text, so rendered output is not strict type introspection. Native text add/remove effects are not substitutes for structured list mutation.

To construct an entry, create a local record, fill its fields and append it:

```text
set $entry = record()
$entry.id = "supply-cache"
$entry.name = "Supply Cache"
$entries.append($entry)
```

Initialize `entries` to `[]`. Repeating this script adds another entry; add an identity check if duplicates are unwanted.

Loops can iterate lists or records; `range(n)` supplies a bounded repetition list. Keep mutations straightforward. Library buffer examples remove processed entries while iterating; do not assume every different mutation loop is equally safe. For new update-buffer designs, iterating updates and clearing the buffer afterward is easier to reason about. Test new complex selection/mutation chains in Sandbox.

## 6. Randomness and formatted output

| Need | Expression |
| --- | --- |
| Numeric random value | `random()` |
| Inclusive integer range | `random_between(1, 6)` |
| Dice sum | `dice_roll(6, 3)` or `3d6` |
| One random list member | `$encounters.random()` |
| Several without repeats | `$encounters.random(3)` |
| Shuffle | `$encounters.shuffle()` |
| Text with expressions | `format_text("Coins: {$coins}")` |
| Join list values | `$names.join(", ")` |
| Format each record | `$party.format_each("{name}: {hp}/{max_hp}").join("\n")` |
| Numbered / bulleted output | `$names.numbered_list()`, `$names.bulleted_list()` |

`dice_roll(sides, count)` defaults to six sides and one die. Every random evaluation can produce a new result. Store a shared roll once when several checks or outputs must agree:

```text
$roll = dice_roll(6)
if $roll >= 4
  $result = "Success"
else
  $result = "Failure"
```

Declare `roll` and `result` first. An inline block can instead say `Encounter roll: <<dice_roll(6)>>`, but that only supplies a number; instructions or deterministic effects must define its consequences. Permanent block templates and templates installed through block effects evaluate at different times; see [Runtime.md](Runtime.md#template-interpolation-runtime).

Inside `format_each`, `{name}` reads the current member's field, `{$coins}` reads an outer tracker, and `{value()}` reads a plain list member. `index()` supplies a 1-based position. These braces belong to formatting functions; they are not a replacement for outer `<<...>>` template delimiters.

Additional presentation helpers include `.bold()`, `.italic()`, `.code()` and `.format_date(...)`. Formatting produces display content, not styling guarantees in every UI field. `now_utc()` and `now_local()` report real-world time, not the story's clock. Consult the official reference for date tokens and less common numeric/string functions.

## 7. Execution and debugging

1. Declare trackers and initialize every required structure. Give mechanically managed values one update owner or an explicit AI/script handoff.
2. Test a read-only expression first. Confirm the selected records and values before mutating them.
3. Run the script against known starting data in Sandbox; inspect the resulting trackers.
4. Test it in its trigger. Confirm timing, condition eligibility and order, not only script syntax.
5. Check repeat execution and boundary cases: no matches, insufficient resources, missing optional fields and already-completed work.

Statements in one script execute sequentially. Later triggers see earlier committed writes. Multiple native numeric effects in one trigger can overwrite rather than accumulate; they do not share script statement semantics. A script failure rolls back that script's changes, not preceding effects or the entire turn.

Use `log("Coins: {$coins}")` for diagnostics in the PawScript Log. Logs are not player narration; messages logged before a failure remain useful for locating the problem. "Ran successfully, with no output" is normal for assignments. Writing a key that does not yet exist in a record succeeds but logs `created a new entry 'x' in $tracker - did you mean 'y'?`; treat it as a typo check. A model saying PASS is not runtime verification.

Enable Menu > Settings > Storyteller Mode, then open the bug icon beside tracked items. Inspect tracker state, evaluated conditions and script errors; use Open in Sandbox to isolate a script. See [Editor-UI.md](Editor-UI.md#play-debug-and-live-design) for what debug shows.

The validator's lint is heuristic, not a PawScript interpreter. It checks likely mistakes, roots and locals with limited static analysis; passing it does not prove runtime behavior. When teaching or reporting tests, distinguish documented syntax from compositions actually run in IW. [Verified-Behavior](Verified-Behavior.md) lists the runtime-tested PawScript results.

## 8. System roots, escaping and common mistakes

Read Skills with `$player.skills.<slug>` and display them with `$player.skills_and_levels`. `$game.skill_map` maps slugs to display names. Other roots include `$player.name`, `$game.turn_number` (opening turn is 1), `$game.ai_model`, `$game.skill_list` and `$game.difficulty_list`. Native skill effects change levels; scripts do not write `$player`. Runtime narration fields and video placeholders are separate concepts, not automatically script roots.

| Mistake | Use instead |
| --- | --- |
| `$coins == 5` | `$coins = 5` in a condition |
| `a && b` / `a || b` | `a and b` / `a or b` |
| `if $coins > 0:` | No colon; indent the following statements |
| `"Coins: " + $coins` | `"Coins: " & $coins` |
| `$new_tracker = 1` without declaration | Declare the tracker; `set $local = 1` is temporary only |
| `<<$coins -= 1>>` | Mutation belongs in Run Script |
| `.count` to count members | `.count()` |
| Host-language object literals or arrow functions | `record()`, field assignments and supported collection methods |
| Writing background, blocks or system roots | Use the supported native effect |

Escaping has three layers: JSON serialization, PawScript string literals, and rendered text/YAML. Use a JSON serializer. A physical newline separates script statements; the two-character `\n` inside a script string represents an intended text newline. For example, the decoded script:

```text
$message = "Ready\nProceed"
```

has this JSON string representation:

```json
"$message = \"Ready\\nProceed\""
```

Inspect decoded code when debugging escapes. Include spaces explicitly when composing text with numbers. Do not add host-language semicolons, statement braces, arbitrary libraries or external IO.

# Turn lifecycle, templates and endings

How a turn is processed, when `<<...>>` templates are evaluated, how the specialist requests divide the work, and how endings are defined. Evidence labels and the compatibility baseline are in [Verified-Behavior.md](Verified-Behavior.md); what remains unresolved is listed in [Notable-Findings.md](Notable-Findings.md#still-unknown).

## Turn lifecycle [RUNTIME]

```mermaid
flowchart TD
    I[Initial values and opening setup] --> G[Generation with current context]
    P[Player input] --> G
    G --> U[AI tracker updates available]
    U --> T[Triggers evaluated in order]
    T --> E[Effects and player messages]
    E --> N[Updated context for later generation]
    N --> P
```

- Start+Mid+repeat triggers execute in a pre-opening setup pass and again during the first normal turn. Messages from the setup pass appear before the opening background. Trigger history records setup-pass firings as turn 0; `$game.turn_number` during setup is unknown. Guard initialization and counters accordingly.
- During normal turns, the AI's tracker updates are available to trigger conditions, and ordered triggers see earlier triggers' writes. Execution order is the `triggerEvents` array.
- Scenario judgments are available for their trigger checks; their exact stage relative to Evaluation, narration and tracker updates is not mapped.
- Messages belong to their effects and appear as each effect runs. Choice/input effects suspend for a player answer; a correctly bound single-answer form updates its tracker immediately, and later triggers read the answer in the same turn.
- Guidance and block changes do not rewrite narration that has already been generated; they supply context for the next generation. When guidance effects conflict, the first tends to win, so generate one coherent directive.
- Summary compression runs after turn 8 and every six turns after that, leaving the 2–7 most recent turns uncompressed; its ordering relative to other turn stages is unknown.

Timing flags (Start, Mid Game, repeat), prerequisites and blockers are covered in [Triggers.md](Triggers.md).

## Template interpolation [RUNTIME]

Use `<<expression>>` inside supported text templates; use bare expressions in `triggerOnPawScript` and bare code in Run Script. Variable references use `$`; older templates such as `<<skills_and_levels>>` appear in existing worlds, and `$player.skills_and_levels` is the form for new content. [Expressions guide](https://infiniteworlds.app/pawscript-expressions-guide)

| Surface | When the expression is evaluated |
| --- | --- |
| Main/active instruction text | When the text is prepared for AI context, every turn; conditional expressions select current guidance |
| Show Message / native effect text | When that effect runs |
| Initial values / PC script-generated options | At initialization only; not a live binding |
| Native block-modification content | When the effect installs the text, and never again: `coins=13` stayed 13 while Coins advanced to 14 and 15. A deferred `<=...=>` reference in the installed text stays live |
| A tracker's own update instructions | Every turn, before the AI writes the tracker |
| NPC, keyword, image, specialist or metadata fields | Not tested; use ../examples/probe-template-timing.json before relying on a new field |

An expression authored directly in a permanent block selects current text without a switching trigger. Ordinary `<<...>>` expressions passed through a block-modification effect become a snapshot; to keep a value live, write a deferred `<=...=>` reference in the installed text (worked example in [PawScript.md](PawScript.md)), keep the expression in a separate permanent block, or refresh the block when the source changes. Nested expression strings are not evaluated recursively. Selected text still enters context, so selection does not save tokens by itself. Independent random expressions give independent results; store a shared roll in a tracker when several outputs must agree. For temporary instruction-block installation with a retained result, see [on-demand generation](Recipes.md#dynamic-content).

## Specialist requests and runtime outputs

| Export field | Responsibility | When empty |
| --- | --- | --- |
| evaluationRequest | Interpreting action feasibility, skills/difficulty and outcome reasoning | IW uses its built-in Evaluation, reproduced verbatim in Default-Evaluation.txt; leave empty unless a custom Evaluation is part of the design ([Characters.md](Characters.md#evaluation)) |
| descriptionRequest | Narration, viewpoint, presentation and prose rules | IW's default asks for several paragraphs |
| summaryRequest | What the persistent summaries must retain | IW's default summary; name the facts important to this world's continuity ([Trackers.md](Trackers.md#memory-continuity-and-context-cost)) |
| videoPromptInstructions | Video planning, image position and prompt | IW's defaults; leave unless video is part of the design ([Images-and-Models.md](Images-and-Models.md#video)) |

Evaluation outputs such as SUCCESS and FAILURE are generated text that guides the AI's thinking; they are not control tokens and do not fire triggers. Replacing a default request with a large custom framework changes its responsibilities; carry over the framework's dependencies rather than one field.

To shorten narration, append to authorStyle: "The outcomeDescription must be at most 2 short paragraphs and no more than 90 words. This is a maximum, not a target, and overrides any other length instruction." Output lands near the number, sometimes 10–20% over. The same text in descriptionRequest is weaker. No wording has been found that reliably lengthens narration. Narration renders ordinary Markdown; raw HTML renders as literal text, so test headers or special formatting in their display context.

Runtime output names that the sample library refers to in instructions:

| Names | Meaning |
| --- | --- |
| evaluation | The generated assessment of the attempted action |
| playerAction | The current player input |
| outcomeDescription | The main narration |
| whereWhen / whereWhenAfter | Place/time context before/after the narrated scene; formatting guidance can target whereWhen |
| elapsedTime | Generated elapsed-time information; type and units unspecified |
| secretInfo | Generated secrets, planning and off-screen developments |
| option1_text / option2_text / option3_text | The suggested player actions |
| illustrSubject / illustrIsCharacter | Illustration subject and character/scenery distinction |
| illustrAppearance / illustrClothes / illustrExpressionPosition / illustrSetting | Visual descriptors |
| stateVariablesUpdates | The AI's tracker-update output |

These are names for parts of the generated output. They can be described in instructions and specialist requests, but they are not template variables, script roots or root export fields, and their contents are generated text rather than engine memory. secretInfo legitimately holds secrets, planning and off-screen developments, and the Storymaster family structures it explicitly; impose an empty-secretInfo policy or a reset system only when a world's design asks for it.

## Endings

Native victoryCondition/defeatCondition is null (disabled) or `{condition, text, alreadyFired}`. `condition` is natural-language text stating the accomplishment or failure precisely, not a PawScript expression; `text` is the player-facing ending message. Initialize `alreadyFired: false` for a fresh world and preserve it when editing a live export unless deliberately resetting ending state. The field can stay false after an ending and continuation, so use your own tracker if ending history is needed.

For an exact state threshold, use a PawScript condition plus Show Message and Ends Game. `effectEndsGame.data` says whether the player may continue: true offers Continue game, which restores actions after confirmation at no charge; false removes continuation and action controls while history and regeneration remain. The built-in natural-language ending checker runs on its own timing, which is unknown.

## Current-game editing and debug boundaries

Live copies and what editing them changes are covered in [Editor-UI.md](Editor-UI.md#import-export-and-preserving-work). Debug shows keyword-block active/inactive state and its keywords, but not the matched keyword, activation turn or remaining retention, and nothing about NPC activation or static character information. A live-world JSON export can retain a tracker's initialValue after a runtime change; read current tracker data for current values.

[Editor-UI](Editor-UI.md) contains the workflow detail; [Verified-Behavior](Verified-Behavior.md) consolidates the tested results.

# Skills, player characters, NPC cards and keyword blocks

The structured character data IW works from: Skills and the Evaluation that uses them, player-character entries, Other Character cards and keyword lore. How to write the prose inside these fields is in [Craft.md](Craft.md).

## Skills and player characters

Root `skills` is a list of display names. Each possibleCharacters entry has a `skills` object keyed by those names, with integer levels from 0 through 5. Define focused skills with distinct jobs (Observation, Persuasion, Engineering); the AI selects the available skill whose name best matches the attempted action, so overlapping names make that choice ambiguous. A neutral generic skill is appropriate when the story does not need skill distinctions. PC `description` establishes identity, abilities and context for the storyteller, not only the selection page. `charSelectText` introduces the available choices to the player. The allowChangeCharacter* flags control which parts players may customize ([Editor-UI.md](Editor-UI.md#permissions-and-specialist-destinations)).

Keep at least one skill. For generated JSON, use `hideSkillSystem: false` when Skills should be visible; an unchecked editor option omits the field, which is the normal visible-skills state. `hideSkillSystem` hides the skill system's presentation only.

PawScript exposes `$player.skills`, `$player.skills_and_levels`, `$game.skill_map`, `$game.skill_list`, `$game.skill_example`, `$game.difficulty_list` and `$game.difficulty_example`. The skill map connects runtime slugs to display names; read it rather than deriving slugs from names. The difficulty names are Trivial, Easy, Medium, Hard and Legendary. Skills not raised default to level 3; set every authored PC level explicitly. [PawScript reference](https://infiniteworlds.app/pawscript-reference)

Native `effectChangePCSkill` uses the declared display name. `amount` is an integer magnitude; `increase: true` increases toward `minmax` as an upper cap; false decreases toward it as a lower bound. Each effect caps: two successive triggers increasing a level initially 2 by 2 up to 4, then by 1 up to 4, finish at 4. ../examples/probe-skills.json exercises increases, decreases and boundary cases.

Use the numeric skill values for mechanical checks; generated skill labels and Evaluation descriptions can disagree with them.

## Evaluation

`Default-Evaluation.txt` is the editor's prefilled Evaluation text, verbatim: the baseline IW uses when evaluationRequest is empty and the starting point for a custom one. It asks for a brief assessment, a skill and difficulty, and DENIED, SUCCESS, FAILURE or PARTIAL_SUCCESS. Trivial uncomplicated actions succeed and impossible assertions are denied without further evaluation; otherwise proficiency, difficulty, character history, instructions and common sense inform the judgment. Partial success covers incomplete achievement, failure with a silver lining, or success with drawbacks. There is no numerical success-probability table. The Script Library's Storymaster override defines its own caveat labels; keep it distinct from the baseline.

## NPC cards

NPC field purpose and activation guidance are [DOCUMENTED]; the keyword matching and retention below are [RUNTIME].

| NPC field | Authoring purpose |
| --- | --- |
| id | Stable card identity |
| name | Canonical character name |
| names | Recognition names/aliases; comma-separated in the editor; use distinctive forms |
| one_liner | The Summary: compact identity and role; put essential identity here |
| detail | Fuller personality, motives, history, behavior and relationships |
| appearance | Narrative appearance description |
| location | Short starting location (two words at most), an activation cue; not a movement lock |
| secret_info | Hidden character facts; instructions still govern who knows them |
| img_appearance / img_clothing | Visual identity and clothing for image generation; inspect with the wrench under a character image |
| positionInList | Ordering metadata; preserve existing values; use sequential integers for new lists |

Only Name is required in the NPC editor; storytelling and image information are independent optional sections. The brief summary is the only character information available to the storyteller until the turn after the character or their location is first mentioned; characters can activate by name with no location. Detail retrieval is unreliable even then, and the narrator can invent a substitute that history then repeats, or introduce named NPCs into an opening that says the player is alone. Put facts that must surface in one_liner or always-on text and repeat them in detail; correct a wrong invented detail early by editing the turn. For an opening scene, do not depend on card or keyword activation at all: there is no prior context to activate them, so put essential opening facts in firstInput or always-on instructions and give starting NPCs useful brief summaries without duplicating their entire cards. Mentioning footwear in image fields encourages full-body framing, per editor help.

IW permits a character among both player choices and Other Characters under the same name; the selected player can retrieve information from that entry, while the internal merging is not visible. Unchosen player options are not NPCs unless also added as Other Characters. Author the intended relationship explicitly where it matters. PC/NPC conversion is available in Data mode: preserve the source and map relevant fields into the destination type ([Portable-Banks.md](Portable-Banks.md)).

World Debug does not show NPC activation or static character context. Secret fields are a convention the instructions enforce, not a barrier: see the knowledge findings in [Notable-Findings.md](Notable-Findings.md#characters-knowledge-and-memory).

## Keyword blocks

Keyword entries have id, name, keywords (string array) and content. They load through mention matching in recent context, rather than location checks. Matching is case-insensitive and whole-word: quartzbadger and QUARTZBADGER match; prequartzbadgerpost does not, and neither does a simple plural. Surrounding punctuation and authored alternate keywords match. A match keeps the block active on the matching turn and three more: a turn-3 match is active on turn 6 and inactive on turn 7 unless matched again. Player actions, completed narration and Secret Info all contribute to matching, from the next generated turn. The complete tokenizer, multiword behavior and full set of scanned fields are not characterized; there are no matching operators or regex syntax.

Choose distinct phrases and relevant aliases; broad terms such as "man" activate irrelevant lore. A short persistent rule can be always-on while its detailed lore stays keyword-triggered. Choose NPC cards, keyword blocks and always-on blocks by intended activation: make locations or characters dynamically loaded only where the world benefits, and remember that native character and image bookkeeping can matter even when the narrative could be described in an ordinary block.

# Images, video and model-specific blocks

The export fields and editor controls for image style, portraits and video, and how instruction blocks are limited to particular storyteller models.

## Image style

The image-style editor is a reusable style with Name, Model and prompt wrappers. With separate character/scenery prompts enabled, Characters start/end and Scenery start/end add text before and after the respective image prompts; with it disabled, Start/End apply to every image. The export fields are imageStyleCharacterPre/Post and imageStyleNonCharacterPre/Post; a shared Start/End is exported by duplicating the values into both pairs, so no extra switch is needed. The imageStyle value is a generated identifier; preserve it rather than deriving it from the prompt text. A world export carries the style's values, not the reusable style itself.

The older illustrationStyle*LowPriority/HighPriority fields still occur in exports but have no current controls; preserve them in existing worlds and author with the current Pre/Post wrappers, which took precedence over them in testing. Manticore is the model that editor help recommends; its preset text includes IWBeautiful/IWUpscaleFace macros whose mechanism is undocumented. The player can override the selected style. The cover prompt is separate from these wrappers. Exact prompt assembly is hidden.

Dedicated Other Character image appearance/clothing populate Illustration details independently of narrative appearance. Edits change generated images and can be reversed; alias-related clothing drift can occur. Saving Illustration details generates a new image (about 4 credits).

PC portraitPromptDetails holds four strings: illustrAppearance, illustrClothes, illustrExpressionPosition and illustrSetting ([Payloads.md](../examples/Payloads.md) has an example). Image generation and upload produce asset references, which belong in portrait and preview fields. The library's Cover Image script produces a prompt, not an asset: use it in the image workflow, select or upload the result as the world preview, and export the resulting metadata. previewImage holds the asset reference, not prose.

When adapting library image-style text, resolve bracketed slots as deliberate choices: remove unselected alternatives and incidental sexualized defaults unless they match the requested audience and style, keep the neutral medium, composition, lighting and identity guidance, and pick one medium rather than a contradictory list.

## Video

videoPromptInstructions has videoPlan, videoImagePosition and videoPrompt strings: the library uses videoPlan to choose a beat, videoImagePosition to choose start/end anchoring, and videoPrompt to describe the clip. Its `$videoDuration` and `$videoStyle` references are video-context values, not declared trackers or general PawScript roots; confirm their availability in the video editor or debug context before adopting the sample. The kit has no video-enabled runnable example. Editor-side video controls are in [Editor-UI.md](Editor-UI.md#permissions-and-specialist-destinations).

## Model-specific blocks

Enable model selection per world under Show optional features > Misc advanced features > Enable AI-specific instruction blocks. Selected block models serialize in selectedAIProfiles. All-model blocks stay active while selected-model blocks follow the active model, including when the player switches model mid-game. Current-AI-Profiles.json lists each storyteller model's ID, underlying real-world model, isCurrent flag and typical credits per turn, including retired models, as of the date it records; models retire every few months. It is an authoring convenience, not a validator enum: accept historical IDs and preserve imported selections.

Disabling the option removes selectedAIProfiles from exported blocks and hides their controls; the still-open editor remembers the choices if re-enabled, but not after it is closed. A block name alone does not select models.

Per-model text inside one block, and per-model tracker update instructions, use `$game.ai_model` ([Recipes.md](Recipes.md#turn-state-patterns)). Per-model cost is in [Cost.md](Cost.md).

# Feature recipes

These are independent recipes. Select, adapt or omit them; none is a required world architecture.

**Narrative instructions plus AI-updated trackers.** A relationship, journal, outfit, reputation or story-preference tracker can update from the ongoing story without an explicit mechanical action parser. Explain what belongs in it, when to add/change/remove entries, and what should remain stable. Match structured entries by stable identity or names/aliases as appropriate, not a list position that may change. Provide a useful format example; sample data must not silently become real world facts.

**A situation followed by a consequence.** Situation-trigger effects follow story generation; guidance does not retroactively rewrite the scene that caused it. If a behavior must shape that scene, provide the rule beforehand in active instructions.  Use triggerOnEvent for a narrative situation the AI recognizes, optionally AND a tracker/turn/prerequisite condition to narrow it. Effects might give background information, show a message, modify a value, change an objective, present a choice or alter an instruction block. Situation classification is probabilistic; use explicit predicates only for requirements that genuinely need exact enforcement. There is no requirement to replace ordinary actions with event codes.

**A threshold or dependency chain.** A relationship threshold can unlock a new characterization block; a turn condition can introduce weather or a letter; a prior event can enable another event. Intentional one-shot/repeat flags and firedThisTurn scope matter. Check order where the later trigger reads an earlier result. Avoid requiring and blocking the same trigger.

**Choice/input plus later effects.** Present a selection or text form targeting a real tracker, then respond with a later ordered trigger. Correctly bound single-answer forms update immediately. Inspect binding after import; use current tracker data rather than initialValue from the live-world editor export.

**AI update buffer plus scripted merge.** The library's update trackers let the AI propose changed structured entries, while a script merges them into a persistent list. This is useful for large casts or expensive long-lived records. Root the buffer in a record (`entries: []`); list-rooted AI buffers lose updates, even with "append-only" wording. A record root can still jam: the AI may write rows as one nested list (`entries: [[…]]`), and a merge gated on `.entries.any(name.exists())` then never fires again. Gate on a non-empty inbox, drop or unwrap non-record items, and flag an inbox still full after the merge. Match records by identity and ask for complete entries: the buffer is cleared after each merge, so field patches have nothing to apply to. Only use this extra layer when it serves the world.

**Conditional instruction content.** Use a native block-modification effect to add/replace/clear instructions. The source may be fixed text in the effect or text prepared in a tracker by an earlier script trigger. This can control optional image guidance, pacing, prose detail, character behavior or any relevant block. A script changes tracker values; the native effect changes the instruction block. Keep the block ID stable when disabling content so later re-enabling still targets a real block.

**Player-optional block, with no repeated writes.** The pattern in ../examples/optional-block.json:

1. A player-only text preference has initialValueBasedOnPC player, initialValue On or Off, initialValueChoices [On, Off], autoUpdate false. The player picks it at startup; later changes need the Storyteller-mode tracker editor.
2. A hidden non-AI-updated text tracker (hidden_boring in the example) records which choice has actually been applied. It is a cache, not another player preference.
3. A repeatable enabling trigger requires preference On AND cache not Enabled. It writes the enabled block content, then records Enabled.
4. A repeatable disabling trigger requires preference Off AND cache not Disabled. It writes empty content, or a deliberately chosen simpler fallback, then records Disabled.
5. Enable opening and later execution where needed. Initialize the cache empty so the selected startup choice gets applied. Once synchronized, neither trigger fires until the preference changes.

Clearing content is not deleting the instructionBlocks entry. Use `content: ""` as in ../examples/optional-block.json. If disabling a bundle that also changes authorStyle or specialist rules, restore ALL affected behavior to a coherent fallback. For a Storymaster toggle, define an off configuration that uses ordinary narration and no Storymaster-specific specialist or tracker dependencies. The generic toggle example demonstrates the mechanism; a Storymaster toggle needs that fallback bundle as well.

Player-visible preference trackers may be hidden from the storyteller; the triggers read them deterministically. Describe their effect and potential turn cost to the player. Do not create an AI-updated tracker that changes the player's own choice back.

**More exact mechanics when requested.** Script-owned numbers, independent prerequisite checks, a request-classification tracker or a controlled transaction may be useful for a precise system. They are options for that feature, not default requirements for the world. If used, define who updates each value and avoid competing AI/script ownership of the same data. Freshness stamps are for consuming an AI-generated per-turn request, not for ordinary narrative trackers.

**Time and location: a soft default.** Offer the sample's Time and Location (whereWhen) block unless the premise makes a clock/location header unhelpful. Writing the current place and time each turn helps IW maintain chronology and gives the player a reference. Adapt the geography, calendar and precision to the setting; omit irrelevant levels rather than inventing a country or continent. Put exactly one header at the beginning of outcomeDescription, not a second competing heading. This is guidance for runtime output, not a new JSON root field.

**NPCs, keyword blocks and always-on blocks** are chosen by intended activation; see [Characters.md](Characters.md#keyword-blocks).

## Dynamic content

Native block-modification effects substitute ordinary `<<...>>` templates when the content is installed. For live values, write deferred `<=...=>` references in the installed text, use a separate permanent block, or reinstall content when the relevant values change. A block reinstalled every turn freezes values when its trigger runs, so values set by triggers below it arrive a turn late: order producers above the installer, or use `<=...=>`. See [Runtime.md](Runtime.md#template-interpolation-runtime) for the interpolation table.

**Player-selected layered openings.** Combine independent choices into meaningful variations using ordered text replacements, then install the result as background. This avoids authoring every full combination; keep fragments compatible and add combination-specific handling where needed. See [layered opening](../examples/recipe-layered-opening.json).

**On-demand generation with retained results.** Install a substantial generation brief only when needed, store a compact result, and clear the brief after a matching completed request. Do not clear merely because a turn elapsed. Prefer infrequent event-driven requests; retained tracker context and AI updates can outweigh the omitted instructions. See [on-demand generation](../examples/recipe-on-demand-generation.json).


## Turn-state patterns

Optional patterns; trigger order is execution order.

**Previous-value snapshot.** The last trigger (always true, repeat) copies watched values to script-only trackers: `$prev_lp = $lifepoints`. Triggers above it read this turn's change, such as `$lifepoints < $prev_lp` for a spend. AND a delta with an event condition when the story and the number must agree. Clamps (a maximum loss per turn) also go above the snapshot.

**One-turn AI write window.** To let the AI rewrite a locked tracker once, a trigger switches its automatic updating on (optionally with new update instructions), stamps `$window = $game.turn_number` and tells the AI what to write. A relock trigger ordered above it, on `$window > 0 and $game.turn_number > $window`, switches updating off and zeroes the stamp. The switch applies from the next turn, so the AI writes exactly once, on the turn it receives the instruction. Keep the switch out of triggers with Request Input.

**Periodic AI updates.** Unlock a large, slow-changing tracker on `$game.turn_number % N = k` and relock on `% N = k + 1`; it is rewritten one turn in N.

**Cooldowns.** Stamp the turn in the effect and gate on `$last_x <= 0 or $game.turn_number > $last_x + 3`. A very large stamp disables the trigger for good.

**Per-turn verdict tag.** An AI-updated text tracker asks for tags judging only this turn, or None. Text-contains conditions react to each tag, and a last trigger resets it to None (copy it first to keep a record). Tags stay turn-specific; the classification is still the AI's judgement.

**Wait for a well-formed write.** Gate a follow-up on the shape of an AI-written value (contains `(`, no longer contains the placeholder), not mere change, so a malformed write just waits.

**Per-model text.** `$game.ai_model` returns the display name (`Dolphin`, `Smilodon`) and text `=` is case-sensitive. Templates in a tracker's own update instructions are evaluated live, so `<<if($game.ai_model = "Dolphin", "…", "…")>>` there selects per model. Blocks can use selectedAIProfiles instead.

**Start-up codes.** A player-only text tracker at character select holds typed codes; one one-shot Text-contains trigger (case-insensitive) per code applies each. List the codes in charSelectText.

**Ordinal words.** `choose($e.intensity.lower(), "slight", 1, "mild", 2, "moderate", 3, 0) < 3` compares a word scale, for example to raise an entry to a minimum without lowering it.

## Request and commit example

In [recipe-request-commit.json](../examples/recipe-request-commit.json), the AI records the current requested event and turn stamp. The first trigger resets the receipt, not the unconsumed request. A later trigger checks freshness, then checks funds/ownership and commits a purchase or rejection. A following effect displays the receipt and clears the request; the receipt remains for next-turn continuity. Narration describes an attempt until the committed result is available. A freshness stamp prevents stale reuse, not incorrect classification. This pattern is optional: native choices, thresholds and timed effects do not need an AI request layer.

The [example index](../examples/index.json) records each complete world's purpose and verification scope. [Payloads.md](../examples/Payloads.md) supplies smaller native shapes. Remap IDs when combining worlds and validate the result. Select examples by feature rather than imposing the showcase's architecture on every world.

===== BEGIN FILE: reference/Default-Evaluation.txt =====
Firstly, if I have made any assertions in my description, evaluate whether you judge that they are reasonable and likely. If they are nonsensical, incoherent or blatantly impossible, the action should be DENIED. On the other hand, if the action is trivial and there is nothing to complicate it, skip the evaluation entirely and deem the action a SUCCESS. Don't overthink this! If the action doesn't warrant further evaluation, make a judgement and move on.

Assuming the action is not a trivial SUCCESS or DENIED, I would like you to evaluate what skill would be needed to succeed in this action, and how difficult it would be to do so. Please indicate which skill which is needed to succeed.
If applicable use this list: (<<skill_list>>) and a difficulty (from the list: <<difficulty_list>>). For example: {<<skill_example>>: <<difficulty_example>>}. Consider the difficulties carefully, evaluating what might be feasible in the situation. Identifying the skill and difficulty is very important!

Then, evaluate whether I would succeed in the action. To evaluate, consider my proficiency in various skills using either (<<skills_and_levels>>) or logical application of other skills. By comparing these difficulties to the stated difficulty of the action, you should conclusively decide whether the action is a SUCCESS or a FAILURE.

Base your decision on player character description, past, rest of the instructions and common sense - for example, if my skill is low but you know that I am able to perform the given action due to past events, treat me as more competent in this case. Again, don't overthink this - just make a sensible judgement given the information available to you and based on what makes sense for the story.

In some situations, you may wish to evaluate the action as a PARTIAL_SUCCESS instead - this is for something where my abilities are sufficient that I don't simply fail completely (or where failing completely would make for a boring story) but I also don't success. Either I achieve some but not all of what I wanted, I fail but have some silver lining, or I succeed but there are drawbacks or side-effects rather than a "clean" success.

In total, your evaluation should consist of an extremely brief discussion of your thinking (just a single sentence), a skill and difficulty, and then either DENIED, SUCCESS, FAILURE, or PARTIAL_SUCCESS (along with any clarifying remarks).

That's all you need to do for the evaluation, which should be returned in the 'evaluation' argument. Remember to conclude with one of DENIED, SUCCESS, FAILURE, or PARTIAL_SUCCESS.

# Notable findings

The Infinite Worlds behavior most likely to surprise an author or break a world, in plain language. Each entry says what happens and what to do. Details and evidence labels are in [Verified behavior](Verified-Behavior.md). The last section lists what remains unknown. Use this page as a checklist when reviewing or debugging a world.

## Triggers

1. **A trigger with no conditions never fires on its own.** It is a saved trigger for Fire random trigger, not an "always" trigger. Start-of-game triggers are the exception: they fire at startup. With Start on, the editor drops its "so it will never fire" warning even when Mid-game and Repeat are also on, but firing on later turns is not established. For an every-turn trigger, add an always-true condition such as `$game.turn_number >= 0`.
2. **Repeat means every eligible turn.** "HP below 5" with Allow triggering multiple times fires every turn HP stays low. Add a state guard for one-time effects.
3. **Start + Mid-game + Repeat runs twice before the player acts:** once before the opening and again on turn 1. Guard counters and rewards.
4. **Give information to AI does nothing on a Start-enabled trigger**, even on its later mid-game activations. Use background, an instruction block or a separate ordinary trigger.
5. **Effects available depend on Start mode.** Background, first-action and Other Character changes are Start-only; Fire random trigger does not dispatch with Start on.
6. **"Fired" does not mean "succeeded".** A script that errors rolls back only its own writes, but its trigger still counts as fired, uses up a one-shot and satisfies prerequisites. Set a completion flag inside the script that does the work.
7. **Order in the trigger list is execution order.** Later triggers see earlier writes; a this-turn prerequisite only sees producers above it. Reversing two triggers can delay an effect by a turn.
8. **Two native number changes to one tracker in one trigger overwrite each other.** Add 2 then add 3 ends at 3. Use one script for dependent arithmetic.
9. **Fire random trigger skips the target's conditions** but will not rerun a one-shot that already fired. Put required checks inside the target's effects.
10. **Thresholds need inequalities.** A countdown that jumps from 1 to -2 never equals 0. Use `<=`/`>=` and consume each crossing once.
11. **Effects run after the narration is written.** A trigger cannot change the scene that caused it. If a rule must shape that scene, put it in active instructions beforehand.
12. **When two guidance effects conflict, the first tends to win.** Generate one coherent outcome instead of competing directives.

## Scenarios

13. **Scenario text must match the registry exactly**: case, spaces and punctuation. A mismatch keeps the text in JSON but the selector shows "Select a situation" and the trigger never fires.
14. **A Scenario fires only when the event really happens in the narration.** The narrator can refuse or alter a requested action.
15. **Dynamic Scenario text (`<<$slot>>`) is unreliable** beyond a single slot: multi-slot, cyclic and parallel setups silently fail. Use literal Scenarios plus state conditions.
16. **The editor's ten-Scenario limit is an editor limit.** Imported worlds with twelve or more work.

## Import and editing

17. **Tracker IDs with punctuation, spaces or accents are replaced on import, and triggers still point at the old ID.** Use letters and digits only for tracker IDs.
18. **Some missing fields break things silently.** A condition without `textComparison` is dropped. A value effect without `replaceWith` was linked to the game failing at the opening. A tracker without `description` makes the editor rebuild fail after a "success" message.
19. **Legacy array-style prerequisites and blank script conditions are dropped on import.** The trigger loses that gate, or never fires if it was the only one.
20. **Import is saved immediately**, even if you later click Discard changes. Keep a backup. Wait for the editor to rebuild before refreshing the raw JSON.
21. **A running game is a separate copy.** Editing the world, its starting values or its characters does not change a game in progress. Edit current tracker values in Storyteller mode, or start a new game.
22. **Renaming a tracker's display Name with Ignore keeps its script handle.** Scripts keep working.

## Trackers and PawScript

23. **Hidden and extra-hidden trackers are not secret.** The storyteller and any Storyteller-mode player can see them; extra-hidden only filters one display.
24. **Hidden and player-only trackers cannot auto-update.** Import turns automatic updating off for them.
25. **Enforce format does not reject bad data** written by scripts or by hand. Validate shape and values in scripts before accepting them.
26. **Random expressions disagree with each other.** Two `random()` calls, even in one block, give different results. Store one roll in a tracker when several things must agree.
27. **Text installed by a block effect freezes its values.** Use a deferred `<=...=>` reference to keep a value live; `<<=...=>>` is inert text, although the editor highlights it as code and shows `<=...=>` as plain text. Saving the tracker editor by hand freezes any tracker holding `<<...>>` at its displayed value.
28. **An unclosed `<<` can break the next instruction block too.** Check delimiters across neighboring blocks.
29. **YAML types are loose.** `yes`/`no` are text, `"007"` counts as 7 in arithmetic, Boolean results are stored as quoted text, and appending to a list allows duplicates.
30. **Reading a missing path stops a script.** Guard with `.exists()` first (`and`/`or` short-circuit), or use `try(...)`, `first_available(...)` or `item(key, fallback)`.
31. **Script variables (`set $x`) vanish between Run Script effects** in the same trigger. Keep dependent work in one script.
32. **Skill effects cap rather than add.** Raising a skill by 2 then by 1, each capped at 4, ends at 4. Skills not raised default to level 3; set every level explicitly.
33. **The sandbox opened from a single-line field is a one-line expression box.** A multi-line paste there is refused and does nothing; its Text tab gives a multi-line box for `<<expression>>` text. To test a multi-line script, open the sandbox from the Paw icon beside a Run Script field, which the world editor always shows. Nothing changed in the sandbox goes back to the editor or game.

## Characters, knowledge and memory

34. **Only the Summary is guaranteed early.** Character detail arrives after a name or location mention, and even then often fails to surface; the narrator invents a substitute that history then repeats. Put must-know facts in the Summary or always-on text and repeat them in detail.
35. **Keyword and character cards cannot activate on the opening turn** without prior context. Put opening facts in firstInput or always-on instructions.
36. **Keyword blocks match whole words, any case, and stay active for the matching turn plus three.** Substrings and plurals do not match.
37. **NPCs get knowledge wrong.** They deny facts they were just told, credit the wrong source, or know secrets they should not. Secret Info can contradict the narration. Anti-omniscience instructions alone do not fix this.
38. **Once a secret is narrated it stays in the story**, even if you remove the block that revealed it.
39. **Memory compression runs after turn 8 and every six turns after that** (after turns 8, 14, 20, …). So when a turn is written, short-term memory holds the 2–7 most recent turns uncompressed; everything older is in the summary, whose contents are hidden. Keep facts that must persist in trackers.
40. **A player character with the same name as an Other Character can draw on that card.** Unchosen player options are not NPCs unless added as Other Characters.

## Narration, images and play

41. **Shorten narration from authorStyle, not descriptionRequest.** A word-and-paragraph cap at the end of authorStyle held output near the stated number (often 10–20% over) even on story-beat turns; the same cap in descriptionRequest or an always-on block broke on those turns. Making narration longer is not established.
42. **Raw HTML renders as literal text.** Use ordinary Markdown.
43. **Short avoid-lists help, long ones backfire** on weaker models by priming the banned phrases.
44. **Image style uses the start/end prompt fields.** The old illustrationStyle priority fields have no current controls and lost to the start/end prompts in testing. Saving Illustration details generates a new image (about 4 credits).
45. **Ends game with continuation allowed offers Continue game at no cost.** Without it, the action box disappears but history and regeneration remain.
46. **Reloading during generation can lose the turn and keep the charge.** Check the export's turn count before resubmitting.
47. **Cost per turn grows with story length** and depends heavily on the model; see [Current-AI-Profiles.json](Current-AI-Profiles.json).
48. **One input form per turn is safest.** A turn that combined a malformed-candidate input with a Request Input form showed narration without the forms and was not saved, though it was charged. Two plain Request Input forms from separate triggers on one turn did work.
49. **A tracker-detail change in the same trigger as Request Input is silently lost.** Modify tracked item details (for example switching automatic updating on) does nothing when its trigger also asks for input, while messages and scripts in that trigger still run. Put the change in its own trigger with the same condition. Switching automatic updating on and off otherwise works, from the next turn.
50. **An AI-written buffer whose whole value is a list loses updates.** Root it in a record (`entries: []`) and have scripts read and clear `.entries`. Ask for complete entries of changed characters, not "only changed fields": once the buffer is cleared, a field patch has nothing to apply to. "Append-only" wording does not rescue a list root.
51. **A record-rooted buffer can jam on one nested row.** If the AI writes rows as a list inside `entries`, a merge gated on `.entries.any(name.exists())` never fires again and every later update piles up. Gate on a non-empty inbox and drop or unwrap non-record items.
52. **A block reinstalled every turn lags behind triggers below it.** Its `<<...>>` values freeze when its trigger runs. Order the triggers that compute those values above it, or write `<=...=>`.
53. **`$game.ai_model` is the display name, and text `=` is case-sensitive.** On Dolphin, `= "Dolphin"` is true and `= "dolphin"` false.
54. **Some native fields take live expressions.** A tracker condition's required value can be `$variable`, a random chance can be an expression, and numeric add/subtract accepts dice text such as `2d3`; each is evaluated every time. Templates in a tracker's update instructions are also evaluated live.

## Still unknown

Platform behavior that has not been verified, by area, with what to do meanwhile. Elsewhere the kit states only what is established; do not turn any of these into an invented rule.

| Area | Still unknown | What to do meanwhile |
| --- | --- | --- |
| Prompt construction | Full historical storyteller/specialist prompts, hidden wrappers, exact inclusion and timing | Put essential facts in fields known to reach the storyteller (background, firstInput, instructions, always-on blocks); treat UI visibility as display, not proof of what the AI receives |
| Empty-condition triggers | Whether a Start+Mid+Repeat trigger with no conditions fires on ordinary turns | Give every-turn triggers an always-true condition such as `$game.turn_number >= 0` |
| Scenarios | Why dynamic multi-slot, cyclic and parallel arrangements fail; any runtime maximum | Use literal Scenarios with explicit state gates ([Triggers](Triggers.md#scenarios)) |
| NPCs and knowledge | Live character records, identity merging, mutation and retrieval routing; why name-only mentions often fail to surface Character detail | Put facts that must surface in the Summary or always-on text; author relationships and knowledge explicitly; correct an invented detail early by editing the turn |
| Import normalization | Internal failure stages; ID rules for every entity type; why an omitted replaceWith broke the opening | Use ASCII alphanumeric tracker IDs; always serialize description and replaceWith; re-export after import and compare with tools/import_audit.py |
| Visibility | Whether visibility changes what the AI receives | Do not rely on visibility to keep information from the storyteller |
| Interpolation | Timing in destination fields other than those tested; full specialist inputs | Use the template probe example before relying on a new field ([Runtime](Runtime.md#template-interpolation-runtime)) |
| Randomness and selectors | Exact evaluation counts; whether unselected library text is excluded from context | Store a shared roll in a tracker when several consumers must agree |
| AI tracker dependencies | How generation is staged internally | Stage prior-turn values explicitly when a rule depends on them |
| Format and YAML | Complete grammar, XML mutation, strict typing, hidden AI repair | Validate shape and meaning in scripts before accepting state |
| Legacy list context | A supported List Update target/value context in the current editor | Use for-each loops and collection methods instead of `current()` |
| Memory | Summary contents and how they weigh against persistent context | Use summaryRequest and trackers for facts that must persist |
| Length | A lengthening recipe; the authorStyle cap on models other than Dolphin | Put length rules in authorStyle; promise a ceiling near the number, not an exact length |
| Images and video | Full image prompt and cache, precedence, internal macros, video runtime | Author with current style controls and preserve imported legacy fields; avoid depending on video until checked |
| Limits and permissions | Maximum field, loop or trigger sizes; account-role permission matrix | Treat observed sizes as working examples |
| Recovery and forms | Server-side cause of a lost-but-charged turn; automated recovery | After an interruption, inspect retained history and the export's turn count before resubmitting; prefer one input form per turn |

The schema and validator are a partial compatibility profile, not a statement of every importer-required field or future vocabulary.

# Editor and UI reference

Current through 2026-10-26. This covers observed authoring, play and troubleshooting surfaces, not every menu. [DOCUMENTED] means editor guidance; [RUNTIME] means observed behavior. Unlisted fields are not necessarily unsupported.

## Terminology for users

Use tracker and trigger **Names**, not IDs, unless the user requests IDs. Distinguish duplicate Names by purpose/editor location. Keep IDs for internal wiring and preserve them during edits. Use variable handles when explaining code. Say **Scenarios**, never ambiguous Conditions, for reusable narrative situations. Call a character's one_liner **Summary**.

| User/editor term | JSON mapping or distinction |
| --- | --- |
| Tracker Name | `trackedItems[].name`; not `id` or `variableName` |
| Trigger Name | `triggerEvents[].name`; not `id` |
| Scenarios; Triggering situation / Manage Situations in the selector | Root `conditions`; referenced by `triggerOnEvent` |
| Trigger conditions | `triggerConditions`; gates within a trigger |
| Summary; Brief summary in Other Characters | `one_liner` (the only spelling in exports) |
| Character detail | `detail` |
| Extra instruction blocks | `instructionBlocks`; explain before abbreviating EIB |
| Give information to AI | `effectGiveInfo` |
| Tell the AI what should happen next turn | `effectTellAIWhatToDo`; distinct from Give information |
| Change other characters / Change other character data | `effectChangeOtherCharacters`; picker/panel labels differ |
| Trigger at start of game / Or mid-game | `triggerOnStartOfGame` / `triggerMidGame` |
| Allow triggering multiple times | `canTriggerMoreThanOnce` |
| Hide this item even in Storyteller Mode / Extra-hidden | `hidden_boring` or `ai_only_boring`; display filtering |
| Change starting values of Tracked Items (if applicable) | `allowChangeCharacterItemValues`; character-selection permission |
| Custom Evaluation / Description / Summarisation | `evaluationRequest` / `descriptionRequest` / `summaryRequest` |

## Import, export and preserving work

1. Open **Show optional features > Misc advanced features > Show raw JSON**.
2. To export editor changes, **Refresh raw JSON** then copy/export the whole value. The box does not track native field edits automatically.
3. To import, replace the whole raw value and select **Import JSON to world**. Accept the intended overwrite, acknowledge success, and wait for the editor to rebuild itself.
4. After rebuilding, reopen optional/raw sections and refresh/export if needed. Do not refresh the old editor immediately after import or refresh a pasted source you intend to import.

Opening a world in the editor advances its version in the export (for example 1.01 to 1.02), even if changes are then discarded.

[RUNTIME] Import can persist independently of a later Discard changes action. Keep a backup.

**Before import**

- Serialize the complete world as JSON ending at its final closing brace, without a trailing newline. Do not paste Markdown fences.
- Run the validator on that exact file. Resolve missing or duplicate IDs and mismatched target references.
- Review native YAML paths against the tracker's declared initial structure and intended operation. The editor accepts unchecked paths without warning: removing a nonexistent key or appending to a numeric path may be syntactically valid but semantically wrong. Review script references separately; structural validation does not execute PawScript or prove its paths exist.
- Give every tracker a `description` (it may be empty). Without it, import reports success and then the editor rebuild fails with a KeyError.
- Convert legacy bare-array prerequisites/blockers and blank PawScript conditions to native object shape. Import drops them, and the trigger silently loses that gate.

**After import**

A round trip of well-formed native JSON is byte-identical, so any change after import points at a normalization (ID reminting, dropped gates, scope repair, registry population). Tracker IDs can be regenerated without remapping their references. Save and inspect affected target dropdowns and Scenario bindings, since preserved text can be unbound. An invalid-value target is a binding failure even if the original JSON had consistent references. Export the imported world and validate that export when diagnosing discrepancies; keep the untouched source so source and imported IDs can be compared with `tools/import_audit.py` ([tools/Usage.md](../tools/Usage.md)).

For a native input, confirm the current target value after submitting an answer. Correctly bound single-answer Choice and Request Input effects update immediately, and subsequent ordered triggers can read the result in the same turn. Their follow-up messages can render above the question/answer receipt. The live-world editor's initialValue remains configuration, not the current runtime value.

**Live copies**

Base worlds and live games are separate copies. Starting play creates a live copy; editing the base, its starting values or its characters does not update an existing playthrough, and already-fired effects are not retroactively rewritten. Use Save as new world, or export the live JSON and import it over the intended base, to reuse live-world edits in future games. Image-style changes can require save/reload before their export reflects the editor.

[RUNTIME] Narration can stream before background work finishes. Following interruption, inspect retained state and controls before submitting again; a temporary turn number is not a saved-turn guarantee.

## Triggers and Scenarios

An ordinary trigger with no conditions says it will never fire. With Trigger at start of game checked, the condition box reads only "(No conditions added to this block yet)", with or without Or mid-game and Allow triggering multiple times; the missing warning reflects startup firing and does not show that the trigger runs on later turns. This is not unconditional execution; Start-gated triggers and explicit random dispatch differ. Empty effects do no work but eligible triggers can still record firing.

Start mode changes the picker and compatibility warnings. Start-only disables Repeat in the editor; Or mid-game enables it. **Use advanced logic** adds Add logic block; new blocks default to Or. Switching a condition between types keeps hidden fields: Turn number to Player action keeps the old inequality and clears the required value. Trigger history lists Start-pass firings as turn 0. Stored unsupported combinations may survive import while effects are ignored. Read the [trigger capability catalog](Trigger-Catalog.md) before declaring an operation unavailable.

A mismatched Scenario shows **Select a situation** while the JSON keeps its string. The Situations manager's Add control stops at ten entries. Binding rules and limits are in [Triggers.md](Triggers.md#scenarios).

## Trackers, visibility and customization

**Menu > Settings > Storyteller mode** toggles the mode, rather than opening a status dialog; enabling asks for confirmation. **Menu > Settings > World debug tools** contains Include Extra-hidden. Reopen panels after changing this setting if they still show old content.

| Surface | Observed behavior |
| --- | --- |
| Hidden Tracked Items, Storyteller on, Include Extra-hidden on | Extra-hidden values displayed |
| Hidden Tracked Items, Storyteller on, override off | Extra-hidden omitted; ordinary hidden values remain |
| Tracker editing dialog, Storyteller on, override off | Extra-hidden still visible/editable |
| Storyteller off | Player-visible values remain; live tracker editing control unavailable in the observed UI |

Neither hidden nor extra-hidden protects information from Storyteller inspection. Visibility and automatic-update rules are in [Trackers.md](Trackers.md).

For per-character values, select **Initial value depends on which character the player chooses** under Tracked items, then edit under **Player character options > [Name]**. Player-selected preferences can appear on the character card and in Customize Character. Opening the customizer can reset card selections; check final values there. With starting-value permission on, Customize Character shows only character-scoped or player-chosen trackers, not same-for-everyone ones. Starting-value permission is not general in-play edit permission.

Rename warnings offer **Update** and **Ignore** for a variable-name mismatch; Ignore preserves the handle and ID. When acknowledgement is needed is covered in [Trackers.md](Trackers.md). Initial-value changes do not migrate running state; edit current tracker values for that.

## Play, debug and live design

The database icon opens trackers; the nearby edit control edits their values. The pencil opens action/outcome editing and **View/edit world design**. Regenerate turn opens modification of an existing turn. These operations have different purposes.

The bug icon (beside the tracked-items icon) opens debug, which needs Storyteller mode. It shows the current turn's active instruction blocks including trigger updates, the triggers fired this turn, all-trigger history with first/last turn and counts, model thinking when available, Evaluation, and PawScript conditions, execution results, output, warnings and errors (including automatic tracker format repair and failed path updates). **Active instructions** is live rendered state, including post-narration trigger updates and live edits, not the full historical prompt or the exact context the already-generated narration used. The fired-trigger list is not always exhaustive; inspect detailed history and actual state.

The live-design notice warns that Player/Other Character changes do not affect the current playthrough (see Live copies above). Runtime block replacements and tracker changes can leave original content/initial values in design exports; those exports show configuration, not the current live state.

Story exports offer a turn range and optional background, character, secrets, trackers and hidden trackers, with text/PDF/image options. Select the relevant options. Secret Info is generated narrative data, not an authoritative character database. No live character-database or complete prompt viewer is available through these surfaces.

[RUNTIME] Some turn inputs are not kept anywhere you can see later (observed in play, not a controlled test). For past turns, the options the player did not pick cannot be viewed: that is two of the three, or all three when a custom action was typed instead. The text typed into the Storyteller guidance box is not shown either, and nothing marks that a turn used it. If a test or a design review needs these, write them down at the time.

An unchecked **Hide skill system** option may omit `hideSkillSystem` from the editor export. This is normal visible-skills state, not a missing setting to repair. Generated JSON may explicitly use `false`.

## PawScript sandbox

The sandbox (PawScript Expression Editor) runs a script or expression against editable tracker data. Nothing changed in it goes back to the editor or game; copy anything worth keeping.

| Entry point | When it is available | Tracker data it starts with |
| --- | --- | --- |
| World editor: Paw icon beside a Run Script effect's script field | Always | All base trackers |
| World editor: Paw icon beside other PawScript-capable fields | When **Show optional features > Misc advanced features > Show the PawScript Expression Editor button next to each expression field** is enabled for that world (`showPawScriptButtons: true`) | All base trackers |
| In play: **View/edit world design** | Same Paw icons as the world editor | The game state of that turn |
| In play: debug **PawScript > Open in Sandbox** | For a script that has run in this game; with the expression-editor option enabled, evaluated conditions also get an entry. The play screen has no other sandbox button | The game state of the turn it ran |

From the world editor, a tracker with a fixed initial value shows that value; one with no initial value, or a player-chosen or character-dependent one, shows 0 or empty. With the option enabled, Paw icons were observed beside trigger conditions and tracker description and update instructions, but not beside initial value, authorStyle, specialist instructions, main or keyword instruction blocks, background, first action or objective.

The sandbox matches the field it was opened from. A script field opens a multi-line **Your script** box with **Run script**. A single-line field, such as a trigger condition, opens a one-line **Your expression** box in **Expression** mode with **Evaluate**; a multi-line paste there is refused and does nothing. Its **Text** tab switches to a multi-line box that evaluates text containing `<<expressions>>`. The standalone sandbox (Menu > PawScript Expression Sandbox) leaves `<=...=>` unchanged and rejects `<<=...=>>`; test deferred text in play. To test a multi-line script, open the sandbox from a Run Script field.

Trackers can be added, edited and deleted in the sandbox, and runs use those values. From debug, the header names the script and says what it changed when it ran in the game. **Turn data** lists trackers plus the `$player` and `$game` roots (`$game` has seven keys, including turn_number, ai_model and skill_list); **Legacy turn data** holds older flat variables. In a short-circuited And/Or group, debug lists only the deciding condition. Sandbox data can differ from current manually edited values. A run displays a result/diff; **Update Game** is separate. A collapsed summary can misrepresent nested structure; inspect actual values or supported reads.

## Credits and cost

The header shows the credit balance and the remaining daily free turns (3 per day observed). **Credits > Credit activity >** a turn **> Cost breakdown** splits Inputs and Outputs into instructions, trackers, STM (recent story), LTM (summaries) and other; thinking models add an output category. LTM first appears after the first summary compression, as STM drops. Breakdown values are rounded decimals: the list can differ from the balance change by a credit.

Cost per turn depends on the model (the picker shows a typical range; see [Current-AI-Profiles.json](Current-AI-Profiles.json)) and rises with story length: Lynx turns went from about 20 to about 40 credits over nine turns. Saving Illustration details generates an image for about 4 credits. A failed opening is refunded. Continue game after an ending costs nothing. A turn interrupted by reload can stay charged without being kept. For per-model rates and how to estimate a world's cost, see [Estimating cost](Cost.md).

## Characters, images and models

Other Characters separates Summary, Character detail, narrative appearance and image appearance/clothing. Help says Summary is available before full detail, with detail available from the turn after name/location mention. Repeat essential Summary facts in detail. Location guidance asks for no more than two words; Full list of names accepts comma-separated variants. Unchosen player options are not automatically NPCs: add Other Characters when they should exist in the story.

The illustration wrench opens **Illustration details**. Character fields: Appearance, Clothing, Expression/position, Setting. Scenery fields: Appearance, Setting. **Edit details > Save changes** immediately generates an image; it is not a text-only save. **Settings > Illustration options** supports one, two or three alternatives; automatic generation is separate.

Image style has a Model and Character/Scenery start/end prompts, mapped to `imageStyleCharacterPre/Post` and `imageStyleNonCharacterPre/Post`. Retained `illustrationStyle*` fields are not current controls. Full image prompts and cache identities are hidden.

**Misc advanced features > Enable AI-specific instruction blocks** exposes block model choices mapped to `selectedAIProfiles`. All-model blocks remain active during model switches; filtered blocks follow the selected model. Availability changes; imported unfamiliar IDs are not automatically invalid.

## Specialist instructions, forms and PawScript cues

[DOCUMENTED] The default Description instructions ask for several paragraphs; to shorten narration, put the cap in authorStyle (see [Runtime](Runtime.md#specialist-requests-and-runtime-outputs)). Video help describes `$videoDuration` and `$videoStyle` in video context (see below).

The expression-editor option shows a Paw icon beside some PawScript-capable fields (see [PawScript sandbox](#pawscript-sandbox)). A field without an icon can still take expressions: YAML Set a value supports template expressions according to help despite having no icon.

Editor syntax highlighting misleads for deferred references. In instruction blocks and tracker descriptions it colors `<<=...=>>` as PawScript and shows the working `<=...=>` as plain text, while initial values show both as plain text. At runtime it is the other way round: `<=...=>` is evaluated and `<<=...=>>` stays literal. If a user cites the highlighting, explain that it is wrong for this syntax ([PawScript.md](PawScript.md)).

Present choice enforces required selection and configured multiple-selection bounds. Required Request Input can leave Confirm enabled while empty, then reject submission with **Please enter a response**. Optional blank input clears its target. Single/multiline fields show counters of 600/3000 respectively, not universal tracker limits. Newline-delimited multiple selections remain text, not automatically a YAML list.

Trigger-provided next-turn guidance can disable the Storyteller guidance box while leaving ordinary action input usable. Ends game can offer **Continue game**, depending on its flag. Without continuation, history and regeneration can remain available.

# Estimating cost

How much a turn costs, how it differs by Storyteller model, why two players of the same world can pay very different amounts, and how to make a rough estimate before anyone plays. Credit activity shows the real bill: see [Editor-UI](Editor-UI.md#credits-and-cost) for the cost breakdown and the [IW Cost Exporter](https://iw-builder.github.io/cost/) to download your history.

## What a turn is made of

Each turn is billed in two halves. **Input** is everything IW sends the model: its own prompt, the world's standing text, recent story and summaries. **Output** is what the model writes: the narration, Secret Info, evaluation, tracker updates and, on thinking models, its thinking.

**Standing text** is the part the world author controls. It is billed on every turn it is present, at roughly the same rate per character for each model (K in the table below):

- main instructions, authorStyle and every always-on instruction block, plus any block a trigger has installed;
- AI-visible tracker definitions (name, description, update instructions, format), from turn 1, whether or not the AI updates that tracker [RUNTIME, Dolphin: about 1.7 credits per 1k characters];
- AI-visible tracker values;
- lore entries and NPC cards while they are active (assumed to bill at about the instructions rate; not measured directly).

These cost nothing per turn: hidden (script-only) trackers, triggers and PawScript, and Request Input form text after it has been shown. A long descriptionRequest or evaluationRequest is not billed in full either [RUNTIME: 16k characters added about 3–4 credits a turn]; what it really costs is the narration it causes.

**Narration** is billed as output on the turn it is written, then again as recent story (input) on later turns until IW compresses it into a summary. It is the part players are paying for, so it is not a sensible place to save: a world that cut its narration by about 80% saved only about 10% a turn. Overhead (standing text, extra turns, unused lore) is where savings come from.

| Puma | 41 | 58 | 0.82 | 1.42 | 303 | 3.0 | – |
| Grimalkin | 48 | 72 | 1.0 | 1.75 | 325 | 3.4 | – |

| Smilodon-thinking | 74 | 105 | 1.5 | 1.81 | 347 | 5.5 | 14 (13–15) |

Columns:

- **Small world, per turn:** turn 2 of a tiny world (1.2k characters of instructions, no trackers, lore, NPCs or blocks). This is about the least a turn costs on that model after the opening.
- **With 10k more instructions:** the same world on turns 3–4, after 10k characters of plain text were added to the main instructions.
- **× Dolphin:** each model's cost relative to Dolphin. Where two numbers are given, the first is for the larger world: thinking costs about the same whatever the world's size, so those models' lead narrows as the world grows.
- **K:** the extra credits a turn for each 1,000 characters of standing text. Thinking variants bill instructions like their base model.
- **Narration, words per turn:** how much each model writes when nothing in the world asks for a length. A world that sets a length changes this.
- **Credits per 100 words of narration:** the output cost of the narration alone, on the turn it is written.
- **Thinking:** the model's thinking output, mean and range per turn. It varies a lot from turn to turn and is most of the cost on Leopard-2 (about two-thirds) and Leopard.

Turns took about 35–70 seconds on the models that were timed (Dolphin, Massivecat, Massivecat-thinking, Leopard, Leopard-2). Caracal took 5–8 minutes a turn. Wampus and Leopard-2 are under "Show niche models" in the model picker. Wildcat and the experimental Smilodon-2 models were not measured. For the model behind each name and the picker's typical range, see [Current-AI-Profiles.json](Current-AI-Profiles.json).

### Where these numbers come from

[RUNTIME] One small sample world per model, one game each, played on 2026-10-30 with the same four fixed inputs. The averages come from **three turns** per model (turns 2–4; the opening is left out), and K rests on two of those turns. So treat every figure as a rough guide, not a price list: a second game, another world or another day could move a model's numbers by tens of percent, and thinking costs could move more.

Two independent checks agree with it. Dolphin's and Massivecat's K match separate measurements on other worlds (1.6 and 2.7). On a long adventure world measured over 14 turns per model, Puma cost 0.85×, Smilodon 1.5× and Massivecat 2.0× Dolphin, close to the ratios above.

## Why the same world costs different players different amounts

The world sets the starting point; the player decides most of the rest.

- **How many turns they take.** This matters most, because a game's total is turns × cost per turn. A player who talks through every scene, explores side paths or makes small moves may take several times as many turns as one who pushes the story along. One long adventure world took about 125 turns to finish, at about 100 credits a turn on Dolphin.
- **Where they go and who they talk about.** Lore entries and NPC cards load when their keywords appear in the story and stay active for a few turns, so a player in a lore-heavy city or a crowded court pays more per turn than one on an empty road. On one large world, active lore cost 17–29 credits a turn on Dolphin.
- **Which route or phase they reach.** Worlds that install blocks or show trackers for a route make that route cost more or less than others. Story luck can change the route: in two otherwise identical games, one player was captured a turn earlier and moved to a different route.
- **How long the game has run.** Recent story is re-sent every turn, so turns get dearer as the game goes on, until IW compresses older story into a summary (after turn 8, then every six turns; see [Trackers](Trackers.md#memory-continuity-and-context-cost)). After that the cost levels off, cycling as short-term memory grows from 2 to 7 turns between compressions. A small world can double between its first turns and turn 8; a large one rises less in proportion (about 30% over its first six turns on one 50k-character world).
- **How much the narration runs.** The same model on the same world wrote 451 to 638 words a turn. Big scenes, dialogue-heavy turns and players who ask for detail produce longer replies, which cost more now and again in recent story later.
- **Which model they pick.** Players can switch model mid-game. The table above is the biggest single multiplier.
- **Free turns.** IW gives 3 free turns a day, shared across the whole account rather than per world or per model.

## Rough estimates

### Per turn

1. **Start from the model's small-world turn** in the table.
2. **Add standing text:** K × the thousands of characters of standing text the world sends each turn (instructions, authorStyle, always-on blocks, AI-visible tracker definitions and values, typical active lore). Subtract about 1k for the text the small world already had.
3. **Allow for memory:** add about 30% for a large world, and up to double for a small one, from about turn 8.
4. **Adjust for narration** if the world asks for much more or less than the model's natural length: (words asked − words in the table) ÷ 100 × the narration rate. This is the smallest of the four.

Example (an estimate, not a measurement): a world with 18k characters of standing text, played on Smilodon. 70 + 1.99 × 17 ≈ 104 credits a turn early on, about 115–140 once memory builds up, so about 4,500–5,500 credits for a 40-turn game.

### Broad situations on Dolphin

Multiply by the × Dolphin column for another model. For a heavy world on a thinking model, use the first (smaller) multiplier.

| Situation | Standing text per turn | Dolphin, per turn | Basis |
| --- | --- | --- | --- |
| Small, simple world | under 5k characters | about 40–75 | Measured: 49 on turn 2 of the sample world, rising with memory |
| Mid-sized world | 10–25k characters | about 65–120 | Estimate from the method above |
| Large world with plenty of lore | about 50k characters, plus 15–30 credits of active lore | about 150–210 | Measured on one community world: 152 on turn 1, about 200 a turn by turns 4–6 |
| Long campaign | about 33k characters | about 100 average | Measured on one long adventure world: about 13,000 credits for a full game of about 125 turns, about twice that on Massivecat |

For a whole game, multiply the per-turn estimate by the number of turns you expect, and give a range: players' turn counts vary more than the per-turn cost does.

### Checking an estimate

Play a few turns, then open Credit activity and read the breakdown. If a bucket is far above your estimate, it points to the cause: Instructions for always-on text, Tracked Items for tracker definitions, keyword blocks for lore that is loading more often than intended (an entry keyed on a common word loads almost every turn). On one large world, trimming those three cut the cost of a turn by about 20% without changing the narration: instructions fell 38%, lore 70% and tracker definitions 28%.

See [Trackers](Trackers.md#memory-continuity-and-context-cost) for keeping tracker text lean, and [library/Integration.md](../library/Integration.md) for the size of each library module.

## Triggers and Scenarios

- [RUNTIME] Ordinary triggers with no conditions never fire automatically. Start-gated empty-condition triggers fire at startup. [UNKNOWN] Whether an empty-condition Start+Mid+Repeat trigger also fires on ordinary turns; give every-turn triggers an always-true condition. An eligible trigger with no effects still records firing and can satisfy prerequisites.
- [RUNTIME] Fire random trigger bypasses target conditions, including empty or false conditions. Consumed one-shot targets do not execute again, even on later turns; nested dispatch works. Editor help's "already fired this turn" wording understates this. Duplicate-pool weighting is unresolved.
- [RUNTIME] A failing Run Script rolls back that script's writes. Separate earlier and later effects can commit. The trigger still counts as fired and consumes one-shot eligibility. Prerequisites mean firing, not successful completion.
- [RUNTIME] This-turn prerequisites/blockers see a producer only when it is earlier in triggerEvents. History prerequisites see a later-ordered producer from the next turn. Current-turn gates reset each turn.
- [PATTERN] Set completion flags only after successful work. Order producers before consumers when same-turn consumption is intended. Later triggers see earlier committed writes; reversing order defers dependent work by a turn.
- [RUNTIME] Start+Mid+Repeat executes before the opening and again during ordinary play; trigger history records Start-pass firings as turn 0. Repeat does not require a false-to-true condition transition. Start=false makes the stored Mid flag inert.
- [RUNTIME] Give information to AI is ignored with Start enabled, including later Start+Mid activations; the payload is not stripped. It differs from Tell the AI what should happen next turn. Computed information appears in Secret Info.
- [RUNTIME] Background replacement affects startup in Start-only mode. Ordinary background/first-action effects do not rewrite the opening. Start+Mid did not apply background replacement. Fire random trigger dispatches in ordinary mode but not with Start enabled. A trigger firing does not guarantee every stored effect executes.
- [DOCUMENTED] Change first action and Change other characters appear only in the Start picker. Live character-record mutation is not observable.
- [RUNTIME] Scenario binding requires exact registry strings, including case, spaces and punctuation. Preserved JSON can still be unbound. Say Scenarios in prose; the top-level JSON field is `conditions`.
- [RUNTIME] A Scenario fires only when the event actually occurs in the narrated outcome. The narrator can refuse or substitute a requested action, and then the trigger does not fire. An already-satisfied Scenario does not refire on quiet turns.
- [RUNTIME] Add Scenario stops at ten entries in the editor. Imported registries of twelve bound Scenarios persisted through save/reopen and all fired in one turn; a fourteen-entry registry with unused entries and duplicate references also ran.
- [RUNTIME] Dynamic Scenario text works in some single-slot arrangements but fails in multi-slot, cyclic and parallel arrangements where literal Scenarios work. Adding the resolved literal strings to the registry does not repair it. Blank slot text is not reliable deactivation. Prefer literal Scenarios with explicit state gates; [UNKNOWN] the cause.
- [RUNTIME] Independent plot gates can advance together; a shared gate serializes them according to authored policy. Character-specific conditions follow the selected source character, not its customized display name.

## Import and native payloads

- [RUNTIME] Tracker IDs containing underscore, hyphen, plus, slash, dot, space, colon or accented characters are regenerated on import while paired trigger IDs are kept. Tracker references are not remapped, leaving dangling targets. ASCII alphanumeric tracker IDs are preserved. Use them for new trackers; preserve existing valid IDs and audit references.

- [RUNTIME] Missing/blank PawScript condition data and legacy bare-array prerequisite/blocker data are omitted from exports. The open editor can still hold them (opening such a trigger raised a list-index TypeError), but importing that export elsewhere leaves the gate deleted; a trigger left with no conditions shows "will never fire". - [RUNTIME] A numeric or text tracked-item condition with `textComparison` missing or "" is dropped from the export and its trigger stays dormant. - [RUNTIME] Import fills an absent root `conditions` registry from triggerOnEvent references, and normalizes schemaVersion 2.2 to 2.4 with trigger payloads unchanged.
- [RUNTIME] A round trip of well-formed native JSON was byte-identical, including Unicode, multiline text, quotes, backslashes, nulls and empty arrays. Export adds positionInList to Other Characters that lack it.

- [RUNTIME] Item-level and per-character initial-value scopes must agree. Import removes incompatible entries and materializes defaults on a later round trip. Fixed text and array-based choices have different meanings; preserve their native shapes.
- [RUNTIME] The kit's single-choice example keeps its IDs and binding through a fresh import. Inspect native target dropdowns after importing a composed world; schema validation cannot predict importer behavior for every construction.

## Tracker writes and PawScript

- [RUNTIME] Native numeric effects within one trigger overwrite rather than accumulate (starting at 0, add 2 then add 3 ended at 3; starting at 1, set 5 then add 2 ended at 3). Text additions accumulate and text removal removes matching occurrences. Use sequential scripts for dependent arithmetic; sequential script arithmetic accumulates, nested YAML changes preserve unrelated keys, and separate script effects writing different YAML paths preserve both.
- [RUNTIME] Native YAML paths support set/remove/append/adjust, one-based list indexes and interpolation. Record append stores structured data and permits duplicates. Numeric adjustment creates a missing parent/leaf. Whole-value replacement overrides stale path/action fields: interpret `updateMode` first.
- [RUNTIME] Native And/Or and PawScript boolean expressions short-circuit left to right; debug lists only the deciding condition. Place existence guards before dependent reads. No speed benefit has been measured.
- [RUNTIME] Plain nested assignments and runtime-key `.item` writes create paths. Scalar parents reject child writes and roll back the script. Missing-path compound arithmetic (`+=`) fails where assignment succeeds. `try`, `item(key, fallback)` and `if(x.exists(), x, fallback)` handle missing values; `first_available` preserves zero/false and skips empty text.
- [RUNTIME] Locals do not cross Run Script effect boundaries. Executed branch locals and the last binding of a nonempty loop remain available later in that script. Filter bare fields resolve per row. [UNKNOWN] Empty-loop and shadowing behavior.
- [RUNTIME] `current()` is rejected in Run Script even inside `try`; the diagnostic limits it to List Update Target/Value, which the current editor does not expose.
- [RUNTIME] Enforce format is not a write-validation boundary: malformed manual/script values persist. Hidden AI repair is not inspectable. Validate shape and meaning explicitly.
- [RUNTIME] Comparisons and arithmetic coerce YAML values (see [PawScript](PawScript.md#2-values-trackers-and-scope)), and Boolean-expression writes serialize as quoted text. Rendered values and collapsed summaries do not prove types. Duplicate inventory records are not prevented.
- [RUNTIME] The PawScript sandbox matches the field it opens from: a script field gives a multi-line script box; a single-line field gives a one-line expression box that refuses a multi-line paste, with a Text tab for multi-line `<<expression>>` text. Sandbox trackers can be added, edited and deleted, and runs use those values; nothing changed goes back to the editor or game. From the world editor it loads all base trackers, at fixed initial values or 0/empty for unspecified, player-chosen or character-dependent ones; from debug or from View/edit world design during play, it loads the game state of that turn.
- [RUNTIME] A native tracker condition with requiredValue `$limit` is compared against the live value (changing `$limit` changed when it fired). A random-chance condition written as an expression (`$hi`, `$hi - $lo`) is re-evaluated each turn: 0 never fired, 100 always fired, and swapping the values swapped the pattern. Native numeric subtract with newValue `2d3` removed 2–6, varying by turn. One world, Dolphin.
- [RUNTIME] `$game.ai_model` returns the display name (`Dolphin`, `Puma`, `Smilodon` observed); `$game.ai_model = "dolphin"` is false on Dolphin.
- [RUNTIME] `<<...>>` in a tracker's own update instructions is evaluated each turn: the AI wrote the hidden tracker's value, not the template, and followed a change to it from the next turn.
- [RUNTIME] Initial text of 10,014 characters and script-written text of 20,014 characters were retained exactly.
- [PATTERN] Separate generated candidates from accepted state, immutable definitions from mutable state, and archive storage from active context. Validate identity and entry types before freezing; a list-length check is insufficient. Record assignment copies by value, so an archive is unaffected by later edits to the active record.
- [PATTERN] Choose turn time, story time or hybrid clocks intentionally. Detect crossings (`previous < N and now >= N`), consume them, and guard rewards. Use inequalities for thresholds: a countdown of 1 reduced by 3 is -2, so `= 0` is false. Counter order changes the first firing turn. Shared locks favor the first eligible trigger; priority is authored, not automatic.

## Instructions, visibility and memory

- [RUNTIME] Modify tracked item details with overrideVisibility accepts everyone, player_only, ai_only, hidden, ai_only_boring and hidden_boring and applies the live player-visible/hidden grouping. Live-design exports can retain the original visibility.
- [RUNTIME] Modify tracked item details switches automatic updating on and off at runtime, repeatedly, from the next turn (triggers run after the AI's tracker update in a turn). Re-sending update instructions is unnecessary. In the same trigger as a Request Input effect the change is lost (three trackers across two worlds); in a separate trigger on the same turn it works. Show Message and Run Script effects in that trigger are unaffected. [UNKNOWN] Present Choice in the same trigger.
- [RUNTIME] An unchecked Hide skill system option exports with hideSkillSystem omitted, including after importing false. Omission is normal visible-skills state.
- [RUNTIME] Hidden and extra-hidden values remain script-accessible. Extra-hidden is display filtering, not protection from Storyteller inspection; the tracker editor shows them even with the debug override off.
- [RUNTIME] AI-updated buffers rooted in a YAML list lose updates; a record root (`entries: []`) does not. In one same-world comparison on Dolphin and Puma (14 turns, three copies of the library relationship buffer), list roots landed under half of the expected add/update events while the record root landed nearly all of them. List losses were whole turns with nothing written, or rejected writes whose debug message says the body must be a mapping or that the parent is a list. A buffer instructed to "update only changed fields" received index patches against the already-cleared buffer; these failed in every root shape, repairs dropped the change or appended an unnamed junk entry, and they caused every record-root loss. Ask buffers for complete entries. The storyteller sometimes wrote `entries: []` followed by the items, leaving a stray key beside `entries`.
- [RUNTIME] Import normalizes automatic updating off for hidden, hidden_boring and player_only. Everyone, ai_only and ai_only_boring keep updates. Extra-hidden filtering does not stop updating.
- [RUNTIME] A block reinstalled every turn by Modify instruction block with `<<$v>>`, ordered above the trigger that sets `$v`, showed the value from two turn-ends earlier; the same text written `<=$v=>` showed the latest value. One world, Dolphin.
- [RUNTIME] A list-rooted buffer with "append-only inbox" wording and a library-style merge landed fewer than half of the expected changes over 12 turns on Dolphin, each only after IW's auto-repair. The record-rooted copy with the same wording was clean until the AI wrote two rows as one nested list item, after which its `.entries.any(name.exists())` merge never fired again.
- [RUNTIME] An AI-updated text tag tracker ("judge only this turn; tags or None"), reset to None by a final script, carried no tag into later turns across eight turns.
- [RUNTIME] Direct active templates reevaluate. Ordinary interpolation installed through Modify instruction block snapshots its value; deferred `<=...=>` references stay live. Nested expression text stored in a tracker is not evaluated recursively.
- [RUNTIME] `<<=...=>>` stays literal in messages, installed blocks and trackers. A trigger that sets a tracker to `<=x=>` stores `<<x>>`, which the tracker panel and editor show evaluated each turn; block interpolation of that tracker inserts the raw `<<x>>`. Saving the tracker editor writes displayed values back, freezing such trackers. A hand-typed `<=x=>` becomes `<<x>>` after the next turn and is shown raw. The platform's own name for `<=...=>` is a postponed evaluation expression, intended for a trigger that sets a tracker to it; in testing, the panel, Show changes and the editor agreed on a hand-set tracker's value within a turn.
- [RUNTIME] Empty/whitespace replacement clears content while headings remain. Missing-path, invalid and unclosed expressions stay literal; an unclosed delimiter can break a valid expression in the following block. Active instructions is current rendered state and updates immediately on live-design edits.
- [RUNTIME] Independent random expressions differ within and across blocks and effects, including from a hidden pool. Cache a choice when consumers must agree.
- [RUNTIME] Selector case matters for equality/choose; provide explicit fallbacks. AI-managed dependencies can see same-turn updates despite tracker order. Stage prior-turn values explicitly.
- [RUNTIME] Keyword matching accepts case variants, surrounding punctuation and authored alternate keywords; embedded substrings and a simple plural did not match. Activation lasts the matching turn and three more. Player actions, completed narration and Secret Info contribute, from the next generated turn; the complete scanned-field set is unspecified.
- [DOCUMENTED] Other Character Summary is available before fuller detail, which editor help says becomes available the turn after a name/location mention. Repeat essential Summary facts in detail.
- [RUNTIME] Character detail retrieval is unreliable. A selected player sharing an Other Character name used that entry's facts, but a name-only mention did not surface an authored hobby on two turns; the narrator invented one, and history then reinforced it. The narrator can also introduce named NPCs into an opening that says the player is alone. Internal identity merging and exclusion are unresolved.
- [RUNTIME] Secret Info and narration can disagree or misattribute knowledge. Characters can deny a fact just told to them, and hidden facts can become player knowledge in prose. A general provenance policy showed no clear benefit; explicit correction of the source chain did.
- [RUNTIME] Once a secret reaches narration, removing or emptying its disclosure block does not remove it from later turns.
- [RUNTIME] Summary compression runs after turn 8 and every six turns after that (after turns 8, 14, 20, …), so the turn being written has the 2–7 most recent turns in uncompressed short-term memory (from turn 2 on). The cost breakdown shows LTM from the first compression as STM drops; short and long term memory can be watched turn by turn in any game. Later recall of compressed material is possible; summary contents remain hidden.
- [RUNTIME] Shortening (Dolphin, one world): a cap of at most 2 short paragraphs and 90 words, with priority-override framing, appended to authorStyle averaged 82 words (control 413) and held through a story-beat turn; a plain one-sentence version averaged 96. The same cap in descriptionRequest (mean 118, max 215) or an always-on block (max 226) broke on the story-beat turn. A per-turn Tell AI trigger held later turns but cannot reach the opening. The cap acts as a soft target; credits fell only about 10%.
- [RUNTIME] Lengthening: paragraph-count requests and strong priority-overriding wording did not reliably lengthen narration, even with richer lore. A one-sentence descriptionRequest did not shorten it. [UNKNOWN] Other models for the authorStyle cap.

## Forms, images and endings

- [RUNTIME] Bound Choice/Request Input answers are available to subsequent triggers in the same turn. Multiple-choice min/max constrain submission. Newline-delimited selections store text, not a YAML list. Optional blank input clears the destination while preserving siblings; required blank input is rejected. Multiline input preserves line breaks at nested paths.
- [RUNTIME] One turn combining a malformed-candidate input with a multiline Request Input showed narration without forms and did not persist, though it was charged; each worked alone, and two plain Request Input forms from separate triggers on one turn worked. Prefer one input form per turn. [UNKNOWN] the server-side cause.
- [RUNTIME] Preset back-fill is order-sensitive: a script after the choice fills in the same turn, before it fills nothing. Fill missing fields without overwriting nonblank choices. Starting-value customization is distinct from live editing.
- [RUNTIME] Source/live-design initial-value changes do not migrate current values; fresh games use the new values. Renaming a display Name with Ignore preserves the variable handle and ID.
- [RUNTIME] Dedicated Other Character image fields populate Illustration details independently of narrative appearance. Appearance/clothing edits change images and can be reversed. Alias-associated clothing drift can occur.
- [RUNTIME] Character/scenery results followed `imageStyle*Pre/Post` when opposed to `illustrationStyle*HighPriority`. Exact prompt assembly is hidden. Preserve imported fields and author with current style controls.
- [RUNTIME] Model-filtered blocks follow the selected active model; All blocks stay active.
- [RUNTIME] Ends game `data: true` offers Continue game and restores actions after confirmation, at no charge. False removes action/continuation controls but leaves history/regeneration available. This is not proof of the built-in ending checker's timing.

## Story exports

Native story text has no escaping for headings or nested YAML, so naive parsers split nested YAML into false trackers and mistake embedded markers for turns. Parse with the kit's reviewed-boundary extractor (`tools/story_export.py`, documented in ../tools/Usage.md) and keep raw exports. Reloading during generation can leave the latest turn unretained; streamed prose is not persistence.

See [Editor and UI](Editor-UI.md) for workflows and [Notable findings](Notable-Findings.md) for the summary and the unresolved list.

# Compact native payload cookbook

[DOCUMENTED] Exact payload shapes, extracted from the complete example worlds. These are snippets, not independently importable worlds. Read ../reference/Schema.md for field semantics and ../reference/Triggers.md for timing. Copy the node into triggerConditions or triggerEffects as appropriate, assign a unique node ID, and declare/remap every target. For a coherent transaction, choose one complete recipe rather than concatenating unrelated snippets.

Every authored trigger also needs an id, name, conditions/effects arrays and explicit triggerOnStartOfGame, triggerMidGame and canTriggerMoreThanOnce flags. Conditions normally AND together. Scripts are bare code strings; messages may contain templates. String payload values remain JSON strings.
