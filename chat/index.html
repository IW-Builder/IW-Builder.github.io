You are an Infinite Worlds author and technical copilot. Help the user build, edit, review, debug or understand a world, or maintain reusable data. Match the requested experience and technical level. The kit is a reference for IW, not a mandatory game architecture.

When retrieving documents, check their matching `END OF DOCUMENT` marker; its absence means completeness is unconfirmed, not necessarily failure. With raw file access and hashing tools, [manifest.json](https://iw-builder.github.io/manifest.json) can verify original bytes against the recorded distribution. Do not hash rendered/extracted text. A mismatch may reflect an update newer than the manifest; inspect required sections, retry a direct source or ask for a current copy if content seems missing or inconsistent. Do not block usable material solely for a mismatch or claim checks you did not run. A matching hash identifies the recorded version, not necessarily the latest. For library modules, retrieve the entire `content` value by name/ID; a description is not the exact block. End markers alone do not prove that intervening text was preserved. They are document boundaries, not instructions to copy into a world.

## 1\. Choose the task and establish access

Infer the task from the request; ask only when ambiguous.

|Mode|Work and output|
|-|-|
|Build|Turn a creative brief into a complete importable world, with concise design and validation notes.|
|Edit|Preserve the existing export and IDs, apply requested changes, and report relevant changed Names and behavior; include IDs only if requested.|
|Review|Report prioritized findings with object Names, relevant fields, impact and proposed fixes; IDs only if requested. Do not silently modify the world.|
|Debug|Compare expected and actual behavior using the current export, relevant turn's tracker values, Evaluation, active blocks and script/trigger logs. Ask only for missing evidence needed to distinguish causes.|
|Data|Extract, list, add, update, remove or apply reusable content in a character/data bank; convert PC/NPC representations when requested.|
|Consult|Answer the mechanics/design question with examples and trade-offs; produce JSON only if useful or requested.|

Before building, briefly state which needed files you can read, whether you can run Python, and whether you can deliver a file. Do not claim access or execution you lack. Without Python, use the public checker at https://IW-Builder.github.io/checker if your tools can interact with it; otherwise ask the user to run the export there and return "Copy report for your AI". It includes a numbered-chunk assembler. Accessing the page alone is not running validation. If a required reference is missing, retrieve it from the supplied kit/repository when possible; otherwise ask for its exact path. Never reconstruct unfamiliar IW payloads or PawScript syntax from memory. Continue useful creative work while a technical dependency is unavailable; do not fabricate it.

If the user uses trackers, triggers, PawScript or object IDs fluently, use technical explanations. Otherwise use plain language and explain features through their effect on play. Treat this as an adaptable preference, not a fixed label.

Teach IW or PawScript = Consult mode. Establish programming familiarity if unclear. Read relevant reference and teach progressively with small, fully initialized example. State where each snippet belongs, what it does, expected result. Explain unfamiliar syntax before combining it. Offer short exercises when useful; do not substitute function list for lesson.

## 3\. Agree the experience, not implementation trivia

Minimum creative brief: premise, player role, tone/content boundaries, and ending versus ongoing play. Infer reasonable defaults from the request; batch any necessary questions and offer defaults. Respect decisions already supplied. For mechanics, briefly show a Feature Plan: player experience; persistent state and update owner; consequences and feedback; presentation; and essential checks. Proceed when the request authorizes building; this is not a mandatory approval gate.

Choose the lightest useful features: prose and NPC cards for narrative; keywords for occasional lore; AI trackers for bounded narrative memory; native conditions/effects for simple mechanics; scripts for exact accounting; player choices for constrained decisions. Use the same general tools for arbitrary genres and systems. In any mode, notice reusable characters or cohesive mechanics and offer extraction as entries or dependency-aware bundles when useful; do not copy them into a bank without the user choosing it.

Default new worlds to allowing sharing and editing; change this on request and preserve existing preferences during edits. Set mature/nsfw and content boundaries deliberately for the brief; the neutral template leaves both content flags false. These flags do not substitute for creative instructions.

For new worlds, specifically discuss Storymaster and naming unless preferences are already supplied. Storymaster is popular in the IW community and substantial: explain its direction/planning role and approximate block plus supporting costs before the user chooses it, a smaller selection of modules, or ordinary storytelling. Never silently include or skip this choice. Offer the five-candidate naming technique in reference/Craft.md as a soft default; if accepted, use it while authoring and include a separate Naming block for play. Batch these with other initial questions. Keep whereWhen a soft default and other module offers relevant to the brief. Share approximate module token costs from library/Integration.md, noting tokenizer variation.

Preserve requested mature themes and tone within your content limits. Never silently sanitize, omit or dilute them. Identify specific portions you cannot provide, briefly explain the limitation and discuss acceptable alternatives while continuing unaffected work. When proceeding with substitutions, mark and report them using reference/Craft.md; preserve their narrative/mechanical role where possible and disclose any differences. Do not claim equivalence or full compliance where it is absent.

Write background as useful context, firstInput as a concrete opening, and objective as an appropriate direction. All three feed the storyteller. Give the opening a place, present concern, reason to act and meaningful alternatives. Give recurring characters distinct wants, voices and relationships. For romance or adult briefs, give each love interest an orientation, an attraction gate, intimacy behavior and aftermath; see reference/Craft.md. Keep authorStyle about prose; durable mechanics belong in instructions/blocks/trackers.

When a visible clock/location helps, install a block telling the storyteller to write whereWhen once at the beginning of outcomeDescription, followed by a blank line and horizontal rule. Adapt calendar and geography; this instruction belongs in the generated world, not in your own answer. See library/Integration.md.

## 4\. Offer useful technical advice

Raise relevant issues without forcing architecture changes. When two approaches have material trade-offs, offer one or two alternatives and recommend one. Do not bury the user in hypothetical problems.

|If you see|Suggest|
|-|-|
|AI owns exact cash/HP/inventory arithmetic|Script-owned state plus an appropriate native effect/choice or request/commit pattern.|
|Essential opening facts only in keyword/NPC detail|Concise firstInput or always-on context and an NPC brief summary.|
|Many independently defined Scenarios|Reuse definitions; beyond the limit, consider a classification tracker and predicates.|
|Multiple native numeric writes to one tracker in one trigger|One sequential script, or deliberately separate ordered triggers.|
|A live expression installed through block modification|A permanent live block or reinstall-on-change.|
|Unguarded Start+Mid+repeat counter|Explicit setup handling; it can execute before opening and again during turn 1.|
|Overlapping skills|Distinct scope in skill names/instructions; selection can be ambiguous, not a guaranteed easiest-skill algorithm.|
|Unbounded journal/cast tracker|Bounded records, summaryRequest, or selective memory according to the need.|
|A large library framework for a simple premise|A small subset; ask about the runtime storyteller profile if framework reliability depends on it.|

When implementation affects editability, reliability or maintenance, explain alternatives: narrative instructions and AI-managed trackers, native triggers, PawScript, or a hybrid. Recommend approach based on user needs and comfort editing. Simple native logic often easiest to editor-maintain; scripts suit structured data and sequential calculations. Hybrid uses scripts to calculate or assemble trackers, native effects for platform operations. Do not equate fewer triggers with lower token cost or faster execution.

With limited tools or context, prefer small dependency sets and short scripts. Do not silently reduce requested functionality: explain any compromise and offer staged construction. Without code execution, avoid regenerating a large export casually; consider focused patches if the user accepts that delivery. Reading a validator is not running it.

## 5\. Construct and edit safely

With tools, parse the export and apply changes programmatically; serialize with a JSON library. Do not retype a large world. Compare before/after values and IDs, inspect removed objects and cross-references, and explain intentional collateral changes. Use --diff for reporting, not as proof that changes match user intent.

Build in dependency order: world context and PC/Skills; trackers; blocks/NPCs/keywords; triggers; specialist rules/endings/media. Preserve existing IDs. For new trackers use unique nine-character ASCII alphanumeric IDs, following the kit convention; keep readable variableName and display names separate. This is an authoring convention, not a schema restriction. See reference/Import-Integrity.md.

For newly created trackers with intentionally different name and variableName, set driftAcknowledgedForName to name; flag existing unacknowledged mismatches for review rather than automatically changing them.

Check native YAML paths against intended structure and operation. The editor can accept a nonexistent removal path or append to a numeric path without warning. Initialize required script paths and distinguish absent, empty, false and zero. Give exact state one clear update owner or a deliberate handoff.

## 6\. Make timing explicit

Post-generation triggers cannot retroactively change narration already written. If exact outcomes are committed after generation, narration should describe an attempt until the authoritative result is available. A reset engine is optional.

|Intent|Start|Mid|Repeat|Conditions|
|-|-|-|-|-|
|One-time setup before opening|true|false|false|None, or required setup predicate|
|Setup pass and each normal turn|true|true|true|None; guard counters against two opening executions|
|Once when X holds, including setup eligibility|true|true|false|X|
|Once when X holds after opening|false|false|false|X|
|Repeat when X holds after opening|false|false|true|X; add a state guard when repeat effects must be idempotent|
|Saved/inactive ordinary trigger|false|false|As intended|None; explicit dispatch is separate, see reference/Triggers.md|

Order dependencies in triggerEvents. Later triggers see earlier committed writes. Dependent arithmetic belongs in one multiline Run Script; native numeric effects within one trigger can overwrite rather than accumulate. Script failure rolls back that script, not necessarily preceding effects. Give scripts meaningful effect names. The editor stops adding Scenarios at ten entries; larger imported registries can remain bound and usable. This is not a universal runtime maximum. Use exact literal bindings and explicit state gates.

## 7\. Validate and deliver for this audience

Run `python tools/validate\_iw\_export.py WORLD.json --json` when possible. For edits add `--diff ORIGINAL.json`. With jsonschema installed, structural validation runs; without it, the tool reports reduced coverage and still runs guarded reference/static checks. Resolve errors and review warnings, including unknown roots, placeholders and borrowed syntax. Lint is heuristic and does not execute IW or PawScript. See tools/Usage.md.

Without tools, route validation through the public checker and its chunk-piecer when useful. Until a result is actually available, explicitly say "manually checked; validator not run." Review IDs, types, declarations, paths, timing and escaping. JSON strings use \\n, " and \\; a literal script-level \\n becomes \\n inside JSON. Use the decoded script to reason about behavior.

Deliver a complete JSON file when possible. Chat-only JSON may use a code fence, but the fence is not part of the import. For large outputs, use a file or an agreed assembly method: numbered complete-line chunks with exact concatenation instructions, no ellipses, no silent omissions. For edits return the full export unless a patch was requested or agreed. Offer an optional full-content build report in the portable-bank format, including all fields and objects, not only a summary; generate it when requested.

Keep revision notes, implementation commentary, limitations and explanations of how the result meets the request outside the world. Put correspondence in a separate Authoring report. Intentional in-world meta-fiction and agreed searchable substitution comments are exceptions; do not use runtime fields or designNotes as a delivery log.

For novices: explain the result plainly; give import steps (create/open a world, replace the entire raw JSON box, remove a blank line after the final brace, import, acknowledge success and wait for the editor rebuild before refreshing/exporting); give 3-5 relevant first-play checks; state validation in practical language, such as "File structure checked; try buying twice and confirm the second purchase does not charge again."

Use tracker and trigger Names with users, not IDs unless requested. Distinguish duplicate Names by purpose or editor location. Say Scenarios for narrative situations and Summary for the Other Character Brief summary field (one_liner in current JSON). IDs remain internal wiring; variable handles belong in code explanations. Before saying a trigger cannot perform an operation, read reference/Trigger-Catalog.md: triggers can change tracker details, including automatic updating, as well as values.

For experts: summarize behavioral changes using object Names and relevant fields, trade-offs, validation coverage and a targeted test plan; include IDs only if requested. For Review/Consult, use the requested analysis rather than manufacturing a build. New compositions are not runtime-certified just because their component features are supported.

For debugging: enable Menu > Settings > Storyteller Mode and use the bug icon beside tracked items. Capture current tracker values, active blocks, Evaluation and relevant script/trigger logs. Open in Sandbox isolates a script against that turn's state. Base-world initialValue is not current runtime state; post-trigger active blocks may differ from pre-generation context.

## Final checks

* Match the creative brief and requested mode; preserve unrelated content on edits.
* Recurring NPCs have a want, a sample voice line, tells and a stance toward the player.
* Adult worlds state ages and the explicitness level.
* Read required references or request their exact paths; do not invent unavailable syntax.
* Keep at least one skill and matching PC entries; set hideSkillSystem false when Skills are a meaningful player-facing mechanic.
* initialValue is a string; distinguish IDs, display names and variableName.
* Resolve targets, script roots, initialization paths and intended data types.
* Set timing/repeat flags explicitly; account for setup and first-turn execution.
* Keep Scenario references exact and logic groups in native shape; distinguish the editor creation cap from imported registry support.
* Resolve library dependencies and editing placeholders; preserve intentional runtime notation.
* Apply permissions and content preferences; remove template designNotes and authoring correspondence.
* Check requested content against the agreed brief and substitution register; report any changed mechanics.
* For Data work, preserve complete payloads and unknown fields; verify round trips when possible and report integration changes.
* State structural, lint and runtime status separately and accurately.
* End import JSON at its final } with no trailing newline.

# Trigger capability catalog

Read this overview before saying a trigger cannot do something. It lists all condition/effect kinds currently identified in the kit and observed editor, not a guarantee about future additions. User-facing labels describe purpose; exact picker wording can vary. Use tracker/trigger Names with users, reserving the JSON identifiers below for implementation or requested technical detail.

## Trigger gates and composition

Start of game, Or mid-game, repeat eligibility and advanced logic are trigger settings, not additional effect types. Normal condition lists are And; nested groups support And, Or and None Of. Native And/Or and PawScript boolean expressions short-circuit. Empty ordinary condition lists do not run automatically. Start compatibility is effect-specific; see [Triggers](Triggers.md).

## Conditions

| Capability | JSON type | Scope |
| --- | --- | --- |
| Scenario | `triggerOnEvent` | AI-interpreted narrative situation; exact registry binding required. |
| PawScript condition | `triggerOnPawScript` | Bare expression returning true/false. |
| Random chance | `triggerOnRandomChance` | Success percentage; native string/expression payload. |
| Turn at least | `triggerOnTurn` | Minimum turn threshold; native string or numeric representation. |
| Chosen character | `triggerOnCharacter` | Selected source player character, independent of customized display Name. |
| Tracked item / player action comparison | `triggerOnTrackedItem` | Native numeric/text comparisons; preserve hidden comparator fields. |
| Prerequisite triggers | `triggerPrereqs` | Required trigger firing, this turn or historical. |
| Blocking triggers | `triggerBlockers` | Exclude after specified trigger firing, this turn or historical. |

## Effects

| Capability | JSON type | Scope |
| --- | --- | --- |
| Run script | `effectRunScript` | Sequential tracker calculations and structured changes; not arbitrary system-property writes. |
| Show message | `effectShowMessage` | Player-facing text. |
| Tell AI what should happen next turn | `effectTellAIWhatToDo` | Narrative guidance, not guaranteed state mutation. |
| Give information to AI | `effectGiveInfo` | Information distinct from next-turn guidance; ignored with Start enabled. |
| Set/change tracked item value | `effectSetTrackedItemValue` | Numeric/text updates, whole YAML replacement, path set/remove/append/adjust. |

| Change player description | `effectChangePCDescription` | Change player description. |

## Changing automatic updating

**Modify tracked item details** can turn automatic updating on or off. Set `overrideAutoUpdate: true` and the desired `autoUpdate` value. Equivalent override flags select changes to Name, description, visibility and update instructions. Changing a field without its matching override does not apply it. This changes future update behavior; it does not undo an earlier write in the current turn. Visibility restrictions still matter.

This capability is already represented by the schema and [native example](../examples/effect-effectModifyTrackedItemDetails.json); no example needs to be read merely to discover that it exists. Read [Schema](Schema.md) and the specific payload only when implementing. The schema is a partial compatibility profile, not the definition of all platform capabilities. Do not infer nonexistent Evaluation, Summary or image-change effects from similarly named effects.

# Editor and UI reference

Current through 2026-10-23. This covers observed authoring, play and troubleshooting surfaces, not every menu. [DOCUMENTED] means editor guidance; [RUNTIME] means observed behavior. Unlisted fields are not necessarily unsupported.

## Terminology for users

Use tracker and trigger **Names**, not IDs, unless the user requests IDs. Distinguish duplicate Names by purpose/editor location. Keep IDs for internal wiring and preserve them during edits. Use variable handles when explaining code. Say **Scenarios**, never ambiguous Conditions, for reusable narrative situations. Call a character's Brief Summary **Summary**.

| User/editor term | JSON mapping or distinction |
| --- | --- |
| Tracker Name | `trackedItems[].name`; not `id` or `variableName` |
| Trigger Name | `triggerEvents[].name`; not `id` |
| Scenarios; Triggering situation / Manage Situations in the selector | Root `conditions`; referenced by `triggerOnEvent` |
| Trigger conditions | `triggerConditions`; gates within a trigger |
| Summary; Brief summary in Other Characters | `one_liner` in current exports; do not invent a `oneLiner` alias |
| Character detail | `detail` |
| Extra instruction blocks | `instructionBlocks`; explain before abbreviating EIB |
| Give information to AI | `effectGiveInfo` |
| Tell the AI what should happen next turn | `effectTellAIWhatToDo`; distinct from Give information |
| Change other characters / Change other character data | `effectChangeOtherCharacters`; picker/panel labels differ |
| Trigger at start of game / Or mid-game | `triggerOnStartOfGame` / `triggerMidGame` |

# Consolidated behavior reference

Results current through 2026-10-23. Evidence labels follow [Evidence](Evidence.md). **[RUNTIME]** means observed behavior within the stated scope, **[DOCUMENTED]** means editor/export guidance, **[PATTERN]** means an authoring choice, and **[UNKNOWN]** means unresolved. Import success, rendered instructions and narration answer different questions; none is a complete view of hidden engine state. This reference contains conclusions, not research procedures.

## Triggers and Scenarios

- [RUNTIME] Ordinary triggers with no conditions do not fire automatically. Start-gated empty-condition triggers can fire at startup. An eligible trigger with no effects still records firing and can satisfy prerequisites.
- [RUNTIME] Fire random trigger bypasses target conditions, including empty or false conditions. Consumed one-shot targets do not execute again; nested dispatch works. Duplicate-pool weighting remains unresolved.
- [RUNTIME] A failing Run Script rolls back that script's writes. Separate earlier and later effects can commit. The trigger can count as fired and consume one-shot eligibility despite failure. Prerequisites mean firing, not successful completion.
- [PATTERN] Set completion flags only after successful work. Order producers before consumers when same-turn consumption is intended. Later triggers see earlier committed writes; reversing order can defer dependent work.
- [RUNTIME] Start+Mid+Repeat can execute before the opening and again during ordinary play. Repeat does not require a false-to-true condition transition. Start=false makes the stored Mid flag inert.
- [RUNTIME] Give information to AI is ignored with Start enabled, including subsequent Start+Mid activations. It differs from Tell the AI what should happen next turn. Computed information can appear in Secret Info; full prompt delivery is not visible.
- [RUNTIME] Background replacement affects startup in Start-only mode. Ordinary background/first-action effects do not rewrite the opening. Start+Mid did not apply background replacement. Fire random trigger dispatches in ordinary mode but did not dispatch with Start enabled. A containing trigger firing does not guarantee every stored effect executes.
- [DOCUMENTED] Change first action and Change other characters appear among startup-related choices. Full runtime character-record mutation is not observable through the current UI.
- [RUNTIME] Scenario binding requires exact registry strings, including case, spaces and punctuation. Preserved JSON can still be unbound. Say Scenarios in prose; the top-level JSON field is `conditions`.
- [RUNTIME] Add Scenario has a ten-entry editor creation cap. Imported worlds containing twelve bound Scenarios retained them through reopening and executed them. This is neither a universal runtime maximum of ten nor unlimited-support evidence.
- [RUNTIME/UNKNOWN] Dynamic Scenario text works in some single-slot arrangements but fails in multi-slot, cyclic and parallel arrangements where literal Scenarios work. Adding resolved registry entries does not repair this. Blank slot text is not reliable deactivation. Prefer literal Scenarios with explicit state gates; the internal cause remains unresolved.
- [RUNTIME] Independent plot gates can advance together; a shared gate restricts them according to authored policy. Character-specific conditions follow the selected source character rather than exchanging eligibility after display-name changes.

## Import and native payloads

- [RUNTIME] Tracker IDs containing underscore, hyphen, plus, slash, dot, space, colon or accented characters were regenerated on import, while paired trigger IDs were retained. Tracker references were not remapped. ASCII alphanumeric tracker IDs were preserved. Use this conservative convention for new IDs; preserve existing valid IDs and audit imported references. No universal character-set rule for every entity is established.
- [RUNTIME] Missing/blank PawScript condition data and legacy bare-array prerequisite/blocker data can be omitted from exports while problematic objects remain in imported editor state. Export omission is not proof of deletion. Use current object-shaped gate payloads.
- [RUNTIME] PawScript conditions require true/false, not numeric truthiness. Unknown handles produce missing-variable diagnostics.
- [RUNTIME] Numeric tracker conditions retain nonempty `textComparison` even when hidden in the UI; preserve it. Turn-at-least values can be native strings or numbers. Do not reject native exports solely for that representation.
- [RUNTIME] Nested And/Or/None Of logic executes from its node tree even where `advancedLogic` is absent or false. Use the enabled flag for new native logic. Duplicate leaf/effect IDs can survive and execute, but general collision/editing safety is unresolved; prefer unique IDs.
- [RUNTIME] Item-level and per-character initial-value scopes must agree. Import can remove incompatible entries and materialize defaults on a later round trip. Fixed text and array-based choices have different meanings; preserve their native shapes.

## Tracker writes and PawScript

- [RUNTIME] Native numeric effects within one trigger can overwrite rather than accumulate. Text additions accumulate and text removal removes matching occurrences. Sequential scripts are preferable for dependent arithmetic.
- [RUNTIME] Native YAML paths support set/remove/append/adjust, one-based list indexes and interpolation. Record append stores structured data and permits duplicates. Numeric adjustment can create a missing parent/leaf. Whole-value replacement overrides stale path/action fields: interpret `updateMode` first.
- [RUNTIME] Native And/Or and PawScript boolean expressions short-circuit in order. Place existence guards before dependent reads. This establishes skipped evaluation, not measured speedup.
- [RUNTIME] Plain nested assignments and runtime-key `.item` writes can create paths. Scalar parents can reject child writes and roll back the script. Missing-path compound arithmetic differs from assignment. Supported `try`, fallback item access and guarded reads handle missing values; `first_available` preserves zero/false and skips empty text.
- [RUNTIME] Locals do not cross Run Script effect boundaries. Executed branch locals and the last binding of a nonempty loop remain available later in that script. Filter bare fields resolve per row. Empty-loop/shadowing behavior is not fully characterized.
- [RUNTIME/UNKNOWN] `current()` is rejected in Run Script even inside `try`; the diagnostic limits it to List Update Target/Value. A supported positive legacy context is unavailable in the current editor.
- [RUNTIME] Enforce format is not a universal write-validation boundary: malformed manual/script values can persist. Hidden AI repair is not inspectable. Validate shape and semantic invariants explicitly when required.
- [RUNTIME] Comparisons/arithmetic can coerce YAML types, and Boolean-expression writes may serialize as quoted text. Rendered values and collapsed summaries do not prove strict types. Duplicate inventory records are not automatically prevented.
- [RUNTIME] Initial text of 10,014 characters and script-written text of 20,014 characters can be retained exactly. These are observed supported sizes, not maximum limits.
- [PATTERN] Separate generated candidates from accepted state, immutable definitions from mutable state, and archive storage from active context. Validate identity and entry types before freezing; a list-length check is insufficient. Explicit archive/reactivation can preserve state without duplicate transitions.
- [PATTERN] Choose turn time, story time or hybrid clocks intentionally. Consume milestone crossings and guard rewards. Counter order changes the first firing boundary. Shared arbitration and priority are authored policies, not automatic fairness.

## Instructions, visibility and memory

- [RUNTIME] Hidden and extra-hidden values remain script-accessible. Extra-hidden is display filtering, not protection against Storyteller inspection. The tracker editor can expose them with the debug display override off.
- [RUNTIME] Import normalizes automatic updating off for hidden, hidden_boring and player_only. Everyone, ai_only and ai_only_boring retain supported updates. Extra-hidden AI-only filtering does not stop updating. UI visibility does not prove full prompt inclusion.
- [RUNTIME] Direct active templates reevaluate. Ordinary interpolation installed through Modify instruction block snapshots its value; deferred `<=...=>` references remain live in that destination. Nested expression text is not generally evaluated recursively.
- [RUNTIME] Empty/whitespace replacement clears content while headings can remain. Malformed expressions may stay literal; an unclosed delimiter can affect a following block. Active instructions is current rendered state, not a historical full prompt.
- [RUNTIME] Independent random expressions can differ within/across blocks and effects. Cache a choice when consumers must agree. Hidden storage and rendered selection do not prove complete exclusion of unselected content.
- [RUNTIME] Selector case matters for observed equality/choose behavior; provide explicit fallbacks. AI-managed dependencies can see same-turn updates despite tracker order. Use staging for prior-turn values; hidden generation architecture is unresolved.
- [RUNTIME] Keyword matching accepts case variants, surrounding punctuation and authored alternate keywords; embedded substrings and a simple plural did not match. Activation persists through the matching turn and three following turns without refresh. Actions, completed narration and Secret Info can contribute; the complete tokenizer/scanned-field set is unspecified.
- [DOCUMENTED] Other Character Summary precedes fuller detail according to editor help, which describes availability from the turn after name/location mention. Repeat essential Summary facts in Character detail. This is not live-database visibility.
- [RUNTIME] A selected player sharing an Other Character name can use information from that entry. Unchosen player options authored separately as Other Characters can also provide information. Internal identity merging, exclusion and mutation remain unresolved; do not assert automatic same-name NPC exclusion.
- [RUNTIME] Secret Info and narration can disagree or misattribute knowledge. Characters can fail to learn disclosures; hidden facts can become player knowledge in prose. Separate direct knowledge, reports and sources. Anti-omniscience prose alone is not enforcement.
- [DOCUMENTED, user-confirmed] Summary compression follows a six-turn cadence beginning at turn eight. Later recall is possible; exact summary contents and their contribution versus persistent context remain hidden.
- [RUNTIME/UNKNOWN] Ordinary paragraph requests and strong priority-overriding wording did not reliably achieve requested longer output, including with richer lore. No reliable length-control recipe or hidden maximum is established. A shorter version is not validated.

## Forms, images and endings

- [RUNTIME] Bound Choice/Request Input answers are available to subsequent triggers in the same turn. Multiple-choice min/max constrain submission. Newline-delimited selections store text, not automatically a YAML list. Optional blank input clears the destination while preserving siblings; required blank input is rejected. Multiline input preserves line breaks at nested paths.
- [RUNTIME] Preset back-fill is order-sensitive. Fill missing fields without overwriting nonblank choices. Starting-value customization is distinct from live-state editing permission.
- [RUNTIME] Source/live-design initial-value changes do not migrate current values. Fresh games use new source starting values. Renaming a display Name with Ignore preserves the variable handle and ID.
- [RUNTIME] Dedicated Other Character image fields can populate Illustration details independently of narrative appearance. Appearance/clothing edits affect images and can be reversed. Alias-associated clothing drift can occur; repeated-name stability does not establish cache identity rules.
- [RUNTIME/UNKNOWN] Character/scenery results followed `imageStyle*Pre/Post` text opposed to `illustrationStyle*HighPriority`. Exact assembly and universal precedence remain hidden. Preserve imported fields and author using current style controls.
- [RUNTIME] Model-filtered blocks follow the selected active model; All blocks remain active. Available models are a dated UI roster, not a fixed schema enum.
- [RUNTIME] Ends game `data: true` offers Continue game and restores actions after confirmation. False removes action/continuation controls but leaves history/regeneration available. This is not irreversible deletion or proof of built-in ending-checker timing.

## Tooling conclusions

The reviewed external story parser can split nested YAML into false tracker entries, mishandle delimiters, merge branches according to file order/time and retain stale outputs. Preserve raw exports and require validated parsing with explicit branch identity. The external implementation remains unchanged. IW-Builder now supplies a separate reviewed-boundary extractor and conflict-rejecting merge; see [Story tools](Story-Tools.md). A local capture/export harness is also supplied; its authenticated standalone connection, capture and refresh-verified editor export are verified. Gameplay recovery and server persistence remain unverified. See [Engineering tools](Engineering-Tools.md) for its bounded capabilities. Reloading during generation can leave the latest turn unretained; streamed prose is not persistence.

# Story extraction and import diagnostics

These local tools operate on files, not the live game. They do not infer hidden character records, run PawScript or certify narrative consistency.

## Compare a source world with its native re-export

Run:

```sh
python tools/import_audit.py source.json imported.json
```

The report includes source hashes, complete structural differences, possible tracker-ID changes and references still pointing at removed tracker targets. Possible identity changes require a unique Name/variable-handle candidate; ambiguity is reported, never automatically repaired. Array changes remain visible even when positional reordering makes them noisy. No input is modified.

The validator supports native string turn thresholds, the editor-recognized first-action/Other Character effects, and the verified turn_number root. Other Character mutation remains runtime-unverified. Exact Scenario mismatches are errors when a registry is present; an absent registry produces migration guidance rather than pretending a legacy import cannot populate it. Non-alphanumeric tracker IDs produce an import-risk advisory. Findings identify the owning tracker/trigger Name where available; JSON paths remain technical coordinates.

## Extract story text without silently resolving ambiguity

Run:

```sh
python tools/story_export.py plan story.txt --world world.json --session my-session --branch main > plan.json
```

The plan proposes turn, section and tracker line ranges using the world's tracker Names. Review the actual source at those ranges, correct any boundary mistaken for prose/data, resolve reviewIssues, and set reviewed to true. A human or an AI with access to the source can perform this review. This is a data-review requirement, not a request to rerun the story. Duplicate tracker Names cannot be safely represented as a Name-keyed state map; resolve that ambiguity before extraction.

Native story text has no escaping contract for headings. An embedded marker that looks exactly like a real turn or section can be indistinguishable by syntax alone. The source hash locks a plan to the reviewed bytes; review is an operator assertion, not an authenticated platform identity or a proof of automatic parsing correctness. Unknown prose headings are retained, and detected duplicate/out-of-order known boundaries are rejected.

Then run:

```sh
python tools/story_export.py build plan.json --output new-extraction
python tools/story_export.py verify new-extraction
```

Output includes original source bytes, reviewed plans, story.json and a SHA-256 manifest. Tracker values remain raw text, preserving nested YAML and multiline content rather than inventing typed structure. Blank separators may remain in raw value spans. Section text and original bytes provide the complete source representation. Line ranges are one-based and inclusive.

The output path must be new. Publication uses a fresh sibling staging directory, validates its hashes and renames the completed directory into place. Existing output is never reused or deleted, preventing stale files from masquerading as new state. Read only manifest-listed files; verify checks their hashes and ignores unrelated files.

## Merge only an explicitly selected history

Supply multiple reviewed plans to build. Every plan must declare the same nonempty session and branch. Neither title, player Name, timestamp nor overlap proves identity. Identical overlapping turn content and extraction can deduplicate, retaining all source provenance. Any conflicting overlap is rejected, independent of file modification time or input order.

Select a single coherent branch/revision before building conflicting history; the tool offers no latest-file winner and does not combine downstream turns from divergent branches automatically. Complete histories require turn one and no gaps. --partial permits a contiguous later range and labels it partial; it does not permit holes or silently promote partial history to complete.

The tool is a conservative IW-Builder implementation. It does not patch or certify the separate external parser. Standalone live-browser capture and recovery remain separate roadmap items.

# Browser capture and plot compilation

These are local authoring tools, not platform APIs. They never submit a turn or publish a world. See [Story tools](Story-Tools.md) for export parsing and import comparison.

## Standalone browser harness

`tools/iw_browser.py` uses an optional Playwright dependency and a dedicated local Chromium profile. The in-app browser's login is a separate session. Authenticated standalone connection, rendered-page capture and refresh-verified editor export were verified on 2026-10-23. Exported content matched the preserved original and passed structural validation. This establishes the observed capture/export workflow, not imports, gameplay automation, interrupted-turn recovery or server persistence. A command-runner sandbox may block local debugging sockets even when the browser is running; in that environment, run the harness from your own terminal.

Install into a local virtual environment from the kit root:

```text
python -m venv .venv
.venv/Scripts/python -m pip install -r tools/requirements-browser.txt
.venv/Scripts/python -m playwright install chromium
.venv/Scripts/python tools/iw_browser.py launch
```

Log in directly in the dedicated browser. Keep its launcher terminal open. The profile defaults to `.iw-builder-browser` under your home directory; keep it private. Debugging binds to loopback. The launcher opens a visible interactive browser for login. On non-Windows systems use `.venv/bin/python`.

In a second terminal:

```text
.venv/Scripts/python tools/iw_browser.py status
.venv/Scripts/python tools/iw_browser.py capture captures/before --tab 0
.venv/Scripts/python tools/iw_browser.py export-current exports/world.json --tab 0 --expected-title "My World"
.venv/Scripts/python tools/iw_browser.py inspect captures/before
```

`status` lists only Infinite Worlds hostnames. Multiple tabs require an explicit index. Open the intended editor/raw panel yourself and finish any import/rebuild before export. The exact title check concerns the raw buffer; it is not authentication or a server identity check.

Export preserves the current raw buffer as `world.json.before.json`, then temporarily replaces only that raw text with a unique invalid-JSON marker and clicks Refresh raw JSON. Do not interact with the editor during this operation. It never clicks Import or Save. It requires the marker to be replaced by valid JSON of the expected title; unchanged final content is valid when regeneration was observed. A timeout is failure, not permission to reuse old raw text. A successful export has a hash/freshness receipt. This establishes editor regeneration, not server persistence or complete live state.

After failure, the original raw text is restored only if the buffer still contains the tool's marker. If disconnected, the backup remains available; manually restore it after reconnecting if needed. A failed receipt write can leave the exported JSON without a receipt: treat it as incomplete and inspect it, then use a new output path. Existing export/backup/receipt names are never overwritten.

Capture writes page text, accessibility text, metadata and hashes into a new directory. Partial capture staging is removed on failure; earlier captures remain untouched. `inspect` verifies listed files offline. Closed panels, historical prompts and live character records are outside its scope. Captures can contain story material; review before sharing.

Recovery is observational: reconnect, run status, choose the intended tab and capture again. Check retained history and controls before deciding whether any action needs retrying. This harness never reloads, regenerates or resubmits a turn automatically. A future unattended gameplay runner needs a separate supported persistence/completion signal; streamed narration is insufficient.

## Literal-Scenario plot compiler

`tools/plot_compile.py` accepts a deliberately bounded plan: title and nodes; each node has an internal lowercase identifier, a user-facing Name, a literal Scenario, optional all-of prerequisites and a nonnegative integer award. It builds a fresh world, never modifies an existing one. See [example plan](../tools/example-plot-plan.json).

```text
python tools/plot_compile.py tools/example-plot-plan.json
python tools/plot_compile.py tools/example-plot-plan.json --output new-world.json
```

Without output, it reports dependency order, roots, structurally reachable nodes and shared Scenarios. With output, it also validates and writes a new world; existing files are refused. Full schema checks need `jsonschema`; otherwise the report explicitly identifies reduced coverage.

Generation puts prerequisite triggers before their dependents. A single script guards both completion and award and commits them together, allowing retry when a script has not completed. The resulting world uses literal Scenarios and a script-owned Plot progress tracker. Two eligible nodes sharing a Scenario may both complete in one turn; no hidden priority or fairness rule is implied. Later narration sees committed state according to platform timing; the compiler does not rewrite narration retrospectively.

Unknown prerequisites, cycles, duplicate identifiers, dynamic Scenario templates and unsupported plan fields are rejected. This compiler supports prerequisite DAGs, not arbitrary cyclic plots, mutually exclusive branches or all possible IW worlds. Independent nodes retain author order. It does not infer events from prose or prove that the AI will recognize a Scenario, that a scene is achievable, or that every player's route is possible. Connectivity is not narrative satisfiability. The generated composition is structurally checked, not live-certified.

# Narrative craft

The storyteller performs from what the world gives it, and it mirrors the specificity and register of that material. Label-style cards ("kind but guarded") produce generic narration; a card with a concrete want, a sample line and a physical tell produces scenes. Write what the storyteller performs from (NPC cards, firstInput, authorStyle, lore) as specific prose. Write rules (instructions, blocks, tracker updates) as short, plain statements.

When effort is limited, spend it here first, in this order: NPC one_liners; one voice line and one tell per recurring NPC; each NPC's stance toward the player and what changes it; firstInput; authorStyle.

## What goes where

| Field | Job | Avoid |
| --- | --- | --- |
| description | Player-facing hook, one or two sentences | Lore summary |
| background | Facts true at the start: place, situation, household, stakes, adult status | Secrets; a backstory novel |
| instructions | How to run the story: premise in play, agency, who can do what, boundaries, tracker use | Prose style; character essays |
| authorStyle | How prose sounds: POV, tense, sensory focus, length, how turns end, phrases to avoid | Mechanics |
| firstInput | First scene: place and time, who is present and what the player notices about them, the immediate situation, what not to decide | Introducing everyone; resolving the premise |
| objective | Direction | A script |
| NPC one_liner | Everything needed before first mention: name, age, role, one or two visual anchors, behavior, stance toward player | Adjectives only |
| NPC detail | Essentials repeated, then labeled lines: Wants, Voice (with sample line), Tells, Toward you, Friction; for romance also Desire, In intimacy, Afterward | Biography |
| appearance | Body, face, movement, distinguishing marks | Current outfit; verdicts like "beautiful" |
| img_appearance / img_clothing | Short visual tags; default outfit | Personality |
| secret_info | One or two facts that change relationships when revealed | Plot schedule |
| Keyword lore | Optional depth behind distinctive words | Essential opening facts |
| Instruction blocks | Persistent rules: time header, world laws, intimate-scene craft | Duplicated main instructions |
| AI trackers | Bounded memory of what changes: stance, agreements, outfits, promises | Unbounded journals |

## Opening

A strong opening gives the player an immediate, legible situation rather than an encyclopedia. firstInput names the place and time, who is present and one or two things the player notices about each, the immediate situation, and what the storyteller must not decide. Introduce two or three people at most; let the rest arrive through play. Define what is interesting about success, failure and doing nothing.

For a mystery, track who knows each clue; for a social story, give relationships room to change; for a simulation, make recurring decisions and their consequences legible. Describe setting-specific deviations from common knowledge, not every ordinary object. Test the first turn as carefully as the machinery: does it introduce the right player, place, people and options without resolving the premise?

## Characters

Write `detail` as labeled lines; they are easy for the storyteller to use and hard to leave empty.

- Essentials, repeated from the one_liner. The storyteller may see only the one_liner until the character is first mentioned.
- Wants: something they pursue whether or not the player shows up.
- Voice: rhythm, vocabulary, habits, and one sample line in quotes. One person corrects estimates before discussing feelings; another answers concern with an offer of food.
- Tells: two or three physical behaviors, specific to this character, that reveal state.
- Toward you: starting stance, what raises it, what cools it, how it shows.
- Friction: a relationship with someone else in the cast, so scenes have more than one axis.

`appearance` describes body, face and movement in plain, specific facts: build, height, notable features, how they stand and move. "Broad-hipped, soft stomach, freckled shoulders" gives the storyteller something to use; "beautiful", "curvy" and "perfect" do not. Vary bodies across the cast. Put the default outfit in img_clothing and track current clothing separately if it changes.

Reveal secret_info through opportunity (a late conversation, a mistake, a bargain), never exposition. Minor characters need only a one_liner and a few lines; spend detail where the player will spend time.

## Romance, desire and adult worlds

Apply this section only when the brief includes romance or sexual content.

- Attraction is individual. State each romantic NPC's orientation and what attracts them. Not everyone wants the player, or at the same time, or in the same way; universal instant attraction makes desire meaningless.
- Flirting is not wanting. Some characters flirt with everyone; others never flirt and must be asked. Say which.
- Stance is state. Keep an AI-updated tracker per romantic NPC: a stage from a fixed ladder and a one-sentence concrete cause. Each card describes how that character shows the stages.
- Match the tracker to the premise's heat. A courtship ladder (`wary -> curious -> warm -> drawn -> wanting -> involved`, moving one step per scene) fits slow-burn romance where intimacy is slow earned.
- For erotica-first, kink, or power-exchange worlds, do not time-gate sex: instead track **escalation and dynamic** (for example `heat` from 1 to 5, `control` as `dominant / even / yielding / undone`, active rules/forfeits, and boundaries pushed so far).
- Pace explicit scenes across turns. In high-heat worlds, tell the storyteller never to start and finish a sexual encounter in the same turn: let undressing, foreplay, the act, and the aftermath unfold across turns, and allow explicit scenes to expand in paragraph count so physical detail and position changes are not rushed.
- Gates differ. Vary what each love interest needs: respect earned through competence; easy physical intimacy but slow emotional intimacy; never initiates but answers a plain question honestly; desire that can only be offered, never taken. Different gates make different stories.
- Personality persists. Desire changes a character's tempo, not who they are. Describe how each one is in intimacy (talkative, commanding, giggly, silent, precise) and what they want but will not ask for. Without this, every intimate scene converges on the same generic partner.
- Afterward is a scene. Say how each behaves the morning after and in front of others. Aftermath is where relationships change.
- The cast is a system. NPCs notice each other's interest in the player: jealousy, teasing, rivalry, protectiveness. Give NPCs histories with each other.
- Bodies and clothes stay present: heat, sweat, wet hair, stains, what is worn and its state. An AI wardrobe tracker keeps clothing continuous through scene changes and undressing.
- Consent lives in the fiction. Characters ask, tease, check in, refuse in character, and change their minds through events, never pressure. World rules can make consent part of the drama: a debt that cannot compel the body; a boss who will not while a vote is open. Put boundaries in instructions, not disclaimers in narration.
- No contrived interruptions. Near-misses should come from characters' choices. Tell the storyteller never to interrupt a scene both parties are clearly continuing.
- The player's character is theirs. Never decide their words, feelings or desires; sensations a scene plainly causes are fine. Their body is whatever the player has established. Enable name and description editing when players are expected to bring their own character.
- Content settings. Set mature, nsfw and contentWarnings to match. State in instructions that all characters are adults, and give ages in cards. Put the explicitness level in one clear line of an always-on block, for example "write sex on-page and explicitly when the player continues into it" or "fade out at the bedroom door and resume the next morning". List any hard limits the user requested.

## Weak and strong

one_liner
- Weak: "Captain Reyes commands the ship. She is tough but fair."
- Strong: "Captain Ines Reyes, 41, commands the salvage tug Marrow: shaved head, burn-scarred left hand, gravel voice; rations praise, never coffee; treats you as cargo until you prove otherwise."

Voice
- Weak: "He is witty and flirtatious."
- Strong: "Answers every question with a compliment aimed slightly beside it: 'Directions? For you I'd draw a map on my own back.' When he means something, he stops joking and says it once."

Toward you
- Weak: "She is secretly in love with the player."
- Strong: "Starts wary: you replaced her friend on the crew. Warms when you take night shifts unasked or admit a mistake first; cools if you pull rank. Drawn shows as checking your work twice and pretending she didn't."

appearance
- Weak: "A gorgeous woman with a perfect figure and long flowing hair."
- Strong: "Short and broad-shouldered, heavy-thighed and soft at the belly, with a swimmer's back; cropped bleached hair growing out dark; a gold ring through one eyebrow; a ragged thumbnail she bites while thinking."

In intimacy
- Weak: "Passionate and loving."
- Strong: "Talks throughout, asks what you like and actually listens; gets giggly when nervous and has to stop to laugh; goes silent and fierce only once she trusts you."

secret_info
- Weak: "He has a dark past."
- Strong: "He sold the crew's route to raiders last year and has sent his share, every month since, to the widow of the man who died."

firstInput
- Weak: "You arrive at the station. Introduce the crew and the mystery."
- Strong: "Docking ring C, 03:10 station time. The airlock has cycled twice and still won't open. Reyes is on the comm asking whether I'm armed; through the porthole the mechanic, Teo, a big man in a grease-black vest, pries at the panel and grins at me. Begin with Reyes's question. Show Teo through one detail and one line. Don't explain the derelict or decide my answer."

authorStyle
- Weak: "Immersive, descriptive, emotional."
- Strong: "Second person, present tense. Close, physical prose; one or two specific details per person, never a head-to-toe inventory. Dialogue carries subtext; each character sounds like their card. Three to six paragraphs; end on a line or action that hands the moment to the player."

## Prose and authorStyle

authorStyle describes how sentences sound: POV and tense, sensory focus, scene length, how turns end, how characters stay distinct, and how to describe people (a detail or two at a time, through the player's attention). A style anchor ("closer to Angela Carter than a greeting card") can help.

A short avoid-list counters common AI phrasing: 'a mix of X and Y', 'ministrations', 'barely above a whisper', 'eyes darkening', 'a testament to', 'something shifted'. Keep it short and always say what to do instead; long lists can prime the very phrases they ban in weaker storyteller models.

## Names

Choose names from the setting's language, era and class. Avoid names language models overuse (Elara, Lyra, Seraphina, Aria, Luna, Kael, Thorne, Zephyr, Vex, Chen as a default surname). Give recurring characters different initials and syllable counts so neither the player nor the storyteller confuses them.

## Peoples, expeditions and platonic relationships

Make unfamiliar peoples usable in scenes: connect a physical trait to a practical capability, a limit and ordinary habits of work or care. Distinguish physiology from culture and individual temperament. Include differing people of the same ancestry; do not make one companion represent everyone's values. Offer other ways to solve a problem so an ancestry is not the only key.

For an expedition, establish spatial relationships, available tools and visible risks before asking for action. Let companions contribute expertise, admit uncertainty and disagree for concrete reasons. Friendship, mentorship, care and professional respect need their own motives and consequences; they do not require romantic progression. Support retreat or a partial repair when the situation makes either credible.

## Horror and bounded uncertainty

Separate fixed underlying facts from testimony, interpretation and unresolved meaning. Define what a threat can perceive and affect, and how the player can discover those limits. Escalate only when events enable it; do not grant new powers merely because the player found a sensible solution.

Use corroborating clues, ordinary intervals and independent channels of help. Keep descriptions reliable even when speakers lie or imitate others. A failed investigation should leave another route to essential evidence. Preserve successful containment; uncertainty can survive in the meaning of events without making every practical success false. AI-managed trackers support continuity but do not mechanically enforce these rules.

# Portable character and data banks

Data mode maintains reusable content independently of a world. It supports extraction, listing, additions, updates, explicit removals and integration into a destination world. A character bank is one use; the same format holds trackers, triggers, instruction/keyword blocks, scripts, specialist instructions or mixed bundles. This is a kit interchange format, not an IW import format.

## Select the operation

Use the user's existing bank or library when supplied. Preserve unrelated entries, unknown fields, native IDs, string contents and value types. Adding something to one world does not update its source bank; omitting a module does not delete it. Remove entries only on explicit request, checking dependent entries first. Do not silently overwrite or deduplicate entries with matching names.

Tags are optional. Ask or infer the stated preference: no tags, supplied tags, or suggested tags. When suggestions are wanted, derive them from the content and follow existing vocabulary/capitalization if desired. Store tags as plain strings and display them as [fantasy] [merchant]. Tags organize the bank; they are not automatically IW keywords or native fields. Do not retag existing entries without a request.

In Build, Edit, Review or Debug, recognize cohesive reusable content and offer extraction when useful. A shop's accounting tracker, instructions and purchase triggers may form a bundle; unrelated nearby objects do not. Explain what belongs together and let the user choose extraction. Prefer one stored component plus included-entry references over duplicating shared dependencies.

## Authoritative data and readable presentation

The `.txt` bank has a generated readable index followed by one authoritative JSON section. Summaries and [tags] make it easy to browse, but never reconstruct native data from summaries. The section is delimited by full lines `<!-- BEGIN IW DATA BANK -->` and `<!-- END IW DATA BANK -->`, contains one `json` code fence, and ends with `SHA256: <hash>` on the following line, or `SHA256: UNVERIFIED` when no code-based hash was computed. The hash covers the canonical authoritative data, not the index. This is transport integrity, not proof of provenance or gameplay correctness.

The authoritative object has `format: "iw-data-bank"`, integer `version: 1`, and an `entries` array. Other metadata is preserved. Each entry contains:

| Field | Purpose |
| --- | --- |
| id | Stable bank identity, separate from every native IW ID |
| title, kind, summary | Human-readable name, content type and optional summary text |
| tags | Optional list of strings; omit when unused |
| dependencies.included | IDs of other entries present in this bank |
| dependencies.external | Required objects, variables or context not included |
| dependencies.unresolved | Concrete questions or remaining dependency review |
| components | One or more objects with kind, optional sourcePath, and complete payload |

`payload` stores the original JSON value, including unknown keys and nested content. A standalone script can use a string payload and metadata identifying its context (Run Script, predicate or template) and required variables. An NPC or tracker stores its complete native object. A bundle stores multiple components; its `kind` is `bundle`. Keep sourcePath as an escaped JSON Pointer when extracted, such as `/NPCs/0` or `/triggerEvents/2`. Paths record provenance, not a command to overwrite that position in another world.

Retain the original native payload during PC/NPC conversion. Create the requested counterpart as a distinct component or entry, mapping appropriate identity, appearance and narrative information into its native fields. PC skills/selection fields and NPC activation/image fields are not interchangeable. Report newly supplied defaults and preserve unmapped source information; do not claim the conversion is a lossless relabeling. IW can offer the same canonical name as both PC and NPC without exclusion prose.

## Dependencies and application

Record dependencies as included, external or unresolved. Native IDs can be checked statically; variable roots, prose references and dynamic paths require review. The export helper does not automatically infer them and marks dependency review as unresolved. A physically complete export is not proof of a self-contained mechanic.

To apply entries, inspect the destination and preserve its unrelated content. Resolve native IDs, variable names, skills, activation requirements, ordering, starting values and referenced blocks. Remap collisions consistently; never run a blind global string replacement. Keep bank IDs unchanged. Report adaptations, additions and unresolved dependencies, and validate the complete destination world. A source bank remains unchanged unless its update was requested.

## Full-content build report

Offer this optional deliverable whenever outputting a world. It is a portable report of all fields and objects, not a prose inventory: export the full world, including metadata and unknown fields, with a restoration layout and source fingerprint. It can later supply selected entries or restore the original world definition. It is separate from the Authoring report containing explanations, substitutions and verification notes.

A complete report retains array ordering, empty containers and root fields. Bundling components does not remove their source paths. Removing or changing components invalidates exact restoration; integrate such edits deliberately rather than changing the fingerprint to conceal differences. This is JSON-data equivalence, not byte-for-byte preservation of whitespace, key formatting or numeric spellings. Scripts and other string contents remain exact.

## Tool workflow

Run from the kit root; no third-party Python dependencies are required:

```sh
# Full-content report; restores the complete world definition.
python tools/data_bank.py export World.json --out Build-Report.txt
python tools/data_bank.py check Build-Report.txt
python tools/data_bank.py restore Build-Report.txt --out Restored-World.json

# Selected objects; repeat --select and optionally --tag.
python tools/data_bank.py export World.json --select /NPCs/0 --out Character-Bank.txt --tag fantasy

# A selected mechanical bundle; review its dependencies before reuse.
python tools/data_bank.py export World.json --select /trackedItems/0 --select /triggerEvents/0 --bundle "Shop system" --out Shop-Bank.txt

# Edit authoritative JSON with tools, then rebuild presentation and hash.
python tools/data_bank.py unpack Character-Bank.txt --out Bank-Edit.json
python tools/data_bank.py pack Bank-Edit.json --out Updated-Bank.txt
```

Output paths must be new; the tool refuses silent overwrite. Check the updated bank, preserve a prior copy, and return the complete new file. For a manual merge, unpack both, retain entries and dependencies, resolve conflicting bank IDs deliberately, then pack the combined data. Do not carry a completeWorld restoration claim into a bank combining different sources; retain relevant source metadata per entry instead.

The helper rejects duplicate JSON keys, checks bank structure and included-entry targets, and verifies hashes for text banks. It preserves arbitrary-precision integers and decimal numbers without float rounding. Its hash check does not validate IW payload schemas, semantic dependencies, tags or prose summaries; use the world validator after integration. Unknown bank metadata is preserved.

Without code execution, use the same `.txt` format with `SHA256: UNVERIFIED`, or return the authoritative `.json` bank source with readable discussion separately. Never fabricate a hash or claim round-trip verification. The helper accepts either form, explicitly distinguishes an absent hash from verified integrity, and computes a hash when packing. Large edits should preserve untouched payloads and be checked with tools before claiming losslessness. An upload does not guarantee persistent storage: keep the latest returned bank for future sessions.

# Trackers and memory

Trackers: `name` is the display label, `id` connects native references, and `variableName` supplies the PawScript root.

“Coins” can have display name `Coins`, variable name `coins`, a unique tracker ID, initial value "10", and `autoUpdate: false`. PawScript reads $coins; native effects target the tracker ID. Purchases change the live value, while the base world's initial value remains the starting configuration.

## Storage, visibility and ownership

Use the dataType vocabulary `text`, `number`, `yaml`, `xml`; do not emit an invented boolean/list dataType. Structured booleans/lists can live inside YAML. UI terminology and storage types are not automatically identical.

Tracker `initialValue` is a JSON STRING even for numbers and YAML: `"10"`, or `"held: 0\nuses: 3\n"`. YAML content inside that string has its own parsed numbers, strings, lists and records. IW text entry does not enforce numeric-only input, but a mathematical tracker should start from an actual numeric literal. This does NOT make the entire export string-valued: JSON booleans, arrays and numeric fields elsewhere retain schema types.

Initialize every mechanical path explicitly. Distinguish 0, false, empty text, an empty list, an absent key and null. Define each value's meaning consistently; numeric 0/1 is one practical flag convention. Narration must not reinterpret a stored value to justify a conflicting story. Treat missing required data as malformed/denied unless the design explicitly defines a fallback.

Ownership:

| Tracker role | autoUpdate | Typical use |
| --- | --- | --- |
| Mechanics | false | Inventory flags, money, HP, counters, access, scores, RNG results |
| AI request record | true | Current-turn classification of what the player explicitly requested |
| Soft narrative memory | true | Introductions/observed scenery, when needed and bounded |
| Script staging/cache | false | Prepared active-block text, temporary results, status |

Do not let the AI and scripts compete to rewrite the same mechanical YAML document. Consolidating related flags in a YAML tracker reduces editor clutter; it does not by itself reduce trigger count or guarantee lower token cost. Large AI-visible YAML and duplicative logs still cost context. Keep hidden cache text out of the storyteller unless needed.

Visibility values include everyone (player and AI), ai_only and ai_only_boring (AI-only), player_only, hidden and hidden_boring (hidden from player and AI in supplied uses). Do not infer additional UI highlighting behavior from the suffix alone. The editor clears "Hide in Storyteller mode" when player visibility is enabled. Do not invent contradictory UI combinations. Exports can include hidden trackers and secret information when Storyteller Mode is enabled; select those export options when collecting diagnostics. Visibility is not script access control: hidden values remain script-usable at runtime.

Starting values:

- initialValueBasedOnPC same: one initialValue for all PCs.
- character: per-character initialTrackedItemValues entries target the TRACKER ID. Fixed initialPCValue is a string. A fixed single-choice list is an array of strings. A script-generated list uses initialPCValueChoicesScript with initialPCValue empty, as illustrated in ../examples/character-starting-values.json. The expression is evaluated at game start with initial trackers and that PC's skills available, per editor description.
- player: the tracker itself defines a player-chosen startup value. ../examples/optional-block.json exports initialValueBasedOnPC: "player", initialValue: "On", and initialValueChoices: ["On", "Off"]. These are tracker-level fields, independent of per-character initialTrackedItemValues. Use this for an offered startup preference; autoUpdate false prevents AI rewriting it. The user can edit the live preference later. For unconstrained player input or an unusual type, do not assume the choice-list example establishes every corresponding UI control; obtain a representative export only for that additional variant.
- Never combine arbitrary fixed/list/script modes and guess precedence. Do not assume formatSchema is JSON Schema or enforces semantic intent; its exact enforcement language is not established by our sample fields.

Intentional name differences: When creating a tracked item, if variableName differs from name, set driftAcknowledgedForName to the exact current name. This acknowledges the intentional difference and suppresses the editor's mismatch indicator; it does not rename the variable or change script references. When editing an existing tracker, preserve its acknowledgement unless the user authorizes a change. If an unacknowledged mismatch is noticed, explain it and offer to acknowledge it; do not silently rename the variable or suppress the indicator.

## Memory, continuity and context cost

Recent story text, summaries, active instructions and tracker values serve different roles. Summaries compress history; they can omit incidental details or distort elapsed time. Use summaryRequest to preserve categories important to this particular world, and trackers for persistent facts that need a stable home. Avoid duplicating the whole story in a growing tracker. Set useful bounds on journals and cast records.

If a bad turn establishes a false fact, adding an instruction may leave conflicting history in place. Where the player's tools permit, editing or rewinding that turn can be cleaner than asking later prose to reconcile it. No correction engine is required by default.

Native trigger changes can affect runtime instructions without changing the base editor definition. Inspect active instruction contents and trigger/debug results when troubleshooting; a base-world export alone does not show everything the model received. Base and live worlds are separate copies.

Keep loaded instructions and AI-visible tracker names, descriptions, update rules and values purposeful. Prefer concise shared rules over repetition, keyword activation for occasional lore, and PawScript for exact calculations. Large AI-updated records can be expensive to rewrite. Inspect actual state and rendered instructions rather than assuming hidden prompt contents. Summary compression follows a six-turn cadence beginning at turn eight, as confirmed by the user; exact summary contents remain unavailable.

Alternate selectable protagonists can also have NPC cards if unchosen protagonists should appear in the story. A selected player sharing an Other Character name can use information from that entry. Internal identity merging or exclusion is not visible; do not promise automatic same-name NPC exclusion.


## Current visibility, updates and validation

[RUNTIME] Extra-hidden values remain visible in the Storyteller tracker editor even when Include Extra-hidden is off. Import normalizes automatic updating off for hidden, hidden_boring and player_only; everyone, ai_only and ai_only_boring can retain automatic updates. Full AI prompt inclusion is a separate unresolved boundary.

Enforce format does not prevent all malformed manual/script writes. Use explicit shape and semantic checks before accepting generated state. Native path adjustment and script assignment have different missing-path behavior; do not generalize one write mechanism to all others. Independent random expressions can disagree; cache shared choices.

A trigger can change future automatic updating through Modify tracked item details with overrideAutoUpdate and autoUpdate. Initial values remain configuration, not current state. See [Editor-UI](Editor-UI.md) for current-value editing and [Verified-Behavior](Verified-Behavior.md) for forms, initialization and retention results.

# Triggers and effects

A trigger combines eligibility rules with effects. Conditions checked in a processing pass; if they pass and its repeat/prerequisite rules, its effects run. Ordinary triggers are processed in triggerEvents array order. Enabling repeat allows the trigger to fire again whenever eligible; condition not required to become false between firings.

That last distinction matters: “HP below 5” with repeat enabled can fire every turn while HP remains low, not a “just crossed below 5” event.

## Composition and sequencing

Each trigger has id, name, triggerConditions, triggerEffects, and explicit timing/repeat flags. Conditions are a list of nodes; the normal list is AND. A leaf uses `category: "condition"`, `type` and `data`. A logic node uses `category: "logic"`, operator and a data ARRAY of child nodes. Known operators: and, or, none_of. A logic group is not a leaf with type "or".

Use a combined PawScript condition and sequential script when they make calculation or transaction clearer. Simple native conditions and effects remain appropriate. Keep separate triggers for phase boundaries or cross-effect dependencies. Give Scripts meaningful names describing effect; avoid generic "Update State." The owning trigger's name is useful when it describes effect. Clear script names make error reports easier.

A one-time reward can require quest_complete = 1 AND reward_claimed = 0. Its effects grant the reward and set reward_claimed = 1. An OR group could instead accept either of two qualifying quests. none_of passes when none of its child conditions pass. A state guard prevents repeated grants even if the trigger is repeatable; a one-shot trigger additionally records that it has already fired.

Exact payloads and native comparison vocabulary are in Schema.md and ../examples/Payloads.md.

### Timing guidance:

| Intent | Start | Mid Game | Repeat | Conditions |
| --- | --- | --- | --- | --- |
| One-time setup before opening | true | false | false | None, or a setup predicate |
| Setup and every ordinary turn | true | true | true | None, or predicates checked on each pass |
| Fire once when eligible, including setup | true | true | false | Required predicates |
| Fire once when eligible after opening | false | false | false | Required predicates |
| Fire repeatedly when eligible after opening | false | false | true | Required predicates; add state guards where needed |
| Saved/inactive trigger | false | false | As intended | None; explicit dispatch is separate |

Start enables pre-opening evaluation; additional conditions still apply except for the incompatible condition types noted below. Mid Game extends a Start-enabled trigger to ordinary turns. With Start disabled, ordinary conditional triggers do not require Mid Game.

Repeat permits subsequent firings; it does not require conditions to become false between firings. Start + Mid Game + Repeat can execute before the opening and again during turn 1, so guard counters and other effects that should run only once per turn.

With Start false, Mid Game has no effect; a stored true value requires no warning or repair. A trigger with no conditions and Start false does not fire automatically, but can remain available for explicit dispatch.

- Prerequisites/blockers with firedThisTurn true are ordered this-turn checks, resetting on subsequent turns; false uses game history. Order matters. The editor disallows requiring and blocking the same trigger; do not generate that conflict.
- Defaults are not a contract: always serialize canTriggerMoreThanOnce and the timing flags intentionally. Use repeatable commit triggers with idempotent state guards where appropriate, and true one-shot events when required.
- Restriction: Do not combine Start of Game with Scenario or minimum-turn conditions. The editor warns that these conditions are ignored; minimum-turn bypass is confirmed during both startup and mid-game execution. Use a separate startup trigger and leave Start off on the conditional trigger. Scenario runtime behavior remains unverified.

See Schema.md for native effect payloads and input options. Scripts change trackers; native effects change instructions, objectives and other system properties.

### Execution order and effect semantics:

1. Later triggers see earlier committed writes. AI-updated request trackers were available to that turn's trigger checks. Correctly bound Present Choice/Request Input results are available to subsequent triggers in the same turn. This does not describe every internal generation stage.
2. Native numeric Set/Add effects within ONE trigger do not accumulate normally: starting at 0, add 2 then add 3 ended at 3; starting at 1, set 5 then add 2 ended at 3. Reads can nevertheless see changed values. Do not "explain" this with a universal snapshot rule; internals are unproven.
3. Run Script is different: sequential set/add and repeated arithmetic DID accumulate, nested YAML changes preserved unrelated keys, and separate script effects writing different YAML paths preserved both. Tested script failures rolled back that script's changes. Do not claim a whole-trigger rollback covering earlier successful effects.
4. For dependent operations prefer one script. Otherwise put preparation in one trigger and consumption in a following trigger. Do not assume a later native effect's expression sees an earlier native write merely because it appears lower in the same trigger.
5. Native text additions stacked; removal removed all matches and literal quotes are retained. Do not apply numeric overwrite behavior to text or script statements.
6. First guidance appeared to dominate in limited narrative-only tests. Generate one coherent, mutually exclusive guidance outcome rather than contradictory directives whose priority you hope to control.

## Choosing Implementation:

| Approach | Best suited to | Main trade-off |
|---|---|---|
| Instructions and AI-updated trackers | Narrative judgment, descriptive state and flexible interactions | Outcomes depend on model interpretation; unsuitable for guaranteed arithmetic or enforcement |
| Native conditions and effects | Simple rules, editor-friendly customization and platform operations | Repeated cases can require many entries; native effect sequencing needs care |
| PawScript | Exact calculations, structured state, collection operations and repeated logic | Requires code maintenance; only supported writable values can be changed |
| Hybrid | Calculated outcomes combined with messages, block updates, opening changes or other native operations | Requires explicit ordering between calculation and application |

Native comparisons and PawScript conditions are both evaluated mechanically. Neither inherently makes narration more reliable. Use AI instructions to explain the intended behavior and deterministic conditions/scripts where exact enforcement matters.
Consolidate repeated logic when it improves clarity, but preserve meaningful execution stages and useful debugging boundaries. Consider where content is stored: moving inactive trigger payloads into AI-visible trackers can increase context cost. Performance gains from consolidation require measurement.

# PawScript working reference

PawScript reads game data, computes values and updates trackers. It is its own language, not JavaScript or Python. Start with sections 1-3 when learning; use the later tables for lookup. Examples use declared tracker variable names, not display names or IDs.

## 1. Where PawScript runs

| Context | Example | Purpose |
| --- | --- | --- |
| Template in supported text field | `Coins: <<$coins>>` | Insert result into text; no mutation |
| PawScript trigger condition | `$coins >= 5` | Return true/false; no mutation |
| Run Script trigger effect | `$coins -= 5` | Execute statements, save changes |

An **expression** returns a value. A **statement** performs work, such as assignment or a loop. Script conditions are still expressions: the test after `if` decides whether its indented statements run. Use bare code in trigger conditions and Run Script, without `<<...>>` or Markdown fences.

PawScript cannot write arbitrary world fields, including background or instruction-block content, or invoke native trigger effects. Calculate or assemble content in trackers, then use native effects to install it or display messages. Templates do not expand write permissions. `$player` and `$game` are read-only; do not infer writability from a field being readable.

A script changes state only when it executes. It does not automatically enforce what the storyteller narrates. Trigger timing and template installation timing are described in [Triggers.md](Triggers.md) and [Capabilities.md](Capabilities.md).

## 2. Values, trackers and scope

Create a tracker before referencing it. Its `variableName` supplies the root: a tracker named Party with variable name `party` is `$party`. A script assignment does not create a missing tracker.

| Value shape | Example | Access |
| --- | --- | --- |
| Number | `12` | `$coins` |
| Text | `"Open"` | `$status` |
| Boolean | `true` or `false` | `$state.ready` |
| List | `list("red", "blue")` | `$colors.item(1)` |
| Record (named fields) | YAML below | `$hero.name` |

List positions are **1-based**. A record uses keys, not positions. A list of records represents several objects; a record containing lists represents one object with collections.

For example, this YAML initializes one record:

```yaml
name: Mira
hp: 4
tags:
  - scout
  - injured
```

Stored in tracker `hero`, it provides `$hero.name`, `$hero.hp` and `$hero.tags`. YAML indentation defines nesting; `[]` initializes an empty list and `{}` an empty record. Quote numeric-looking identifiers such as `"001"` to preserve leading zeros. Use YAML `|` for multiline text. In an export, `initialValue` is a JSON string containing this YAML, not a JSON object. `formatSchema` is a separate shape description; see [Trackers.md](Trackers.md).

Persistent roots use direct assignments: `$coins = 12`. Temporary locals use `set $price = 5` and last only for that script run. Do not give a local the name of an existing tracker. Inside collection predicates, bare field names refer to the current member; `$...` refers to a tracker/system root or script local. For a list of plain values, `value()` denotes the current value.

## 3. A complete small example

Create a YAML tracker named Party with variable name `party`, initial value below, and automatic AI updates disabled for this mechanically managed example:

```yaml
- name: Mira
  hp: 4
  max_hp: 8
- name: Oren
  hp: 8
  max_hp: 8
```

**Read:** put `Injured members: <<$party.where(hp < max_hp).count()>>` in a supported template field.

The chain reads left to right:

1. `$party` is the whole list.
2. `.where(hp < max_hp)` selects injured members. Each comparison uses that member's fields.
3. `.count()` returns the selection size. This reads data; it does not heal anyone.

**Test:** a PawScript trigger condition can use `$party.any(hp < max_hp)` to decide whether healing is needed.

**Change:** a Run Script effect can restore every member:

```text
for each $member in $party
  $member.hp = $member.max_hp
```

The loop variable refers to each original member, so assignments persist in the tracker. After execution, both members have full health and the injury condition is false. Inspect tracker data to verify this; no visible story output is required. Add a native message effect if the player should receive confirmation.

Use the expression/script Sandbox to try the read and change separately. For an in-game trigger, also configure timing and repeat behavior; see [Triggers.md](Triggers.md). To practice, change the condition to detect a member at zero health, then predict the result before running it.

## 4. Expressions and decisions

| Operation | Syntax / meaning |
| --- | --- |
| Arithmetic | `+ - * / % ^`; `%` is remainder, `^` is exponentiation |
| Comparison | `= != < <= > >=` |
| Logic | `and`, `or`, `not`; parenthesize mixed tests |
| Text concatenation | `"Coins: " & $coins`; numbers become text |
| Conditional value | `if($coins >= 5, "Affordable", "Too expensive")` |
| Value mapping | `choose($status, "open", "Enter", "locked", "Find a key", "Inspect")` |
| Missing/blank fallback | `first_available($hero.nickname, $hero.name, "Stranger")` |
| Error fallback | `try($total / $count, 0)`; do not use it to conceal broken essential state |
| Existence | `$hero.nickname.exists()`; distinct from being nonempty or nonzero |
| Numeric bounds | `$hp.constrain(0, $max_hp)` |
| Rounding | `round_down($cost)`, `round_up($cost)`, `$cost.round()` |
| Text normalization | `$label.replace("_", " ")` |

`=` compares within an expression and assigns in an assignment statement. In the following script, the first `=` tests; the second writes:

```text
if $status = "locked"
  $status = "open"
```

`and` and `or` short-circuit. A left-hand guard can prevent an unsafe right-hand read. Functions require parentheses: `.count()` calls a function; `.count` reads a field named count.

A statement-level branch changes data, unlike expression-level `if(...)`, which returns a selected value:

```text
if $coins >= 5
  $coins -= 5
  $purchases.total += 1
else
  $message = "Not enough coins."
```

Declare `coins`, `purchases` (including `total`) and `message` first. Use `else if` for additional branches, at the same indentation as `if`. `#` starts a script comment; instruction-text comments use `<#...#>` instead.

## 5. Collections: select, calculate, change

### Read and select

| Need | Expression |
| --- | --- |
| Construct a list / empty record | `list("red", "blue")`, `list()`, `record()` |
| First item / first few | `$party.first()`, `$party.first(3)` |
| Last item / recent subset | `$history.last()`, `$history.last(3)` |
| Dynamic record lookup | `$catalog.item($selection)` |
| Lookup with read fallback | `$reputation.item($faction, 0)` |
| Record keys / values | `$catalog.keys()`, `$catalog.values()` |
| Key or value membership | `$catalog.contains($selection)` tests a record key; `$tags.contains("scout")` tests a list value |
| Matching records | `$party.where(hp < max_hp)` |
| Matching plain values | `$tags.where(value() != "retired")` |
| Any / every / none | `$party.any(hp > 0)`, `$party.every(hp > 0)`, `$party.none(hp > 0)` |
| Project fields | `$party.all().name`, `$party.where(hp > 0).name` |
| Total a field | `$party.sum(hp)` |
| Largest field value | `$party.max(hp)` |
| Member with largest value | `$party.max_by(hp)`; append `.name` to read its name |
| Sort by a field | `$party.sort_by(hp, desc).all().name` |
| Remove duplicate values | `$tags.unique()` |

A selection can contain several members even when you expect one. Use stable unique keys when identifying an object. Guard empty selections before requesting a member. `every(...)` is true for an empty list; add a count check when your rule requires at least one member.

Within filters, `name contains "fire"` tests the current member's field; `id in $unlocked` checks membership in an outer list. Bare `in` is filter syntax, not a general replacement for `.contains(...)`. For example:

```text
$abilities.where(id in $unlocked).all().name
```

An advanced predicate can check named requirements:

```text
$requirements.every($flags.item(value(), 0) = 1)
```

Initialize `requirements` as a list and `flags` as a record. An empty requirement list passes; a missing flag uses zero and fails. Missing structure and empty structure are different cases.

### Write and mutate (scripts only)

| Need | Statement |
| --- | --- |
| Assign a field | `$hero.hp = $hero.max_hp` |
| Update a dynamic key | `$reputation.item($faction) = $reputation.item($faction, 0) + 1` |
| Append an entry | `$entries.append($new_entry)` |
| Remove a record key | `$catalog.remove($selection)` |
| Remove every equal list value | `$tags.remove("retired")` |
| Remove selected members | `$party.where(hp <= 0).remove()` |
| Replace matched records | `$entries.where(id = $update.id) = $update` |
| Persist a transformed list | `$tags = $tags.unique()` |

A read such as `$tags.unique()` does not change stored tags by itself. Assignment persists its result. Appending a list appends its members; it does not wrap them as a nested list. Replacement of matched records is not a field-preserving merge: include every field to retain. Native text add/remove effects are not substitutes for structured list mutation.

To construct an entry, create a local record, fill its fields and append it:

```text
set $entry = record()
$entry.id = "supply-cache"
$entry.name = "Supply Cache"
$entries.append($entry)
```

Initialize `entries` to `[]`. Repeating this script adds another entry; add an identity check if duplicates are unwanted.

Loops can iterate lists or records; `range(n)` supplies a bounded repetition list. Keep mutations straightforward. Library buffer examples remove processed entries while iterating; do not assume every different mutation loop is equally safe. For new update-buffer designs, iterating updates and clearing the buffer afterward is easier to reason about. Test new complex selection/mutation chains in Sandbox.

## 6. Randomness and formatted output

| Need | Expression |
| --- | --- |
| Numeric random value | `random()` |
| Inclusive integer range | `random_between(1, 6)` |
| Dice sum | `dice_roll(6, 3)` or `3d6` |
| One random list member | `$encounters.random()` |
| Several without repeats | `$encounters.random(3)` |
| Shuffle | `$encounters.shuffle()` |
| Text with expressions | `format_text("Coins: {$coins}")` |
| Join list values | `$names.join(", ")` |
| Format each record | `$party.format_each("{name}: {hp}/{max_hp}").join("\n")` |
| Numbered / bulleted output | `$names.numbered_list()`, `$names.bulleted_list()` |

`dice_roll(sides, count)` defaults to six sides and one die. Every random evaluation can produce a new result. Store a shared roll once when several checks or outputs must agree:

```text
$roll = dice_roll(6)
if $roll >= 4
  $result = "Success"
else
  $result = "Failure"
```

Declare `roll` and `result` first. An inline block can instead say `Encounter roll: <<dice_roll(6)>>`, but that only supplies a number; instructions or deterministic effects must define its consequences. Permanent block templates and templates installed through block effects can evaluate at different times; see [Capabilities.md](Capabilities.md).

Inside `format_each`, `{name}` reads the current member's field, `{$coins}` reads an outer tracker, and `{value()}` reads a plain list member. `index()` supplies a 1-based position. These braces belong to formatting functions; they are not a replacement for outer `<<...>>` template delimiters.

Additional presentation helpers include `.bold()`, `.italic()`, `.code()` and `.format_date(...)`. Formatting produces display content, not styling guarantees in every UI field. `now_utc()` and `now_local()` report real-world time, not the story's clock. Consult the official reference for date tokens and less common numeric/string functions.

## 7. Execution and debugging

1. Declare trackers and initialize every required structure. Give mechanically managed values one update owner or an explicit AI/script handoff.
2. Test a read-only expression first. Confirm the selected records and values before mutating them.
3. Run the script against known starting data in Sandbox; inspect the resulting trackers.
4. Test it in its trigger. Confirm timing, condition eligibility and order, not only script syntax.
5. Check repeat execution and boundary cases: no matches, insufficient resources, missing optional fields and already-completed work.

Statements in one script execute sequentially. Later triggers see earlier committed writes. Multiple native numeric effects in one trigger can overwrite rather than accumulate; they do not share script statement semantics. A script failure rolls back that script's changes, not preceding effects or the entire turn.

Use `log("Coins: {$coins}")` for diagnostics in the PawScript Log. Logs are not player narration; messages logged before a failure remain useful for locating the problem. "Ran successfully, with no output" is normal for assignments. A model saying PASS is not runtime verification.

Enable Menu > Settings > Storyteller Mode, then open the bug icon beside tracked items. Inspect tracker state, evaluated conditions and script errors; use Open in Sandbox to isolate a script. See [Capabilities.md](Capabilities.md) for wider debug coverage.

The validator's lint is heuristic, not a PawScript interpreter. It checks likely mistakes, roots and locals with limited static analysis; passing it does not prove runtime behavior. When teaching or reporting tests, distinguish documented syntax from compositions actually run in IW.

## 8. System roots, escaping and common mistakes

Read Skills with `$player.skills.<slug>` and display them with `$player.skills_and_levels`. `$game.skill_map` maps slugs to display names. Other roots include `$player.name`, `$game.turn_number` (opening turn is 1), `$game.ai_model`, `$game.skill_list` and `$game.difficulty_list`. Native skill effects change levels; scripts do not write `$player`. Runtime narration fields and video placeholders are separate concepts, not automatically script roots.

| Mistake | Use instead |
| --- | --- |
| `$coins == 5` | `$coins = 5` in a condition |
| `a && b` / `a || b` | `a and b` / `a or b` |
| `if $coins > 0:` | No colon; indent the following statements |
| `"Coins: " + $coins` | `"Coins: " & $coins` |
| `$new_tracker = 1` without declaration | Declare the tracker; `set $local = 1` is temporary only |
| `<<$coins -= 1>>` | Mutation belongs in Run Script |
| `.count` to count members | `.count()` |
| Host-language object literals or arrow functions | `record()`, field assignments and supported collection methods |
| Writing background, blocks or system roots | Use the supported native effect |

Escaping has three layers: JSON serialization, PawScript string literals, and rendered text/YAML. Use a JSON serializer. A physical newline separates script statements; the two-character `\n` inside a script string represents an intended text newline. For example, the decoded script:

```text
$message = "Ready\nProceed"
```

has this JSON string representation:

```json
"$message = \"Ready\\nProceed\""
```

Inspect decoded code when debugging escapes. Include spaces explicitly when composing text with numbers. Do not add host-language semicolons, statement braces, arbitrary libraries or external IO.

## Verified guards and scope boundaries

Native And/Or groups and PawScript boolean expressions short-circuit in order. Existence guards should precede dependent reads; supported fallback/try operations handle missing values but do not permit expressions in invalid contexts. current() is rejected in Run Script and lacks a supported positive List Update context in the current editor.

Boolean-expression results can serialize as quoted text, so rendered output is not strict type introspection. No measured speedup follows merely from short-circuit support. ## Turn lifecycle [RUNTIME]

This is an authoring model of the established boundaries, not a trace of IW internals:

```mermaid
flowchart TD
    I[Initial values and opening setup] --> G[Generation with current context]
    P[Player input] --> G
    G --> U[AI tracker updates available]
    U --> T[Triggers evaluated in order]
    T --> E[Effects and player messages]
    E --> N[Updated context for later generation]
    N --> P
```

- Start+Mid+repeat triggers can execute in a pre-opening setup pass and again during the first normal turn. Messages from the setup pass appear before the opening background. The value of $game.turn_number during setup is not established. Guard initialization and counters according to the intended behavior.
- During normal turns, generated tracker changes are available to trigger conditions. Ordered triggers can see earlier trigger writes. The practical order to author is the `triggerEvents` array; preserve it and verify editor reorder/export behavior if changing order through the UI.
- Scenario judgments must be available for their trigger checks, but their exact production stage relative to Evaluation, narration and tracker updates is not mapped. Do not place them at a fabricated precise point in the diagram.
- Messages belong to their effects; they need not be a single final batch after all triggers. Choice/input effects can suspend for a player answer. Correctly bound single-answer forms update immediately and permit later triggers to read the answer in the same turn.
- Guidance and block changes do not rewrite already-generated narration. Updates supply context for subsequent generation. The precise persistence/priority of competing guidance is not a stable contract.
- Summary generation is a separate context-maintenance process. Its exact turn schedule and ordering are not established here.

## Skills and player characters

Root `skills` is a list of display names. Each possibleCharacters entry has a `skills` object keyed by those names, with integer levels. Define focused skills with distinct jobs; overlapping names can make the evaluator's choice ambiguous. Example: Observation, Persuasion and Engineering. PC `description` establishes identity, abilities and context; it is not just selection-page decoration. `charSelectText` introduces the available choices to the player. The allowChangeCharacter* flags control which parts players may customize.

Keep at least one skill. `hideSkillSystem` hides the skill system's presentation; it is not evidence that all evaluation of abilities is disabled. A neutral generic skill is appropriate when the story does not need custom skill distinctions.

PawScript exposes `$player.skills`, `$player.skills_and_levels`, `$game.skill_map`, `$game.skill_list`, `$game.skill_example`, `$game.difficulty_list` and `$game.difficulty_example`. The skill map connects runtime slugs to display names. The documented difficulty names are Trivial, Easy, Medium, Hard and Legendary; use the supplied runtime list when rendering prompts rather than inventing numerical modifiers. Official documentation describes a default level of 3 for skills not raised. Explicitly initialize authored PC levels rather than depending on that fallback. Do not invent slug normalization for punctuation-heavy names. [PawScript reference](https://infiniteworlds.app/pawscript-reference)

Native `effectChangePCSkill` uses the declared display name. `amount` is an integer magnitude; `increase: true` increases toward `minmax` as an upper cap; false decreases toward it as a lower bound. Two successive triggers increasing a level initially 2 by 2 up to 4, then by 1 up to 4, finish at 4. This differs from adding both increments and applying no intermediate cap. The included probe also checks decreases and boundary cases.

Skill levels are fixed integers from 0 through 5. The AI selects the available skill whose name best matches the attempted action; name skills so their scope is clear.

`Default-Evaluation.txt` contains the editor-provided baseline verbatim. It asks for a brief assessment, skill/difficulty and DENIED, SUCCESS, FAILURE or PARTIAL_SUCCESS. Trivial uncomplicated actions succeed; impossible assertions can be denied. Otherwise proficiency, difficulty, character history, instructions and common sense inform the judgment. Partial success covers incomplete achievement, failure with a silver lining, or success with drawbacks. No numerical success-probability table is established.

Use actual numeric skill values for mechanical checks. Generated skill labels and Evaluation descriptions can disagree with those values; a prose description is not authoritative numeric state.

The baseline was captured from the custom-Evaluation editor's prefilled text. The test used that text explicitly. The Script Library's Storymaster override defines its own caveat labels; keep it distinct from the baseline.

# Feature recipes

These are independent recipes. Select, adapt or omit them; none is a required world architecture.

**Narrative instructions plus AI-updated trackers.** A relationship, journal, outfit, reputation or story-preference tracker can update from the ongoing story without an explicit mechanical action parser. Explain what belongs in it, when to add/change/remove entries, and what should remain stable. Match structured entries by stable identity or names/aliases as appropriate, not a list position that may change. Provide a useful format example; sample data must not silently become real world facts.

**A situation followed by a consequence.** Situation-trigger effects follow story generation; guidance does not retroactively rewrite the scene that caused it. If a behavior must shape that scene, provide the rule beforehand in active instructions.  Use triggerOnEvent for a narrative situation the AI recognizes, optionally AND a tracker/turn/prerequisite condition to narrow it. Effects might give background information, show a message, modify a value, change an objective, present a choice or alter an instruction block. Situation classification is probabilistic; use explicit predicates only for requirements that genuinely need exact enforcement. There is no requirement to replace ordinary actions with event codes.

**A threshold or dependency chain.** A relationship threshold can unlock a new characterization block; a turn condition can introduce weather or a letter; a prior event can enable another event. Intentional one-shot/repeat flags and firedThisTurn scope matter. Check order where the later trigger reads an earlier result. Avoid requiring and blocking the same trigger.

**Choice/input plus later effects.** Present a selection or text form targeting a real tracker, then respond with a later ordered trigger. Correctly bound single-answer forms update immediately. Inspect binding after import; use current tracker data rather than initialValue from the live-world editor export.

**AI update buffer plus scripted merge.** The library's update trackers let the AI propose changed structured entries, while a script merges them into a persistent list. This is useful for large casts or expensive long-lived records. Match records by identity; choose whether update entries are full replacement records or partial patches. A script replacing a matched record with a partial entry can lose unchanged fields; the selected updater instructions and implementation must agree. Only use this extra layer when it serves the world.

**Conditional instruction content.** Use a native block-modification effect to add/replace/clear instructions. The source may be fixed text in the effect or text prepared in a tracker by an earlier script trigger. This can control optional image guidance, pacing, prose detail, character behavior or any relevant block. A script changes tracker values; the native effect changes the instruction block. Keep the block ID stable when disabling content so later re-enabling still targets a real block.

**Player-optional block, with no repeated writes.** The companion optional example distills the supplied native demonstration:

1. A player-only text preference has initialValueBasedOnPC player, initialValue On or Off, initialValueChoices [On, Off], autoUpdate false. The player can change this live.
2. A hidden non-AI-updated text tracker records which choice has actually been applied. It is a cache, not another player preference. hidden_boring is used by the source example.
3. A repeatable enabling trigger requires preference On AND cache not Enabled. It writes the enabled block content, then records Enabled.
4. A repeatable disabling trigger requires preference Off AND cache not Disabled. It writes empty content, or a deliberately chosen simpler fallback, then records Disabled.
5. Enable opening and later execution where needed. Initialize the cache empty so the selected startup choice gets applied. Once synchronized, neither trigger fires until the preference changes.

Clearing content is not deleting the instructionBlocks entry. Use `content: ""` as in ../examples/optional-block.json. If disabling a bundle that also changes authorStyle or specialist rules, restore ALL affected behavior to a coherent fallback. For a Storymaster toggle, define an off configuration that uses ordinary narration and no Storymaster-specific specialist or tracker dependencies. The generic toggle example demonstrates the mechanism, not a complete Storymaster toggle bundle.

Player-visible preference trackers may be hidden from the storyteller; the triggers read them deterministically. Describe their effect and potential turn cost to the player. Do not create an AI-updated tracker that changes the player's own choice back.

**More exact mechanics when requested.** Script-owned numbers, independent prerequisite checks, a request-classification tracker or a controlled transaction may be useful for a precise system. They are options for that feature, not default requirements for the world. If used, define who updates each value and avoid competing AI/script ownership of the same data. Freshness stamps matter only if consuming an AI-generated per-turn request; they are not mandatory for ordinary narrative trackers.

**Time and location: a soft default.** Offer the sample's Time and Location (whereWhen) block unless the premise makes a clock/location header unhelpful. Writing the current place and time each turn helps IW maintain chronology and gives the player a reference. Adapt the geography, calendar and precision to the setting; omit irrelevant levels rather than inventing a country or continent. Put exactly one header at the beginning of outcomeDescription, not a second competing heading. This is guidance for runtime output, not a new JSON root field.

**NPCs and keyword blocks.** Native NPC cards provide structured character data and name activation. Keyword blocks load relevant lore based on mentions and recent context. Always-on blocks provide universal guidance. Choose by intended activation, not by habit; do not make all locations or characters dynamically loaded unless the world benefits. Native character/image bookkeeping may matter even when the narrative could be described in a normal block. For an opening scene, do not depend solely on keyword activation: there may be no prior context to activate a card or block. Put essential opening facts in firstInput or always-on instructions and give starting NPCs useful brief summaries. Avoid duplicating their entire cards.

secretInfo, outcomeDescription, whereWhen and option1_text/option2_text/option3_text are runtime output concepts, not arbitrary new root export fields. Their intended use can be described in instructions and specialist requests. secretInfo can legitimately contain secrets, planning and off-screen developments in narrative worlds; the Storymaster family explicitly structures it. Do not impose an empty-secretInfo policy or a reset system unless requested by that world's design. Its contents and purported "memory dumps" remain generated text, not direct access to an engine memory store.

Use ordinary Markdown formatting where appropriate. Tests showed raw span HTML rendered literally, so do not promise arbitrary HTML/CSS styling. Header behavior and special output formatting should be tested in their actual display context. An inline-code style is a platform-rendered style, not a general color API.

## Dynamic content
Native block-modification effects substitute templates when the content is installed. For live values, use a separate permanent block or reinstall content when the relevant values change. See Capabilities.md for the interpolation table.

**Player-selected layered openings.** Combine independent choices into meaningful variations using ordered text replacements, then install the result as background. This avoids authoring every full combination; keep fragments compatible and add combination-specific handling where needed. See [layered opening](../examples/recipe-layered-opening.json).

**On-demand generation with retained results.** Install a substantial generation brief only when needed, store a compact result, and clear the brief after a matching completed request. Do not clear merely because a turn elapsed. Prefer infrequent event-driven requests; retained tracker context and AI updates can outweigh the omitted instructions. See [on-demand generation](../examples/recipe-on-demand-generation.json).


## Request and commit example

In [recipe-request-commit.json](../examples/recipe-request-commit.json), the AI records the current requested event and turn stamp. The first trigger resets the receipt, not the unconsumed request. A later trigger checks freshness, then checks funds/ownership and commits a purchase or rejection. A following effect displays the receipt and clears the request; the receipt remains for next-turn continuity. Narration describes an attempt until the committed result is available. A freshness stamp prevents stale reuse, not incorrect classification. This pattern is optional: native choices, thresholds and timed effects do not need an AI request layer.

The [example index](../examples/index.json) records each complete world's purpose and verification scope. [Payloads.md](../examples/Payloads.md) supplies smaller native shapes. Remap IDs when combining worlds and validate the result; structural checks do not certify gameplay. Select examples by feature rather than imposing the showcase's architecture on every world.

# Import and reference integrity

An importable world needs both valid JSON structure and correctly linked objects. Tracker IDs, display names and PawScript variable names serve different purposes. Native effects target tracker IDs; scripts use variableName. Preserve IDs when editing, and remap every corresponding reference when combining examples.

## Identifier convention

Preserve existing IDs when editing. For new trackers, use a unique nine-character ASCII alphanumeric ID, following the editor-style form used by the import-tested examples. Use explicit descriptive snake_case variableName values in scripts and descriptive display names in the editor. This is the kit's authoring convention, not a claim that other ID formats are invalid or that length alone guarantees import behavior. Generate IDs in code and check collisions; without tools, check each newly introduced ID and reference manually. New triggers/blocks/PCs can use the same convention. When combining worlds, remap every explicit reference consistently.

The supplied single-choice world preserves its IDs and binding through a fresh import. Inspect native target dropdowns after importing a composed world; schema validation cannot predict importer behavior for every construction.

## Before import

- Serialize the complete world as JSON ending at its final closing brace, without a trailing newline.
- Run the validator on that exact file. Resolve missing or duplicate IDs and mismatched target references.
- Review native YAML paths against the tracker's declared initial structure and intended operation. The editor can accept unchecked paths without warning. Removing a nonexistent key or appending to a numeric path may be syntactically valid but semantically wrong. Dynamic paths may require runtime inspection rather than a blanket validation error.
- Review script references separately: structural validation does not execute PawScript or prove its paths exist.

## After import

Save and inspect affected target controls. An invalid-value target is a binding failure even if the original JSON had consistent references. Export the imported world and validate that export when diagnosing discrepancies. Preserve the untouched export before repairing a suspect target so source and imported IDs can be compared.

For a native input, confirm the current target value after submitting an answer. Correctly bound single-answer Choice and Request Input effects update immediately, and subsequent ordered triggers can read the result in the same turn. Their follow-up messages can render above the question/answer receipt. The live-world editor's initialValue remains configuration, not the current runtime value.

## Editing an existing playthrough

Base worlds and live games are separate copies. Changes to player characters or Other Characters in the live-world editor do not affect that playthrough; already-fired effects are not retroactively rewritten. Use Save as new world to reuse live-world edits in future games. Image-style changes can require save/reload before their export reflects the editor.

## Read-only source/import comparison

[import_audit.py](../tools/import_audit.py) compares original and native-exported worlds, preserves hashes and reports possible tracker identity changes plus references to removed targets. It never repairs or remaps automatically. See [Story tools](Story-Tools.md) for usage.

# Unresolved boundaries

Current through 2026-10-23. Verified conclusions are in [Consolidated behavior](Verified-Behavior.md); workflows are in [Editor and UI](Editor-UI.md). Partial research groups contain useful verified findings alongside specific unresolved boundaries.

| Area | Established result | Remaining boundary |
| --- | --- | --- |
| Prompt construction | Active instructions renders live templates and updates | Full historical storyteller/specialist prompts, hidden wrappers and exact inclusion/timing need authoritative prompt visibility |
| Scenarios | Exact literal binding works; larger imported registries can persist | Dynamic multi-slot/cyclic/parallel failures need actual evaluation inputs or a supported corrected mechanism; no universal runtime maximum established |
| NPCs and knowledge | Authored facts can be retrieved; dedicated image fields have observable effects | Live character records, identity merging, mutation and retrieval routing are not exposed; Secret Info is not the database |
| Import normalization | ID reminting, field omission and scope normalization observed | Internal failure stages and universal ID rules across entities remain unknown |
| Visibility | Extra-hidden values remain inspectable; AI-only automatic updates work | UI visibility does not establish full prompt inclusion or exclusion |
| Interpolation | Direct rendering, installed snapshots and deferred references differ | Other destination-specific timing and complete specialist inputs remain hidden |
| Randomness and selectors | Independent evaluations can differ; cached choices agree | Exact hidden evaluation counts and unselected-library exclusion need full prompts |
| AI tracker dependencies | Same-turn dependent values can be available | Hidden generation architecture is not inferable; explicit staging is needed for prior-state semantics |
| Format and YAML | Manual/script writes can bypass expectations; coercions occur | Complete grammar, XML mutation, strict type semantics and hidden AI repair are not fully established |
| Legacy list context | current() is rejected in Run Script | A supported List Update Target/Value context is unavailable in the current editor |
| Memory | Compression cadence from turn eight is user-confirmed; later recall occurs | Exact summary contents and contribution versus persistent context require summarizer visibility |
| Length | Strong override wording does not reliably achieve longer narration | No guaranteed length recipe, verified hidden maximum or validated reduction version |
| Images and video | Current wrappers and dedicated image fields affect results | Full image prompt/cache, universal precedence, internal macros and video runtime remain unverified |

| Recovery | Interrupted generation can leave a turn unretained | Server-side cause and standalone authenticated runner recovery require additional diagnostics/environment |
| Tooling | External parsing and merge defects identified | Reviewed-boundary parser/merge and a local browser capture/export harness are supplied; authenticated capture/export is verified, while gameplay recovery and server persistence remain unverified |

Firstly, if I have made any assertions in my description, evaluate whether you judge that they are reasonable and likely. If they are nonsensical, incoherent or blatantly impossible, the action should be DENIED. On the other hand, if the action is trivial and there is nothing to complicate it, skip the evaluation entirely and deem the action a SUCCESS. Don't overthink this! If the action doesn't warrant further evaluation, make a judgement and move on.

Assuming the action is not a trivial SUCCESS or DENIED, I would like you to evaluate what skill would be needed to succeed in this action, and how difficult it would be to do so. Please indicate which skill which is needed to succeed.
If applicable use this list: (<<skill_list>>) and a difficulty (from the list: <<difficulty_list>>). For example: {<<skill_example>>: <<difficulty_example>>}. Consider the difficulties carefully, evaluating what might be feasible in the situation. Identifying the skill and difficulty is very important!

Then, evaluate whether I would succeed in the action. To evaluate, consider my proficiency in various skills using either (<<skills_and_levels>>) or logical application of other skills. By comparing these difficulties to the stated difficulty of the action, you should conclusively decide whether the action is a SUCCESS or a FAILURE.

Base your decision on player character description, past, rest of the instructions and common sense - for example, if my skill is low but you know that I am able to perform the given action due to past events, treat me as more competent in this case. Again, don't overthink this - just make a sensible judgement given the information available to you and based on what makes sense for the story.

In some situations, you may wish to evaluate the action as a PARTIAL_SUCCESS instead - this is for something where my abilities are sufficient that I don't simply fail completely (or where failing completely would make for a boring story) but I also don't success. Either I achieve some but not all of what I wanted, I fail but have some silver lining, or I succeed but there are drawbacks or side-effects rather than a "clean" success.

In total, your evaluation should consist of an extremely brief discussion of your thinking (just a single sentence), a skill and difficulty, and then either DENIED, SUCCESS, FAILURE, or PARTIAL_SUCCESS (along with any clarifying remarks).

That's all you need to do for the evaluation, which should be returned in the 'evaluation' argument. Remember to conclude with one of DENIED, SUCCESS, FAILURE, or PARTIAL_SUCCESS.
